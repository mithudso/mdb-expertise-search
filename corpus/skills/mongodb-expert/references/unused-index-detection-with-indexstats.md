# Unused index detection with $indexStats

## Overview

$indexStats` reports per-index usage counters (`accesses.ops`, `accesses.since`) for the mongod node that runs it. Zero `ops` marks a drop candidate only if the `since` window spans the workload's full cycle and every replica-set member and shard also shows zero. Counters reset on restart, index drop/recreate and any `collMod` change, including hide/unhide. They exclude internal use (TTL deletes, chunk migration) and ignore unique-constraint and shard-key needs. MongoDB's own flow: `$indexStats`, hide the index, watch for regressions, then drop. Atlas Performance Advisor automates unused, redundant and hidden-index suggestions; Percona's exporter and PMM keep longer history. Dead indexes cost write latency, cache and disk; a wrong drop causes collection scans.

## Core Concepts

### Unused index detection with $indexStats

- $indexStats` is an aggregation stage that returns usage statistics for each index of a collection. Per index it returns `name`, `key`, `host`, `accesses` (`ops` and `since`), `shard` (sharded clusters only), `spec`, and `building` (only when true).[^c1-1][^c1-2][^c1-3]
- accesses.ops` counts user operations that used the index. It excludes internal operations: TTL-index deletion of expired documents, and index use during chunk split, move and post-move cleanup.[^c1-1][^c1-2][^c1-17][^c1-18]
- accesses.since` is the time from which MongoDB gathered the statistics for that index. It is populated even when `ops` is 0: the manual's sample output shows `_id_` and `price_1` with `ops: 0` and a set `since`. Read `ops` against the length of the window that `since` opens.[^c1-1][^c1-2][^c1-19]
- Index statistics reset on `mongod` restart, on index drop and recreation, and whenever `collMod` modifies the index. Changing `hidden` (only when the value actually changes) or `expireAfterSeconds` resets them; hiding an already hidden index or unhiding an already visible one does not.[^c1-1][^c1-2][^c1-6][^c1-5]
- The counters are per node. The `accesses` field reports usage only for the mongod where the aggregation runs, and MongoDB says to run `$indexStats` on each node in the cluster for fuller usage data. Output rows carry `host` (and `shard` on sharded clusters) so you can tell nodes apart.[^c1-1][^c1-2][^c1-3][^c1-4][^c1-23]
- The Atlas Data Explorer index `Usage` column counts lookups by the primary node only, and the Compass `Usage` column counts only the node Compass is connected to. Both pages call the number informational and send you to `$indexStats` on each node for decisions. verified-as-of: 2026-10-14[^c1-13][^c1-14]
- Unnecessary indexes degrade write performance and consume disk and memory, because inserts and indexed-field updates must maintain every index. The Atlas Performance Advisor suggests dropping unused, redundant and hidden indexes 'to improve write performance and increase storage space'.[^c1-4][^c1-11][^c1-18][^c1-20]
- $indexStats` dates from MongoDB 3.2: Pythian says 3.2 introduced it, and the 3.2.0 JIRA tickets SERVER-21815 (user operations only) and SERVER-22048 (`$match` recording) both describe its behavior as of 3.2.0. (two sources)[^c1-19][^c1-17][^c1-16]
- $indexStats` must be the first stage of an aggregation pipeline, is not allowed in transactions, and under access control needs a user with at least the `clusterMonitor` role.[^c1-1][^c1-2]
- $indexStats` lists hidden indexes too, and its `spec` carries `hidden: true` only for hidden indexes. Hidden indexes stay in statistics output because they are still maintained on every write and still use disk and memory.[^c1-5][^c1-1]
- $indexStats` is a collection-level aggregation stage: `db.<coll>.aggregate([{ $indexStats: {} }])`. It returns one document per index with `name`, `key`, `host` and `accesses` (`ops` and `since`). A sharded cluster adds `shard`. `spec` holds the full index definition and lists `hidden` only when it is true. `building` appears only while the index is building.[^c1-1][^c1-2][^c1-28]
- accesses.ops` counts user operations that used the index. `accesses.since` is the time from which MongoDB gathered statistics for that index; it is not the time of last use. So `ops: 0` means the index was not used since `since`. It does not mean the index was never used.[^c1-1][^c1-19][^c1-13]
- accesses.ops` excludes internal operations: deletions by TTL indexes, and chunk split, chunk migration and post-move deletion. MongoDB engineers recorded this in SERVER-21815 (affects 3.2.0, closed Done, no fix version). The manual now documents the exclusion.[^c1-1][^c1-17][^c1-18]
- The counters are node-local. `$indexStats` reports `accesses` only for the `mongod` that runs the aggregation. A read served by a secondary does not raise the primary's count. For cluster-wide usage, run `$indexStats` on every node: each replica-set member and each member of each shard.[^c1-1][^c1-4][^c1-3][^c1-23]
- An index's statistics reset when `mongod` restarts, when the index is dropped and recreated, and when `collMod` modifies the index. After a reset, `since` moves forward and `ops` starts again from zero.[^c1-1][^c1-2][^c1-18][^c1-31][^c1-28]
- $indexStats` must be the first stage of the aggregation pipeline. It is not allowed in transactions.[^c1-1][^c1-2][^c1-31]
- Unused indexes cost write throughput, storage and memory. Every insert and delete maintains every index on the collection. Every update that changes an indexed field maintains each index containing that field. No source read quantifies the saving.[^c1-29][^c1-4][^c1-11][^c1-18][^c1-20]

## Methodology

- Basic detection recipe: run `db.<coll>.aggregate([{ $indexStats: {} }])` per collection, keep entries with `accesses.ops == 0`, and skip `_id_` because `dropIndexes` never drops the `_id` index. The stage is per collection, so survey a deployment by looping `getSiblingDB(db).getCollectionNames()` and printing zero-ops indexes.[^c1-19][^c1-20][^c1-4][^c1-7] _(Unused index detection with $indexStats)_
- Judge zero `ops` only over a window that covers the workload's full cycle. Netdata asks for 24+ hours of representative load including peak and off-peak and nightly batches; Percona warns an index used once a month for heavy reporting looks unused otherwise; Pythian says to compare the window with `db.serverStatus().uptime`.[^c1-20][^c1-18][^c1-19] _(Unused index detection with $indexStats)_
- A drop candidate must show zero `ops` on every node that can serve reads: all replica-set members (secondaries can serve reads the primary never sees) and every shard's nodes. Netdata says to sum `accesses.ops` across shards before calling an index globally unused.[^c1-19][^c1-23][^c1-20][^c1-1] _(Unused index detection with $indexStats)_
- Hide-then-drop is MongoDB's documented flow: use `$indexStats` to shortlist, hide each candidate (`db.coll.hideIndex(name)` or `collMod` with `hidden: true`) so the planner stops using it while writes still maintain it, watch for regressions, then drop it (a hidden index can be dropped without unhiding) or unhide it at once if queries regress.[^c1-4][^c1-5][^c1-7][^c1-11] _(Unused index detection with $indexStats)_
- A hide trial cannot be judged with `$indexStats`: the planner cannot use a hidden index, so its `ops` cannot rise while hidden, and hiding resets its counters. Judge the trial by query latency, slow-query log COLLSCAN entries and `explain()` on critical query shapes. This follows from the Hidden Indexes behavior rules; no source states it as one sentence. (two sources)[^c1-5][^c1-20][^c1-11] _(Unused index detection with $indexStats)_
- Before dropping, take a backup of affected collections (Pythian) and record the current index definitions with `getIndexes()` so a dropped index can be recreated quickly (Netdata). (two sources)[^c1-19][^c1-20] _(Unused index detection with $indexStats)_
- Tentative: After a drop, Netdata checks the slow-query log for new COLLSCAN entries, runs `explain('executionStats')` on critical query shapes (a query may move to another index instead of scanning), and compares `opLatencies.writes` before and after to confirm the write-cost gain.[^c1-20] _(Unused index detection with $indexStats)_
- dropIndexes` and `db.collection.dropIndexes()` take an exclusive lock on the specified collection for the duration of the operation, and later operations on that collection wait. Drop during low traffic or a maintenance window.[^c1-7][^c1-8][^c1-20] _(Unused index detection with $indexStats)_
- Prioritise by size: combine zero-ops indexes with `collStats` `indexSizes` and `totalIndexSize` or `dbStats` `indexSize` to find the removals that free the most space. (two sources)[^c1-3][^c1-20] _(Unused index detection with $indexStats)_
- Let the counters span the longest real workload cycle before trusting a zero. A monthly reporting job, a nightly batch or a rarely run geo query can be the only user of an index. Compare `since`, and `db.serverStatus().uptime`, against that cycle.[^c1-18][^c1-19][^c1-20][^c1-31] _(Unused index detection with $indexStats)_
- MongoDB's documented removal sequence: find rarely used indexes with `$indexStats`, hide candidates with `db.collection.hideIndex()`, watch the effect, then drop with `db.collection.dropIndexes()`. If the impact is negative, unhide the index instead of rebuilding it. A hidden index can be dropped directly without unhiding it first.[^c1-4][^c1-5][^c1-7][^c1-11] _(Unused index detection with $indexStats)_
- Hiding tests only dependence on reads. A hidden index is invisible to the query planner and cannot be named in `hint()`. It is still maintained on every write, still enforces a unique constraint, and still expires documents if it is a TTL index. A clean hide period therefore says nothing about whether a unique or TTL index is still needed. (two sources)[^c1-5][^c1-11] _(Unused index detection with $indexStats)_
- Hiding an unhidden index, or unhiding a hidden one, resets its `$indexStats` counters. Hiding an already hidden index, or unhiding an already unhidden one, does not. While an index is hidden, judge impact from query latency, slow-query log entries and `explain()` plans, not from the hidden index's own counter. (two sources)[^c1-5][^c1-1][^c1-20] _(Unused index detection with $indexStats)_
- Verify after a drop. Check the slow-query log for new `COLLSCAN` entries on the collection. Run `explain('executionStats')` on critical query shapes. Compare write latency (`opLatencies.writes`) and the WiredTiger cache dirty ratio before and after. `explain` in `allPlansExecution` mode shows partial statistics from plan selection, which helps when a query may fall back to another index. (two sources)[^c1-20][^c1-3] _(Unused index detection with $indexStats)_
- Counters do not survive a restart, so export them. Sample `$indexStats` on a schedule into a monitoring system, for example PMM through `mongodb_exporter`. Percona notes the history then survives an instance restart, provided retention is at least one full application cycle. (two sources)[^c1-18][^c1-27] _(Unused index detection with $indexStats)_
- Combine evidence across nodes before declaring an index unused. Collect `$indexStats` from every replica-set member and every shard, and keep the index if any node shows use. Percona's advisor says to analyze every member before dropping. Netdata says to sum `accesses.ops` across shards. AWS's tool merges per-instance results. Pythian says to confirm the index is not used on secondaries.[^c1-23][^c1-20][^c1-29][^c1-19] _(Unused index detection with $indexStats)_

## Practical Patterns

- Leading-prefix redundancy: an index is redundant when its keys are a leading prefix of another index on the same collection ({ a: 1 } against { a: 1, b: -1 }); { b: -1 } is not. `$indexStats` does not detect this, so compare key patterns. The Performance Advisor does and lists the covering indexes so you can verify the drop.[^c1-11][^c1-20] _(Unused index detection with $indexStats)_
- Shard-key guard: since MongoDB 6.0, `dropIndexes` and `db.collection.dropIndexes()` raise an error if asked to remove the last remaining shard-key-compatible index, so a shard-key index with zero `ops` cannot be dropped as the last one.[^c1-7][^c1-8] _(Unused index detection with $indexStats)_
- Tentative: Replica-set members can carry different index sets (for example tagged or low-priority nodes), so per-node `$indexStats` lets you right-size indexes per node role, not only per collection.[^c1-18] _(Unused index detection with $indexStats)_
- Find redundant (prefix) indexes from index definitions, not from usage counters. An index is redundant if its keys are a prefix of another index in the same collection: `{ a: 1 }` is redundant next to `{ a: 1, b: -1 }`, but `{ b: -1 }` is not. Keep the compound index and drop the prefix index. Percona Toolkit `check-duplicated`, Atlas's Redundant badge and AWS's index-review each run this check separately from the zero-ops scan.[^c1-11][^c1-26][^c1-20][^c1-29][^c1-30] _(Unused index detection with $indexStats)_

## Anti-Patterns

- Do not drop on a short window. After a restart, rebuild or any `collMod` (including hide/unhide) every counter restarts at zero, so active indexes look unused. Netdata says not to drop within 24 hours of a restart; Pythian says to check `db.serverStatus().uptime` first.[^c1-1][^c1-20][^c1-19] _(Unused index detection with $indexStats)_
- Do not drop a TTL index because `ops` is 0. Expiry deletions by the TTL monitor are not counted, so an index that is actively expiring documents can report zero.[^c1-1][^c1-17][^c1-18] _(Unused index detection with $indexStats)_
- Do not drop a unique index because `ops` is 0. It can enforce uniqueness on writes with no reads. Percona says a uniqueness check on INSERT does not increment the counter; Netdata warns that dropping it removes the constraint and can allow duplicate keys. (two sources)[^c1-18][^c1-20][^c1-10] _(Unused index detection with $indexStats)_
- Tentative: Hiding an index does not suspend its constraints: a hidden unique index still enforces uniqueness and a hidden TTL index still expires documents. A hide trial therefore tests only planner use, not whether the constraint or expiry is still needed.[^c1-5] _(Unused index detection with $indexStats)_
- Do not drop on a short or freshly reset window. Restart, drop and recreate, `collMod` and hide/unhide all reset an index's counter, so a young `since` makes active indexes look unused. Rules of thumb differ: Atlas needs 7 or more days, Netdata asks for at least 24 hours of uptime under a representative workload. Choose the window from your own workload cycle. verified-as-of: 2026-10-18[^c1-1][^c1-5][^c1-11][^c1-20] _(Unused index detection with $indexStats)_
- A unique index can show `ops: 0` while still enforcing integrity. Percona reports that the uniqueness check on insert does not increment `ops`. Dropping the index removes the constraint and allows duplicate keys. Exclude unique indexes from zero-ops drop lists. A hidden unique index keeps enforcing its constraint too. (two sources)[^c1-18][^c1-20][^c1-5] _(Unused index detection with $indexStats)_
- An active TTL index can show `ops: 0`, because TTL deletions are not counted in `accesses.ops`. A hidden TTL index still expires documents, so neither the counter nor a hide test exposes the dependency. Dropping the index stops expiry. (two sources)[^c1-1][^c1-17][^c1-5] _(Unused index detection with $indexStats)_
- Use of the shard key's supporting index by chunk split and migration is not counted in `ops`, so a zero does not prove that index is idle. Since MongoDB 6.0, `dropIndexes` raises an error if you try to drop the last remaining shard-key-compatible index. (two sources)[^c1-1][^c1-7] _(Unused index detection with $indexStats)_
- A usage count alone is not a drop decision. Studio 3T says the drop decision is rarely a simple question of whether the index was used recently. AWS says never to drop an index without discussing it with all interested parties and testing performance. Atlas says to consider hiding an index before dropping it. (two sources)[^c1-31][^c1-29][^c1-30][^c1-11] _(Unused index detection with $indexStats)_

## Troubleshooting

- Tentative: Old-version undercount: SERVER-22048, reported against 3.2.0 and fixed in 3.2.3 and 3.3.1, added `$indexStats` recording for aggregation `$match` index use (its title also names mapReduce `query` index use). Counters from 3.2.0 to 3.2.2 can show zero for indexes that `$match` stages used.[^c1-16] _(Unused index detection with $indexStats)_
- If many indexes show zero `ops`, compare each `accesses.since` and `db.serverStatus().uptime` with the last restart before trusting the list. A recent restart makes active indexes look unused, and PMM's advisor documents the same caveat. (two sources)[^c1-19][^c1-20][^c1-23] _(Unused index detection with $indexStats)_
- Old servers can undercount. `$indexStats` exists since MongoDB 3.2. In 3.2.0 and 3.2.1, index use by aggregation `$match` and by mapReduce was not recorded (SERVER-22048; SERVER-22183 is a duplicate report). The fix shipped in 3.2.3 and 3.3.1. A zero from such a build is not reliable. (two sources)[^c1-16][^c1-25][^c1-19][^c1-31] _(Unused index detection with $indexStats)_
- dropIndexes` takes an exclusive lock on the collection for its duration, and later operations on that collection wait. Schedule drops for low traffic and watch lock waits. verified-as-of: 2026-10-14[^c1-7][^c1-20] _(Unused index detection with $indexStats)_
- Continuous `$indexStats` scraping is an extra aggregate query and can add load. Percona keeps the collector off by default for that reason. On instances with many collections, `--collector.collstats-limit=N` disables the collstats, dbstats, topmetrics and indexstats collectors when the collection count exceeds N. `--mongodb.indexstats-colls` restricts scraping to named collections. (two sources) verified-as-of: 2026-10-20[^c1-18][^c1-27] _(Unused index detection with $indexStats)_
- $indexStats` needs authorization. The manual requires at least the `clusterMonitor` role when access control is on. AWS's index-review README lists `indexStats` among the permissions it needs, with collStats, listCollections, listDatabases and serverStatus. (two sources)[^c1-1][^c1-30] _(Unused index detection with $indexStats)_

## Disagreements & Open Questions

- Disagreement (Unused index detection with $indexStats): Meaning of `since`: Percona's 2018 post says it is 'when the ops counter first iterated to one'. The MongoDB manual says it is 'the time from which MongoDB gathered the statistics', and both the manual's and Percona's own sample outputs show `since` set while `ops` is 0.[^c1-18][^c1-1][^c1-19]
- Disagreement (Unused index detection with $indexStats): Internal operations: Netdata says internal operations can inflate `$indexStats` counters and that `_id_` 'shows usage from internal operations'. The MongoDB manual and SERVER-21815 say only user operations are counted, and the manual's and Pythian's sample outputs show `_id_` at `ops: 0`.[^c1-20][^c1-1][^c1-17][^c1-19]
- Disagreement (Unused index detection with $indexStats): Observation window: Netdata treats zero `ops` after 24+ hours of normal load as a removal candidate (while also saying to wait a full workload cycle), the Atlas Performance Advisor waits 7+ days after creation or restart, and Percona says to wait through the longest cycle, such as a monthly report.[^c1-20][^c1-11][^c1-18]
- Disagreement (Unused index detection with $indexStats): Lock scope of an index drop: Pythian (2018) says a write lock on the whole database blocks all operations; the current MongoDB manual says `dropIndexes` takes an exclusive lock on the specified collection.[^c1-19][^c1-7]
- Disagreement (Unused index detection with $indexStats): Redundancy rule: the Performance Advisor flags an index as redundant only when it is a leading prefix of another index ({ b: -1 } is not redundant to { a: 1, b: -1 }). The manual's 'Remove Unnecessary Indexes' walkthrough drops { time: 1 } as covered by { day: 1, time: 1 }, mixes the field names `days` and `day`, and its own sample output shows `time_1` with ops 1.[^c1-11][^c1-4]
- Disagreement (Unused index detection with $indexStats): FeatureCompatibilityVersion needed to hide an index: the Hidden Indexes and `hideIndex()` pages say 7.0 or greater; the `collMod` page says 4.4 or greater.[^c1-5][^c1-9][^c1-6]
- Disagreement (Unused index detection with $indexStats): Exporter flag drift: Percona's 2018 post enables index usage in PMM with `-collect.indexusage`; the current exporter reference documents `--collector.indexstats` and `--mongodb.indexstats-colls`.[^c1-18][^c1-22]
- Disagreement (Unused index detection with $indexStats): Three sources define `since` differently. The MongoDB manual says it is the time from which MongoDB gathered the statistics (its own example shows `ops: 0` entries with a `since` value). Percona's 2018 post says it is when the ops counter first iterated to one, yet its own sample output shows `ops: 0` with a `since` value. Atlas's Admin API describes `since` as the 'Date of most recent usage of index'. Treat `accesses.since` as the window start, and verify what the Atlas field holds before using it that way.[^c1-1][^c1-18][^c1-24]
- Disagreement (Unused index detection with $indexStats): The manual's 'Remove Unnecessary Indexes' example says `{ time: 1 }` can be dropped because `{ day: 1, time: 1 }` covers time-related queries. Atlas's redundancy rule counts only prefixes, and its own example says `{ b: -1 }` is not redundant next to `{ a: 1, b: -1 }`. By that rule `{ time: 1 }` is not redundant. The example also lists `days` in the text but `day_1` in the output.[^c1-4][^c1-11]
- Disagreement (Unused index detection with $indexStats): The minimum observation window differs. Atlas flags an index as unused after 7 or more days. Netdata asks for at least 24 hours of uptime under a representative workload. Percona gives no number and says to wait for a considerable time, citing a once-a-month report as the hazard.[^c1-11][^c1-20][^c1-18]
- Disagreement (Unused index detection with $indexStats): Sharded-cluster collection differs. Percona's PMM advisor says to run its `$indexStats` script on mongos (sharded cluster) or mongod (replica set) nodes. Netdata says `$indexStats` on a mongos does not aggregate statistics across shards and tells you to run it on each shard primary.
