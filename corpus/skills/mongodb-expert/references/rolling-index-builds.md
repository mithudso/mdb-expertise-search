# Rolling index builds

## Overview

A rolling index build creates an index on one replica set member at a time instead of on all members at once. The operator hides a member, restarts it as a standalone on another port, builds the index, rejoins it, and repeats for each secondary. The primary is stepped down and built last, so at least one election occurs. Atlas, Ops Manager and Cloud Manager automate this. Since MongoDB 4.4 the default build runs on all data-bearing members under a commit quorum, so MongoDB now limits rolling builds to deployments with high average CPU or a WiredTiger cache regularly over 90% full. The costs are lower resiliency, longer builds, an oplog-window requirement, and no unique indexes unless writes stop. A 2022 critical alert covered an automation defect, fixed in Atlas on 2023-08-22, that left indexes open to key inconsistencies. The manual procedure was unaffected.

## Core Concepts

### Rolling index builds

- A rolling index build creates an index on one replica set member at a time instead of on all members at once. MongoDB hides at most one member at a time, builds the index on it as a standalone, starts with the secondaries, and builds on the former primary last.[^c1-1][^c1-2][^c1-14][^c1-15]
- A rolling build requires at least one replica set election. After every secondary has the index, the operator steps the primary down with rs.stepDown() and then builds on the former primary.[^c1-1][^c1-2][^c1-9][^c1-14]
- MongoDB's documentation states that rolling index builds lower the resiliency of the cluster and increase build duration. The Atlas, Ops Manager and Cloud Manager pages add that MongoDB only recommends rolling builds when regular index builds do not meet your needs.[^c1-1][^c1-2][^c1-7][^c1-10][^c1-11]
- Since MongoDB 4.4 the default (non-rolling) index build on a replica set or sharded cluster runs simultaneously on all data-bearing members. The primary marks the index ready only after a commit quorum of data-bearing voting members, including itself, has finished building. The default commit quorum is votingMembers, meaning all data-bearing voting members.[^c1-4][^c1-13]
- Tentative: Simultaneous index builds require featureCompatibilityVersion 4.4 or higher on every mongod in the replica set or sharded cluster.[^c1-4]
- MongoDB's current guidance is to use a rolling build only if average CPU utilization exceeds (N-1)/N-10%, where N is the number of CPU threads available to mongod, or if the WiredTiger cache fill ratio regularly exceeds 90%. If the deployment meets neither condition, MongoDB says to use the default index build. verified-as-of: 2026-10-14[^c1-1][^c1-2][^c1-5][^c1-8]
- A rolling index build creates the index on one replica set member at a time instead of on all data-bearing members at once. MongoDB takes at most one member out of service at a time, starts with the secondaries, builds the index on that member running as a standalone, and handles the primary last.[^c1-1][^c1-2][^c1-14]
- A rolling build requires at least one replica set election, because the primary is stepped down so the former primary can be indexed. MongoDB states that rolling builds lower the resiliency of the cluster and increase build duration.[^c1-1][^c1-4][^c1-2][^c1-9]
- MongoDB's manual says to use a rolling build only in two cases: average CPU utilization exceeds (N-1)/N-10%, where N is the number of CPU threads available to mongod, or the WiredTiger cache fill ratio regularly exceeds 90%. In every other case the manual says to use the default index build. verified-as-of: 2026-10-14[^c1-1][^c1-2][^c1-5]
- Since MongoDB 4.4 the default index build runs simultaneously on all data-bearing replica set members (only on shards that hold data for the collection in a sharded cluster). Every mongod needs featureCompatibilityVersion 4.4 or higher. The primary waits for a commit quorum of votes before it marks the index ready, and the default commitQuorum is votingMembers. verified-as-of: 2026-10-19[^c1-4][^c1-13]
- Before MongoDB 4.4, Percona says the best practice for creating an index was a rolling build, and many teams instead built directly on the primary and let the index replicate. ScaleGrid (2017) called rolling the preferred method because foreground builds block for hours and background builds run longer and still degrade performance. The MongoDB FAQ confirms that under featureCompatibilityVersion 4.0 the default foreground build holds the exclusive lock for the whole build. (two sources)[^c1-13][^c1-23][^c1-5]
- Since featureCompatibilityVersion 4.2 the default (non-rolling) build holds the exclusive collection lock only at the start and the end of the build. The rest of the build yields to interleaved reads and writes.[^c1-5][^c1-15]
- Rolling builds are not available on every Atlas tier. The Atlas UI allows them only on M10 and larger clusters. The Atlas CLI reference says a rolling index cannot be created on an M0 free cluster or an M2/M5 shared cluster. The manual says the feature is not supported on Atlas Infinite clusters. (two sources) verified-as-of: 2026-10-14[^c1-7][^c1-21][^c1-1]
- Rolling builds apply to replica sets and sharded clusters, not to standalone mongod deployments. Data Explorer in Ops Manager and Cloud Manager does not support rolling builds for standalone deployments, and ScaleGrid notes that a standalone instance can only use a background build. (two sources)[^c1-10][^c1-11][^c1-23]

## Tools & Frameworks

- Atlas offers rolling index builds only on M10+ clusters. The Atlas Administration API documentation says you cannot create a rolling index on an M0 free cluster or an M2/M5 shared cluster. verified-as-of: 2026-10-14[^c1-7][^c1-8] _(Rolling index builds)_
- Tentative: Rolling index builds are not supported on Atlas Infinite clusters. verified-as-of: 2026-10-14[^c1-1] _(Rolling index builds)_
- In Atlas, the Create Index dialog offers a 'Build in rolling process' option. Atlas then takes one node at a time out of the replica set, starting with the secondaries, starts it in standalone mode, builds the index, and returns the node to the set. Atlas says nodes may appear down while it builds offline and that this is expected. (two sources) verified-as-of: 2026-10-14[^c1-7][^c1-9] _(Rolling index builds)_
- The Atlas Administration API exposes rolling builds as 'Create One Rolling Index' (a POST to /api/atlas/v2/groups/{groupId}/clusters/{clusterName}/index, API version 2023-01-01), and the Atlas CLI wraps it as 'atlas api rollingIndex createRollingIndex'. The caller needs the Project Data Access Admin role. (two sources) verified-as-of: 2026-10-14[^c1-9][^c1-8][^c1-17] _(Rolling index builds)_
- Ops Manager and Cloud Manager Data Explorer can build indexes in a rolling fashion on replica sets and sharded clusters, but not on standalone deployments. The automation removes one node at a time from the cluster, starting with a secondary.[^c1-10][^c1-11] _(Rolling index builds)_
- Ops Manager and Cloud Manager rolling builds are incompatible with the unique, storageEngine, textIndexVersion and 2dsphereIndexVersion index options. Ops Manager ignores these options if you set them.[^c1-10][^c1-11] _(Rolling index builds)_
- Tentative: Starting in MongoDB 8.0, the sharded-cluster procedure points to the directShardOperations role for maintenance that runs commands directly against a shard. The docs warn that this role can make the cluster stop working correctly and may cause data corruption, so use it only for maintenance or under MongoDB support guidance, and stop using it when the maintenance ends.[^c1-3] _(Rolling index builds)_
- Tentative: With the Percona Operator for MongoDB on Kubernetes you cannot simply stop mongod in a pod, because the health check fails and Kubernetes starts a replacement pod at once. The Operator's sleep-forever file in /data/db keeps the pod asleep without starting mongod. Then run mongod --shutdown, start a standalone mongod on another port (the example uses 27117), build the index, run db.shutdownServer(), and delete the file to resume. The author recommends doing this by hand rather than with automation unless you are very confident in it.[^c1-14] _(Rolling index builds)_
- Atlas exposes rolling builds three ways: the 'Build in rolling process' option in the Create Index dialog of the Atlas UI; the Atlas CLI command atlas clusters indexes create ('Atlas builds the index in a rolling manner'); and the Atlas Admin API operation behind atlas api rollingIndex createRollingIndex (API version 2023-01-01). The CLI and API calls need the Project Data Access Admin role. verified-as-of: 2026-10-14[^c1-7][^c1-20][^c1-9] _(Rolling index builds)_
- During an Atlas UI rolling build, Atlas takes each node out of the replica set, starts it in standalone mode, builds the index, returns it to the set, and repeats node by node. Nodes may appear as down while Atlas builds offline; Atlas says this is expected behavior. (two sources) verified-as-of: 2026-10-14[^c1-7][^c1-9] _(Rolling index builds)_
- Automated rolling builds do not support unique indexes. Atlas rejects a configuration that combines the rolling option with unique and returns an error. Ops Manager and Cloud Manager ignore the options unique, storageEngine, textIndexVersion and 2dsphereIndexVersion for rolling builds. MongoDB's 2022 alert also states that unique indexes are not created with the rolling index build process. verified-as-of: 2026-10-14[^c1-7][^c1-10][^c1-11][^c1-12] _(Rolling index builds)_
- Ops Manager and Cloud Manager Data Explorer remove one node at a time, starting with a secondary. They cancel a rolling build that does not succeed on every node and remove the index from the nodes where it was built. On cancellation they create an Activity Feed event and email the project owner the cluster, namespace, project, organization and a link to the event. (two sources)[^c1-10][^c1-11] _(Rolling index builds)_
- In Ops Manager and Cloud Manager, request rolling and non-rolling index builds one at a time: wait for the running build to finish before requesting another, and wait for a running rolling build before requesting a second rolling build. By default up to three non-rolling index builds can run concurrently. (two sources) verified-as-of: 2026-10-14[^c1-10][^c1-11] _(Rolling index builds)_

## Methodology

- Build on the secondaries one at a time, and let each member catch up on replication before starting the next one. Step the primary down and build on it last.[^c1-2][^c1-14][^c1-15] _(Rolling index builds)_
- Tentative: The replica set tutorial hides the secondary before taking it offline. On the primary, record the member's priority, then set priority to 0 and hidden to true with rs.reconfig(). After the build and catch-up, restore the original priority and set hidden to false with rs.reconfig().[^c1-2] _(Rolling index builds)_
- To build in isolation, restart the member as a standalone: remove or comment out replication.replSetName (or --replSet) and use a different port. The different port keeps the other members and all clients from contacting the member while the index builds.[^c1-2][^c1-14][^c1-15] _(Rolling index builds)_
- While a member runs as a standalone for the build, set the server parameter disableLogicalSessionCacheRefresh to true. Remove that parameter before restarting the member as a replica set member.[^c1-2][^c1-3] _(Rolling index builds)_
- The member being built is out of the replica set during the build, so the oplog must cover the build time. MongoDB says to size the oplog so the build can finish without the member falling too far behind to catch up. Percona's worked example calls for a two-hour oplog window for a two-hour build, plus a margin.[^c1-2][^c1-3][^c1-6][^c1-14][^c1-15] _(Rolling index builds)_
- Tentative: On a sharded cluster, first disable migrations for the collection with setAllowMigrations:false through mongos. Next run an aggregation with $collStats grouped by shard to find the shards that hold chunks. Then run the secondary-then-primary rolling sequence on those shards only, and finally re-enable migrations with setAllowMigrations:true. An unsharded collection returns NamespaceNotSharded for the setAllowMigrations command, which the docs say to ignore.[^c1-3] _(Rolling index builds)_
- Tentative: When a shard member is restarted as a standalone for a rolling build, the docs also have you comment out sharding.clusterRole and set skipShardingConfigurationChecks to true, in addition to the replica set changes. Remove both skipShardingConfigurationChecks and disableLogicalSessionCacheRefresh before restarting the member as a shard replica set member.[^c1-3] _(Rolling index builds)_
- Manual replica-set procedure, per secondary: on the primary, hide the member (set priority 0 and hidden 1 with rs.reconfig, saving the original priority); restart the member as a standalone; run createIndex on it; restart it as a replica set member and let replication catch up; then restore its priority and set hidden false. Repeat for each secondary. Last, run rs.stepDown() on the primary and repeat the steps on the former primary.[^c1-2][^c1-1][^c1-14] _(Rolling index builds)_
- While a member runs as a standalone it must use a different port than the replica set port, so other members and clients do not contact it, and the manual tells you to set the setParameter disableLogicalSessionCacheRefresh to true. When the member rejoins the set you must remove disableLogicalSessionCacheRefresh and restore the original port and replication.replSetName.[^c1-2][^c1-3][^c1-18] _(Rolling index builds)_
- In the sharded-cluster procedure, a shard member restarted as a standalone must also set skipShardingConfigurationChecks to true (together with disableLogicalSessionCacheRefresh), and you must remove both parameters before it rejoins. The current manual also has you comment out replication.replSetName and sharding.clusterRole during the standalone window.[^c1-3][^c1-18] _(Rolling index builds)_
- Tentative: On a sharded cluster, build only on shards that hold chunks for the collection. The current manual finds them with db.getSiblingDB(db).getCollection(coll).aggregate([{$collStats:{}},{$group:{_id:'$ns',shard_list:{$addToSet:'$shard'}}}]). The manual also warns not to run DDL operations while the rolling build is in progress.[^c1-3] _(Rolling index builds)_
- The sharded-cluster procedure changed between doc versions. The 7.0 manual starts with 'A. Stop the Balancer' and runs sh.stopBalancer() on a mongos. The current manual starts with 'A. Stop Migrations' and runs setAllowMigrations with allowMigrations false for the one collection, then re-enables migrations in step E. On an unsharded collection the NamespaceNotSharded error can be ignored. verified-as-of: 2026-10-14[^c1-18][^c1-3] _(Rolling index builds)_
- Size the oplog before starting. The oplog window must be longer than the time one member needs to build the index, or that member falls too far behind to catch up. Percona's example: a two-hour build needs at least a two-hour oplog window, plus margin.[^c1-2][^c1-14][^c1-15] _(Rolling index builds)_

## Practical Patterns

- On Atlas, a documented alternative to a rolling build is to scale the cluster up temporarily so it meets the requirements for a default index build. Atlas charges for the scaling.[^c1-2][^c1-5] _(Rolling index builds)_
- To avoid a default build that waits on an unreachable member without using a rolling build, pass the commitQuorum option to createIndex()/createIndexes() when you start the build. MongoDB also provides the setIndexCommitQuorum command to change the quorum of a build already in progress. Percona's test used commitQuorum 'majority' and the build finished with one of three voting nodes down.[^c1-4][^c1-13] _(Rolling index builds)_
- On Atlas, the documented alternative to a rolling build is to temporarily scale the cluster up to meet the requirements of a default index build. Atlas charges for the scaling, and the manual points to the Cluster Configuration Costs page.[^c1-2][^c1-5] _(Rolling index builds)_
- Percona recommends rolling builds for teams with very tight SLAs or systems already close to peak capacity (2025), and its 2023 commitQuorum post still concludes that the best practice is to create indexes in a rolling manner even on 4.4 and later. (two sources)[^c1-14][^c1-13] _(Rolling index builds)_
- On Kubernetes, stopping mongod inside a pod fails the health check and Kubernetes replaces the pod. The Percona Operator workaround: create /data/db/sleep-forever (for example with kubectl exec ... touch) so the container entry point sleeps without starting mongod; generate the TLS PEM files by hand; start mongod as a standalone on another port without --replSet; build; delete the file so the pod resumes and catches up from the oplog. Do secondaries first, then rs.stepDown() the primary. Percona advises doing this manually unless you trust your automation. (two sources) verified-as-of: 2026-01-12[^c1-14][^c1-22] _(Rolling index builds)_

## Anti-Patterns

- Do not use the rolling procedure for a unique index unless you can stop all writes to the collection for the whole procedure. Otherwise members can end up with inconsistent data. If you cannot stop writes, build the unique index with createIndex() on the primary (replica set) or through mongos (sharded cluster).[^c1-2][^c1-3] _(Rolling index builds)_
- MongoDB warns against running a rolling index build and a replicated (default) index build at the same time, because it might lead to unexpected issues such as broken builds and crash loops.[^c1-1][^c1-2][^c1-3][^c1-4][^c1-5][^c1-7] _(Rolling index builds)_
- Atlas, Ops Manager and Cloud Manager do not support a unique rolling build. Atlas rejects a rolling build that sets the unique option with an error, the Atlas API reference says unique is unsupported for rolling indexes, and Ops Manager and Cloud Manager list unique as incompatible with rolling builds.[^c1-7][^c1-10][^c1-11][^c1-17] _(Rolling index builds)_
- In Ops Manager and Cloud Manager, request rolling and non-rolling index builds one after another, never at the same time. Wait for a running rolling build to finish before requesting another rolling build.[^c1-10][^c1-11] _(Rolling index builds)_
- Tentative: Do not run DDL operations while a rolling index build is in progress on a sharded cluster.[^c1-3] _(Rolling index builds)_
- Never run a rolling index build and a default (replicated) index build at the same time. MongoDB warns this might lead to unexpected issues, such as broken builds and crash loops. Ops Manager and Cloud Manager tell you to request the builds sequentially.[^c1-1][^c1-2][^c1-3][^c1-4][^c1-7][^c1-10] _(Rolling index builds)_
- Do not use the manual rolling procedure for a unique index unless you can stop all writes to the collection for the whole procedure; otherwise the members can end up with inconsistent data. If you cannot stop writes, build the unique index with createIndex on the primary (on a mongos for a sharded cluster).[^c1-2][^c1-3] _(Rolling index builds)_
- Do not make rolling builds the default choice. Atlas, Ops Manager and Cloud Manager all state that rolling builds reduce cluster resiliency and increase build time, and that MongoDB only recommends them when regular index builds do not meet your needs.[^c1-7][^c1-10][^c1-11] _(Rolling index builds)_

## Troubleshooting

- Tentative: In May 2024 a user who sent unique:true to the Atlas rolling-index endpoint received HTTP 500 'Unexpected error' instead of a validation message. The same request without unique returned HTTP 202. verified-as-of: 2024-05-07[^c1-17] _(Rolling index builds)_
- If an Ops Manager or Cloud Manager rolling build succeeds on some nodes and fails on others, the automation cancels the build and removes the index from the nodes where it succeeded. It posts an activity feed event and emails the project owner. After an aborted rolling build, run listIndexes on each node to confirm the cancelled index is gone; otherwise the cluster might stay inconsistent.[^c1-10][^c1-11] _(Rolling index builds)_
- Ops Manager and Cloud Manager name five design patterns that commonly trigger a restart loop in a rolling build: an index key that exceeds the index key limit; an index name that already exists; an index on more than one array field; an index on a collection that has the maximum number of text indexes; and a text index on a collection that has the maximum number of text indexes.[^c1-10][^c1-11] _(Rolling index builds)_
- MongoDB's critical alert on rolling index builds (the URL is dated September 2022) says Atlas, Cloud Manager and Ops Manager 'rolling index builds' on MongoDB 4.2.19+, 4.4.13+, 5.0.6+ and 6.0.0+ could create indexes that are vulnerable to index key inconsistencies after a replication rollback or server crash. Affected indexes show log=(enabled=true) in the indexDetails.<indexName>.creationString field of collStats output.[^c1-12][^c1-10][^c1-11] _(Rolling index builds)_
- Tentative: The alert names two triggers and two symptoms. Triggers: a secondary rolls back writes that updated the index, or a primary crashes within the journalCommitInterval (default 50 ms) of writes that updated the index. Symptoms: extra index entries that give wrong results for covered queries, and out-of-date or missing entries that give incomplete results for queries that use the index.[^c1-12] _(Rolling index builds)_
- The alert's scope is the automated feature only. Indexes built with the documented manual rolling procedure are not affected. Unique indexes, including _id, are not affected because they are not created with the automated rolling process.[^c1-12][^c1-10][^c1-11] _(Rolling index builds)_
- Atlas deployed a fix on 2023-08-22 that makes rolling index builds safe on all MongoDB versions, though earlier builds may have affected some clusters. Cloud Manager needs MongoDB Agent 12.4.0.7703 or later. For Ops Manager the alert lists agents 11.0.20.7105-1+ (Ops Manager 5.0) and 12.0.11.7605-1+ (Ops Manager 6.0). Alternatively upgrade the cluster to 4.2.23+, 4.4.17+, 5.0.12+ or 6.0.2+. Upgrading does not repair indexes that are already inconsistent. (two sources) verified-as-of: 2026-10-14[^c1-12][^c1-10][^c1-11] _(Rolling index builds)_
- Tentative: For possible inconsistencies the alert says to run validate on every collection on every node and to resync any node where validate reports failures. A logical initial sync remediates inconsistencies on a node. If you cannot tell which indexes are affected, resync the node or rebuild the indexes with the documented manual rolling process or, on MongoDB 4.4+, with the optimized non-blocking build.[^c1-12] _(Rolling index builds)_
- If a member stays out longer than the oplog window, it can no longer catch up by replication. It goes into RECOVERING with 'too stale to catch up' and needs a full initial sync, which can take hours to days depending on data size and network throughput.[^c1-6][^c1-16] _(Rolling index builds)_
- A default build with the default commit quorum (votingMembers) waits for every data-bearing voting member. If one is unreachable, the build keeps running until that member returns. Percona showed this with one secondary down.[^c1-4][^c1-13] _(Rolling index builds)_
- Tentative: If you restart a mongod as a standalone while it has an in-progress replicated index build, the mongod cannot restart that build. The build stays paused until you drop it manually.[^c1-4] _(Rolling index builds)_
- A manual rolling build across shards can leave a sharded collection with inconsistent indexes if it fails on one shard or builds a different index specification on one shard. The config server primary periodically checks for inconsistent indexes; configure the checks with enableShardedIndexConsistencyCheck and shardedIndexConsistencyCheckIntervalMS. serverStatus on the config server primary reports shardedIndexConsistency.[^c1-3][^c1-4] _(Rolling index builds)_
- Before building a unique index on a sharded collection, check that no document violates the constraint. If one shard holds a chunk with duplicates, the build can succeed on the shards without duplicates and fail on that shard, which leaves inconsistent indexes. Running dropIndex() through mongos removes the index from the collection on all shards.[^c1-3][^c1-4] _(Rolling index builds)_
- SERVER-68925 incident (2022): indexes created by the automated 'rolling index build' feature of Atlas, Cloud Manager and Ops Manager had WiredTiger table logging enabled. Affected indexes show log=(enabled=true) in the indexDetails.<index>.creationString field of the collStats output. After a secondary's replication rollback, or a primary crash within the journalCommitInterval (default 50 ms), such an index can hold extra entries (wrong covered-query results) or stale or missing entries (incomplete results). Unique indexes (including _id) and indexes built with the documented manual procedure were not affected. SERVER-68925 restores the startup check of WiredTiger table logging settings.[^c1-12][^c1-19][^c1-10] _(Rolling index builds)_
- SERVER-68925 affected versions and fixes. Server fix versions: 4.2.23, 4.4.17, 5.0.12, 6.0.2 (also 6.1.0-rc1 and 6.2.0-rc0). The Ops Manager and Cloud Manager docs name the clusters at risk as 4.2.19-4.2.22, 4.4.13-4.4.16, 5.0.6-5.0.11 and 6.0.0-6.0.1, and name fixed agents as 12.0.11.7606 or later (Ops Manager) and 12.4.0.7703 or later (Cloud Manager). The ticket was created 2022-08-18 and resolved 2022-08-26.[^c1-19][^c1-10][^c1-11][^c1-12] _(Rolling index builds)_
- To build safely after the SERVER-68925 incident, use the documented manual rolling procedure or upgrade the agent or server to a fixed version. To repair existing inconsistencies, MongoDB's alert says to run validate on each collection on each node and resync (logical initial sync) any node that fails. (two sources)[^c1-12][^c1-10] _(Rolling index builds)_
- Ops Manager and Cloud Manager automated rolling builds can enter a restart loop when the index cannot be built. Patterns that commonly trigger it: the index key exceeds the index key limit; the index name already exists; an index on more than one array field; a new text index on a collection that already has the maximum number of text indexes. (two sources)[^c1-10][^c1-11] _(Rolling index builds)_
- After an aborted or cancelled automated rolling build in Ops Manager or Cloud Manager, run listIndexes on each node to verify the cancelled index no longer exists. Otherwise the cluster might remain in an inconsistent state. (two sources)[^c1-10][^c1-11] _(Rolling index builds)_
- A sharded collection has an inconsistent index when the shards that hold its chunks do not all have the same indexes with the same options. Rolling builds cause this when the build fails on one shard or uses a different specification, and a unique build can succeed on shards without duplicates but fail on the shard whose chunk has duplicates. The config server primary checks periodically (enableShardedIndexConsistencyCheck, shardedIndexConsistencyCheckIntervalMS), and serverStatus on it reports shardedIndexConsistency.[^c1-3][^c1-4] _(Rolling index builds)_
- Tentative: Cloud Manager docs: after a rolling build, if the MongoDB database runs with featureCompatibilityVersion lower than 4.2, resync the head database so it takes the new index into account.[^c1-11] _(Rolling index builds)_

## Disagreements & Open Questions

- Disagreement (Rolling index builds): Percona's June 2023 commitQuorum post concludes 'the best practice is to create indexes in a rolling manner', even after describing the simultaneous default build of 4.4+. MongoDB's current documentation limits rolling builds to deployments with high average CPU or a WiredTiger cache regularly over 90% full, and tells every other deployment to use the default build.[^c1-13][^c1-1][^c1-2]
- Disagreement (Rolling index builds): OneUptime's March 2026 guide presents the standalone-restart rolling build as the general way to build an index without impact ('Always use the standalone restart approach'). It gives no CPU or cache criteria, no unique-index caveat and no commit-quorum context. MongoDB's documentation restricts rolling builds to the CPU and cache cases and requires a write stop for unique indexes.[^c1-15][^c1-1][^c1-2]
- Disagreement (Rolling index builds): The critical alert lists MongoDB Agent 12.0.11.7605-1+ as the Ops Manager 6.0 fix, while the current Ops Manager Data Explorer page tells users to upgrade to agent 12.0.11.7606 or later.[^c1-12][^c1-10]
- Disagreement (Rolling index builds): Percona calls rolling builds the best practice for creating indexes, even on 4.4 and later, and recommends them for tight SLAs or near-peak systems. MongoDB's manual says to use a rolling build only when average CPU exceeds (N-1)/N-10% or the WiredTiger cache fill ratio regularly exceeds 90%, and to use the default build otherwise.[^c1-13][^c1-14][^c1-1]
- Disagreement (Rolling index builds): ScaleGrid (2017, a vendor post that promotes its own rolling-build orchestration) says rolling builds give no significant performance impact. MongoDB's current docs say rolling builds lower resiliency, increase build duration and require an election.[^c1-23][^c1-1]
- Disagreement (Rolling index builds): The sharded-cluster procedure differs by doc version: the 7.0 manual stops the balancer with sh.stopBalancer(); the current manual blocks migrations for the one collection with setAllowMigrations. Older blogs and runbooks may describe only the balancer step.[^c1-18][^c1-3]
- Disagreement (Rolling index builds): The 2022 alert lists open-ended affected server versions (4.2.19+, 4.4.13+, 5.0.6+, 6.0.0+). The Ops Manager and Cloud Manager docs bound them (4.2.19-4.2.22, 4.4.13-4.4.16, 5.0.6-5.0.11, 6.0.0-6.0.1), and SERVER-68925 lists fix versions 4.2.23, 4.4.17, 5.0.12 and 6.0.2.[^c1-12][^c1-10][^c1-11][^c1-19]
- Disagreement (Rolling index builds): The alert says the Atlas fix was deployed on 'August 22, 2023', but its URL is dated sept-2022 and SERVER-68925 was resolved on 2022-08-26.
