# Bucket catalog memory and closure reasons

## Overview

MongoDB time series inserts go through a per-mongod in-memory bucket catalog: open buckets plus small archived records, split across 32 hash stripes. Buckets leave open state for distinct reasons: time forward (soft close), time backward (archive), count, size, schema change and cache pressure (hard close), plus idle-bucket expiry when catalog memory passes timeseriesIdleBucketExpiryMemoryUsageThreshold (default 5% of RAM from 8.0.5, 2.5% before). The 'cache pressure' limit is cacheSize / (2 * node-wide active buckets), floored at 5 KiB. It is a computed budget, not observed eviction. SERVER-89233 (fixed 8.0.5) shows how inflated cardinality yields one-document buckets. The manual is stale on the 2.5% default, on 'in WiredTiger', and on numBucketsClosedDueToTimeBackward.

## Core Concepts

### Bucket catalog memory and closure reasons

- mongod keeps one in-memory bucket catalog for all time series collections on the node. It holds the open buckets and a small record for each archived bucket, split across 32 hash stripes; a given metaField value always maps to the same stripe. Restarting mongod closes all buckets and resets the catalog.[^c1-13][^c1-1]
- The manual lists six circumstances that close a bucket: time moving past the bucket span (forward or backward), the document limit (default 1000), the storage size limit (default 125 KiB, with a 12 MiB allowance for buckets under 10 documents, and the active bucket set not fitting the allowed storage engine cache size), the catalog exceeding its total memory allocation, a conflicting operation such as a chunk migration or update, and a mongod restart.[^c1-1][^c1-3]
- When catalog memory exceeds timeseriesIdleBucketExpiryMemoryUsageThreshold, expireIdleBuckets works through idle buckets. It archives an idle open bucket that can still take inserts and increments numBucketsArchivedDueToMemoryThreshold. It closes an idle bucket whose state conflicts with insertions and increments numBucketsClosedDueToMemoryThreshold; cleared or frozen buckets are only removed. If memory is still high, it drops archived records, also counted in numBucketsClosedDueToMemoryThreshold. Each call is bounded by timeseriesIdleBucketExpiryMaxCountPerAttempt (default 3). verified-as-of: 2026-10-20[^c1-8][^c1-13][^c1-11]
- Tentative: expireIdleBuckets has two call sites in bucket_catalog_internal.cpp: allocating a new bucket (allocateBucket) and loading a reopened bucket (loadBucketIntoCatalog). It has no background timer, so a node that stops allocating or reopening buckets does not shed catalog memory. verified-as-of: 2026-10-20[^c1-8]
- The cache-derived bucket size limit is cacheSizeBytes / (2 * activeBuckets), raised to at least timeseriesBucketMinSize (default 5120 bytes) and capped at timeseriesBucketMaxSize (default 128000 bytes, about 125 KiB). activeBuckets is the node-wide count of open plus archived buckets. If the next measurement would push a bucket past this limit, the bucket is hard-closed with rollover reason kCachePressure when the limit is below the normal maximum, and with kSize otherwise. verified-as-of: 2026-10-20[^c1-8][^c1-11][^c1-21][^c1-16]
- cacheSizeBytes in that formula is the configured WiredTiger cache size: getStorageCacheSizeBytes() multiplies getCacheSizeMB(), which returns the configured _wtConfig.cacheSizeMB. It is not live cache occupancy, eviction state or dirty ratio. 'Cache pressure' in kCachePressure and numBucketsClosedDueToCachePressure therefore names a computed budget, not an observed eviction condition. (two sources) verified-as-of: 2026-10-20[^c1-14][^c1-15][^c1-8]
- Each rollover reason maps to one action. kTimeForward soft-closes the bucket, which stays eligible for reopening. kTimeBackward archives the bucket and keeps a small in-memory record. kCount, kSchemaChange, kCachePressure and kSize hard-close the bucket permanently. Archiving increments numBucketsArchivedDueToTimeBackward; each other reason increments its own numBucketsClosedDueTo counter. verified-as-of: 2026-10-20[^c1-7][^c1-6][^c1-8]
- Tentative: determineRolloverReason checks in this order and returns the first match: time span forward, time backward, document count, size or cache pressure, schema incompatibility. Schema change therefore registers only when the earlier checks pass, and a comment in the function records an earlier bug where skipping the size check also skipped later checks and let mixed-schema data into a bucket. verified-as-of: 2026-10-20[^c1-8]
- A backward timestamp increments numBucketsArchivedDueToTimeBackward. The counter numBucketsClosedDueToTimeBackward is no longer emitted: SERVER-89158 (fixed in 8.0.0-rc7 and 8.1.0-rc0) removed it because it never rose above zero. The manual's serverStatus and collStats pages still list it. verified-as-of: 2026-10-20[^c1-24][^c1-9][^c1-2][^c1-4]
- Default limits on master: timeseriesBucketMaxCount 1000 measurements, timeseriesBucketMaxSize 128000 bytes, timeseriesBucketMinCount 10, timeseriesBucketMinSize 5120 bytes, timeseriesIdleBucketExpiryMaxCountPerAttempt 3, timeseriesSideBucketCatalogMemoryUsageThreshold 104857600 bytes. A bucket with fewer than 10 measurements may grow past the size limit, up to 12 MiB. numBucketsKeptOpenDueToLargeMeasurements counts those buckets. verified-as-of: 2026-10-20[^c1-11][^c1-1][^c1-2]
- Before SERVER-95511, timeseriesIdleBucketExpiryMemoryUsageThreshold defaulted to 0, which meant 2.5% of system memory, and positive values were bytes (7.0 branch). SERVER-95511 (fixed in 8.0.5 and 8.1.0-rc0; commit of 2024-10-31) changed the default to 5. Values 1 to 100 now mean a percentage of system memory, values above 100 mean bytes, and zero or negative values fall back to 5%. verified-as-of: 2026-10-20[^c1-12][^c1-11][^c1-17][^c1-20]
- serverStatus().bucketCatalog.numBuckets is the node-wide gauge of active buckets (open plus archived). The dynamic size limit uses the same gauge. numArchivedBuckets is numBuckets minus numOpenBuckets, clamped at zero. The bucketCatalog section returns an empty document while the catalog has no per-collection stats entries, that is, before any time series collection is used after startup. verified-as-of: 2026-10-20[^c1-10][^c1-16][^c1-2]
- Catalog memory is measured with mongod's tracking allocator and reported in bytes as serverStatus().bucketCatalog.memoryUsage. The idle-expiry threshold is a share of total system RAM, not of the WiredTiger cache.[^c1-2][^c1-13][^c1-11]
- The bucket catalog is one mongod-wide in-memory structure (a ServiceContext decoration) split into 32 hard-coded lock stripes. It tracks open and archived buckets. mongod's tracking allocator measures its memory, and serverStatus reports that figure as bucketCatalog.memoryUsage. A mongod restart discards the catalog and closes all buckets.[^c1-41][^c1-40][^c1-38][^c1-1]
- Each internal rollover reason maps to one of three actions. Count, schema change, cache pressure and size hard-close the bucket. A timestamp past the bucket's time span (time forward) soft-closes it, so it stays eligible for reopening. A timestamp earlier than the bucket's minimum time (time backward) archives it. If the bucket still holds uncommitted measurements, the server records the reason and acts when the last batch commits. verified-as-of: 2026-10-20[^c1-34][^c1-35][^c1-33][^c1-40]
- The manual lists seven closure triggers: time moving forward or backward past the bucket span; the document limit (default 1,000); the size limit (default 125 KiB, or up to 12 MiB when the bucket holds fewer than 10 measurements); active buckets not fitting the storage-engine cache; the catalog exceeding its total memory allocation; a conflicting operation such as a chunk migration or update; and a mongod restart. The defaults match timeseriesBucketMaxCount 1000, timeseriesBucketMaxSize 128000 bytes and timeseriesBucketMinCount 10 in the server source. verified-as-of: 2026-10-20[^c1-1][^c1-31][^c1-33]
- Two separate memory-driven paths close buckets early, and they use different counters. Catalog-memory expiry runs when bucketCatalog.memoryUsage exceeds timeseriesIdleBucketExpiryMemoryUsageThreshold: the server archives idle open buckets (numBucketsArchivedDueToMemoryThreshold) and, if usage stays over the limit, drops archived entries (numBucketsClosedDueToMemoryThreshold). The cache-derived size cap closes a growing bucket when the next measurement would exceed a limit computed from the WiredTiger cache size and the active-bucket count (numBucketsClosedDueToCachePressure). Do not read one family of counters as evidence about the other. verified-as-of: 2026-10-20[^c1-33][^c1-40][^c1-2][^c1-1]
- expireIdleBuckets works in this order. It archives each idle open bucket that can still accept inserts and counts it in numBucketsArchivedDueToMemoryThreshold. It removes a cleared or frozen idle bucket with no counter. It closes any other idle bucket and counts it in numBucketsClosedDueToMemoryThreshold. After the idle list is empty it closes archived entries and counts each in numBucketsClosedDueToMemoryThreshold. The server runs this only when it allocates a new bucket or loads a reopened bucket into the catalog, and it stops after timeseriesIdleBucketExpiryMaxCountPerAttempt expiries (default 3; the loop test is <=, so up to 4 per call). Code reading of the pinned master source. (two sources) verified-as-of: 2026-10-20[^c1-33][^c1-40][^c1-31]
- timeseriesIdleBucketExpiryMemoryUsageThreshold sets the catalog's memory budget and can be changed at startup or at runtime. From 8.0.5 and 8.1.0-rc0 (SERVER-95511) it defaults to 5. A value from 1 to 100 means a percentage of system memory. A value above 100 means bytes. Zero or a negative value resets to the 5% default. verified-as-of: 2026-10-20[^c1-31][^c1-32][^c1-43][^c1-20][^c1-17]
- Through 8.0.4 the same parameter took bytes only, and its default of 0 resolved to about 2.5% of system memory (the code multiplies system MB by 25 x 1024, which is 2.44%). SERVER-61195 (fixed 5.0.6 and 5.2.0) replaced an earlier fixed 100 MB limit with one that scales with RAM. SERVER-95510 recorded the default as 'a conservative 2.5%' in October 2024 and proposed 5%.[^c1-42][^c1-46][^c1-19]
- Since 6.2.0 (SERVER-69899) the server lowers the maximum bucket size so that all active buckets together use at most about half the WiredTiger cache. The limit is cacheBytes / (2 x activeBuckets), raised to at least timeseriesBucketMinSize (default 5,120 bytes) and capped at timeseriesBucketMaxSize (default 128,000 bytes). With no active buckets the static maximum applies. verified-as-of: 2026-10-20[^c1-21][^c1-33][^c1-31][^c1-23]
- The cache term is the configured WiredTiger cache size (storage engine getCacheSizeMB() x 1 MiB), not live cache occupancy. The bucket term is the process-wide count of open plus archived buckets across every time series collection (serverStatus bucketCatalog.numBuckets). numBucketsClosedDueToCachePressure therefore reflects a capacity ratio, not observed cache eviction, and a busy collection can shrink the cap of a quiet one. verified-as-of: 2026-10-20[^c1-39][^c1-33][^c1-23][^c1-37][^c1-40]
- When a measurement would push a bucket past its effective size limit, the server reports kSize if the effective limit equals timeseriesBucketMaxSize and kCachePressure if the cache-derived limit is lower. A bucket with fewer than timeseriesBucketMinCount (default 10) measurements may grow past that limit, up to the smaller of 12 MiB and the cache-derived limit, and is counted once in numBucketsKeptOpenDueToLargeMeasurements. Beyond that ceiling it closes as kSize or kCachePressure by the same rule. verified-as-of: 2026-10-20[^c1-33][^c1-31][^c1-2]
- Tentative: determineRolloverReason checks in this order: time forward, time backward, document count, size or cache pressure, then schema change. The first match wins, so a measurement that breaks both the size limit and the schema is counted as size or cache pressure, not schema change. Single-source code reading. verified-as-of: 2026-10-20[^c1-33]
- Since 6.1.0 (SERVER-66683) a bucket that could still accept measurements but would close because of memory pressure or out-of-order inserts is archived instead. The per-stripe archive keeps only a hash of the bucket key and the bucket _id. A memory-driven closure is not permanent: the README says an archived entry dropped for memory remains eligible for query-based reopening, which needs a {metaField: 1, timeField: 1} index (created by default for collections made on 6.3 or later). Without that index no query-based reopening happens and a new bucket opens.[^c1-47][^c1-40]
- timeseriesSideBucketCatalogMemoryUsageThreshold is a byte budget (default 104,857,600, startup or runtime) for a separate side bucket catalog. The IDL and Alibaba Cloud describe it as the level above which idle buckets in that catalog expire. SERVER-75176 (7.2.0-rc0) added a memory limit on the side catalog used by each time series update command and says an update over the limit should return an error; the ticket does not name the parameter. (two sources) verified-as-of: 2026-10-20[^c1-31][^c1-28][^c1-48]
- Catalog memory and the WiredTiger cache are separate budgets. A closed bucket exists only as an on-disk document; MongoDB's 2026-02-23 blog says closed buckets are not pinned and are evicted by normal WiredTiger cache eviction. The budgets interact only through the cache-derived bucket size cap.[^c1-30][^c1-40][^c1-33]
- Tentative: SERVER-94770 (fixed 8.0.5 and 8.1.0-rc0) reduced the memory footprint of archived buckets in the BucketCatalog. The ticket has no description, so the saving is unquantified. verified-as-of: 2026-10-20[^c1-49]

## Tools & Frameworks

- Closure counters appear node-wide in serverStatus().bucketCatalog and per collection under timeseries in collStats (db.collection.stats()). Both come from the function appendExecutionStatsToBuilder, which emits numBucketsClosedDueToCachePressure and numBucketsClosedDueToSchemaChange. The collStats reference lists neither counter. The SERVER-89233 reporter read numBucketsClosedDueToCachePressure from stats(). verified-as-of: 2026-10-20[^c1-9][^c1-10][^c1-16][^c1-4][^c1-18] _(Bucket catalog memory and closure reasons)_
- timeseriesIdleBucketExpiryMemoryUsageThreshold and timeseriesSideBucketCatalogMemoryUsageThreshold can be set at startup or at runtime; timeseriesBucketMaxCount is startup-only. Alibaba Cloud's MongoDB 8.0 parameter list agrees: no restart for the two thresholds, restart required for timeseriesBucketMaxCount (range 1 to 10000). The side catalog threshold takes bytes only (default 100 MB); Alibaba limits it to 52428800 through 209715200. verified-as-of: 2026-10-20[^c1-11][^c1-28] _(Bucket catalog memory and closure reasons)_
- timeseriesBucketMinSize (default 5120 bytes, settable at startup and at runtime) is the floor of the cache-derived limit. SERVER-82798 (fixed in 7.0.4 and 7.2.0-rc0) made the dynamic calculation respect it. SERVER-105187 (Backlog, created 2025-05-17) says that raising it up to timeseriesBucketMaxSize effectively turns dynamic bucketing off, and proposes making the factor of 2 configurable. (two sources) verified-as-of: 2026-10-20[^c1-11][^c1-22][^c1-23] _(Bucket catalog memory and closure reasons)_
- serverStatus().bucketCatalog (since 5.0) is process-wide. It reports numBuckets (open plus archived), numOpenBuckets, numIdleBuckets, numArchivedBuckets (numBuckets minus numOpenBuckets, floored at 0), memoryUsage in bytes, one counter per closure or archive reason, and a stateManagement block. Per-collection counters appear in $collStats storageStats output for time series collections. verified-as-of: 2026-10-20[^c1-2][^c1-37][^c1-36] _(Bucket catalog memory and closure reasons)_
- The manual's bucketCatalog table lists numBucketsClosedDueToTimeBackward, but current server code does not emit it: a backward timestamp archives the bucket and increments numBucketsArchivedDueToTimeBackward. The 7.0.0 source still had the Closed counter. verified-as-of: 2026-10-20[^c1-2][^c1-36][^c1-45][^c1-33] _(Bucket catalog memory and closure reasons)_

## Methodology

- With default limits, the dynamic limit starts to shrink buckets once active buckets exceed cacheSizeBytes / 256000, and it reaches the 5120-byte floor above cacheSizeBytes / 10240. For an 8 GiB WiredTiger cache those points are about 33,500 and about 839,000 active buckets. Compare serverStatus().bucketCatalog.numBuckets with these values. (two sources) verified-as-of: 2026-10-20[^c1-8][^c1-11] _(Bucket catalog memory and closure reasons)_
- To find what closes buckets, divide each closure counter by numBucketInserts. A large numBucketsClosedDueToCachePressure share points at the dynamic size limit. Rising numBucketsArchivedDueToMemoryThreshold or numBucketsClosedDueToMemoryThreshold, with memoryUsage near the threshold, points at catalog memory. numBucketsClosedDueToTimeForward points at granularity or bucketMaxSpanSeconds. numBucketsClosedDueToSchemaChange points at field type changes. (two sources) verified-as-of: 2026-10-20[^c1-2][^c1-8][^c1-27][^c1-25] _(Bucket catalog memory and closure reasons)_
- Work out the expiry threshold as a percentage of total system RAM: 5% from 8.0.5, 2.5% before. Compare it with serverStatus().bucketCatalog.memoryUsage. Expiry runs only on bucket allocation or reopen, so a quiet node can keep memoryUsage above the threshold. (two sources) verified-as-of: 2026-10-20[^c1-11][^c1-17][^c1-8] _(Bucket catalog memory and closure reasons)_
- Active-bucket cardinality is node-wide. SERVER-105187 says the dynamic calculation 'combines the global cardinality of buckets across all collections', and the SERVER-89233 patch still passes catalog.globalExecutionStats.numActiveBuckets to determineRolloverAction. Many collections, for example one collection per day, can therefore shrink the size limit for new buckets in all of them. A forum poster attributed small buckets to iterating daily collections (Feb 22, 2024). Since SERVER-89233, dropping a collection subtracts its buckets from the global gauge. (two sources) verified-as-of: 2026-10-20[^c1-23][^c1-16][^c1-27] _(Bucket catalog memory and closure reasons)_
- Derived from the formula and defaults (arithmetic, not stated by MongoDB): the cap drops below the 128,000-byte static maximum once active buckets exceed cacheBytes / 256,000, and reaches the 5,120-byte floor at cacheBytes / 10,240 active buckets. Setting timeseriesBucketMinSize at or above timeseriesBucketMaxSize keeps the cap at the static maximum; SERVER-105187 calls this effectively disabling dynamic bucketing. (two sources) verified-as-of: 2026-10-20[^c1-33][^c1-31][^c1-23] _(Bucket catalog memory and closure reasons)_
- Which closure reason dominates depends on write rate and span. In MongoDB's 2026 blog tests (M30, 10 devices) fast writers closed buckets on size or count, and slow writers closed them on time span. Read the counters accordingly: Size and Count are normal at high rates; TimeForward means the span is short relative to the write interval; SchemaChange means a field changed type; CachePressure and MemoryThreshold mean capacity limits. (two sources)[^c1-30][^c1-2][^c1-33] _(Bucket catalog memory and closure reasons)_
- Suggested diagnostic order for too many small buckets (synthesis of the sources): (1) per collection, compare timeseries.bucketCount with documents inserted and read avgNumMeasurementsPerCommit; (2) see which numBucketsClosedDueTo* counter dominates; (3) if CachePressure, compare process-wide numBuckets x 2 x 128,000 with the configured WiredTiger cache, and on 7.0 or 8.0.4 and earlier look for stale counts after collection drops; (4) if MemoryThreshold counters rise, compare memoryUsage with the threshold (5% of RAM on 8.0.5 and later, about 2.5% before) and raise it; (5) reduce metaField cardinality. (two sources) verified-as-of: 2026-10-20[^c1-26][^c1-18][^c1-2][^c1-33] _(Bucket catalog memory and closure reasons)_

## Practical Patterns

- Bucket count follows distinct metaField values. Fine-grained or changing metaField values create many sparsely packed, short-lived buckets, which raises catalog cardinality. Choose a stable, coarse metaField and a granularity (or bucketMaxSpanSeconds) that matches the measurement interval. The manual warns that granularity 'seconds' on data arriving every 5 minutes gives multiple buckets per polling interval, many holding a single document.[^c1-1][^c1-5] _(Bucket catalog memory and closure reasons)_
- Insert with insertMany, group measurements with the same metaField in the same batch, and set ordered to false (manual). The server design notes say insertMany batches are organized by meta value and sorted ascending by time; earlier versions targeted buckets per measurement in the order the client gave, which produced very sub-optimal bucketing for time-descending batches. verified-as-of: 2026-10-20[^c1-5][^c1-13] _(Bucket catalog memory and closure reasons)_
- A new bucket's start time rounds down to the granularity boundary (or bucketRoundingSeconds). Documents with slightly out-of-order timestamps that arrive close together therefore land in the same bucket instead of forcing a backward-time rollover.[^c1-1][^c1-8] _(Bucket catalog memory and closure reasons)_
- Archiving keeps a small in-memory record, so a later measurement that fits can reopen the on-disk bucket cheaply. If no record exists, the server queries the bucket collection for a reopening candidate. numBucketsReopened, numBucketsFetched, numBucketQueriesFailed and numBucketReopeningsFailed show how well reopening works. (two sources) verified-as-of: 2026-10-20[^c1-13][^c1-2] _(Bucket catalog memory and closure reasons)_
- Tentative: Query-based reopening needs the {metaField: 1, timeField: 1} index, which the server creates by default for time series collections created in 6.3 and later. Without that index the server does not use query-based reopening. verified-as-of: 2026-10-20[^c1-13] _(Bucket catalog memory and closure reasons)_
- Workaround for a collapsing cap: raise timeseriesBucketMinSize toward timeseriesBucketMaxSize (SERVER-105187, an unresolved Backlog ticket last updated 2025-07-14 that asks for a proper knob). The parameter is startup-only in 7.0.0 and startup-or-runtime from 7.3.0 and in 8.0.x. Cost: SERVER-69899 added the cap because uncapped buckets in high-cardinality workloads can exceed the WiredTiger cache and make each write hit disk. (two sources) verified-as-of: 2026-10-20[^c1-23][^c1-31][^c1-44][^c1-21] _(Bucket catalog memory and closure reasons)_
- To raise catalog memory, set timeseriesIdleBucketExpiryMemoryUsageThreshold at runtime. From 8.0.5 prefer a percentage so the budget follows RAM when Atlas autoscaling resizes the node. SERVER-95510 cites support cases since 5.0 that needed higher limits. SERVER-95511 warns that fixed byte values risk out-of-memory errors after a scale-down. (two sources) verified-as-of: 2026-10-20[^c1-19][^c1-20][^c1-31] _(Bucket catalog memory and closure reasons)_

## Anti-Patterns

- Raising timeseriesBucketMinSize to timeseriesBucketMaxSize switches off dynamic sizing but trades smaller buckets for WiredTiger cache risk. SERVER-69899 (fixed in 6.2.0-rc0) added the limit because many active buckets at the full 125 KiB could exceed the cache and make each document write trigger a disk write. Compare active buckets times bucket size with the cache before disabling it. (two sources) verified-as-of: 2026-10-20[^c1-21][^c1-23] _(Bucket catalog memory and closure reasons)_
- Storing different BSON types in the same field path makes consecutive measurements schema-incompatible. The server hard-closes the bucket and increments numBucketsClosedDueToSchemaChange. Keep each field path to one type. (two sources) verified-as-of: 2026-10-20[^c1-2][^c1-8] _(Bucket catalog memory and closure reasons)_
- MongoDB engineers call the old 2.5% catalog memory default conservative and note that users often need to change the memory parameters. SERVER-95510 (2024-10-03, closed as a duplicate of SERVER-95511) says raising the limit in many deployments since 5.0 improved time series performance. Leaving the default unexamined on a high-cardinality node risks needless archiving and closing. (two sources) verified-as-of: 2026-10-20[^c1-19][^c1-20] _(Bucket catalog memory and closure reasons)_
- A high-cardinality metaField creates one bucket per distinct value per time window, so it produces many sparse short-lived buckets. Each one adds to the active-bucket count that divides the WiredTiger cache in the dynamic size cap and to catalog memory. SERVER-69899 was written for exactly this high-cardinality case. Keep metaField values few and stable. (two sources)[^c1-1][^c1-21][^c1-52] _(Bucket catalog memory and closure reasons)_
- Restarting mongod is a mitigation, not a fix. It closes all buckets and resets the catalog (and any stale cardinality count), but users report relief lasting about three days (forum 2024-02-22) or restarting servers daily (feedback 2024-02-22). SERVER-89233 is fixed from 8.0.5. (two sources)[^c1-1][^c1-26][^c1-51][^c1-18] _(Bucket catalog memory and closure reasons)_

## Troubleshooting

- Symptom: nearly one bucket per document, avgNumMeasurementsPerCommit near 1, and a very large numBucketsClosedDueToCachePressure, usually days after startup. SERVER-89233 (sharded cluster, 7.0.4 and 7.0.5, created 2024-04-10) describes it. A forum poster saw bucketCount 25,000 and 17 measurements per commit when loading a collection on a fresh server, but about 420,000 buckets, 1 measurement per commit and about 415,000 cache-pressure closures when loading it after other collections (Oct 19, 2023). Replies through Mar 2025 report the same. verified-as-of: 2026-10-20[^c1-18][^c1-26][^c1-27] _(Bucket catalog memory and closure reasons)_
- Tentative: In a 7.0.2 replica set (Feb 2024), about 120.4 million documents produced 12,151,933 buckets (about 9.9 documents per bucket, avgBucketSize 4849) on a 128 GB host and 1,508,453 buckets (about 79.9 per bucket, avgBucketSize 13428) on a 16 GB host. The 16 GB host reported numBucketsClosedDueToCachePressure 1,050,343; the 128 GB host's closure counters were all zero. The larger host got the smaller buckets, so cache size alone does not predict bucket density. verified-as-of: 2026-10-20[^c1-27] _(Bucket catalog memory and closure reasons)_
- SERVER-89233 is Fixed in 8.0.5 and 8.1.0-rc0 (resolved 2024-10-03). The ticket requested backports to 8.0 and 7.0, but it lists no 7.0.x fix version as of 2026-10-20. Commit 46e8db22 ('Track cardinality per-collection for time-series') replaced the catalog-wide uint32 counter numberOfActiveBuckets with per-collection numActiveBuckets gauges and subtracts a dropped collection's gauge from the global one. Neither the ticket nor the commit states a root cause. The reporter also hit the problem after dropping and re-inserting collections. (two sources) verified-as-of: 2026-10-20[^c1-18][^c1-16] _(Bucket catalog memory and closure reasons)_
- A mongod restart is a temporary workaround: it closes all buckets and resets the catalog, and one forum user reported relief for about three days after each restart (Feb 22, 2024). (two sources)[^c1-1][^c1-26] _(Bucket catalog memory and closure reasons)_
- Forum users could not find a server parameter for bucket catalog memory (Mar 3, 2025). The parameter is timeseriesIdleBucketExpiryMemoryUsageThreshold. SERVER-95510 calls it undocumented (2024-10-03), and the current manual's bucketing page does not name it. (two sources) verified-as-of: 2026-10-20[^c1-26][^c1-19][^c1-1] _(Bucket catalog memory and closure reasons)_
- Dropping a collection, moving a chunk, an election, or a direct write such as an update or delete clears tracked buckets and can close them. stateManagement.trackedClearOperations counts clears whose bucket removal was deferred, and stateManagement.currentEra increments when a bucket is cleared. (two sources)[^c1-2][^c1-1] _(Bucket catalog memory and closure reasons)_
- Tentative: In MongoDB's internal medium- and high-cardinality workloads, buckets close because time moves forward, so raising the count or size limits would not help them (SERVER-88644, Backlog, created 2024-03-27). verified-as-of: 2026-10-20[^c1-25] _(Bucket catalog memory and closure reasons)_
- The manual's bucketing page (fetched 2026-10-19; its navigation labels the manual 9.0 Current) still says the catalog's default allocation is 2.5% of available system memory. That is right for 7.0 through 8.0.4 but not for 8.0.5 and later, where the source default is 5%. Alibaba Cloud's 8.0 parameter table also lists 5%. verified-as-of: 2026-10-20[^c1-1][^c1-43][^c1-31][^c1-28] _(Bucket catalog memory and closure reasons)_
- Reported failure mode: buckets shrink to about one measurement each. ## Disagreements & Open Questions

- Disagreement (Bucket catalog memory and closure reasons): Default catalog memory allocation. The manual (current, v8.0 and v7.0 pages) says 2.5% of available system memory. Source on master and the v8.0 branch sets the default to 5, meaning 5% of system memory, since SERVER-95511 (8.0.5, 8.1.0-rc0), and Alibaba Cloud's 8.0 parameter list also says 5%. The 2.5% figure holds for 7.0 and 8.0.0 through 8.0.4 only.[^c1-1][^c1-3][^c1-11][^c1-17][^c1-28]
- Disagreement (Bucket catalog memory and closure reasons): Where the catalog lives. The manual calls the bucket catalog 'a specialized in-memory cache in WiredTiger'. The server design notes say catalog memory is tracked with mongod's tracking allocator, and the expiry threshold is a share of system RAM. Only the dynamic size limit takes the WiredTiger cache size as an input.[^c1-1][^c1-13][^c1-11]
- Disagreement (Bucket catalog memory and closure reasons): Backward timestamps. The manual says time moving backward closes a bucket and documents numBucketsClosedDueToTimeBackward in serverStatus and collStats. Source archives the bucket (kTimeBackward maps to kArchive), counts numBucketsArchivedDueToTimeBackward, and SERVER-89158 removed the closed counter.[^c1-2][^c1-4][^c1-24][^c1-7]
- Disagreement (Bucket catalog memory and closure reasons): Counters the collStats reference omits. The collStats page lists seven bucket counters under timeseries. The server also emits numBucketsClosedDueToCachePressure, numBucketsClosedDueToSchemaChange, numBucketsArchivedDueToMemoryThreshold and numActiveBuckets from the same function.[^c1-4][^c1-9]
- Disagreement (Bucket catalog memory and closure reasons): Same phrase, two mechanisms. serverStatus describes numBucketsClosedDueToMemoryThreshold as the active set not fitting 'the allowed bucket catalog cache size', while the bucketing page uses 'allowed storage engine cache size' for the size-limit case. In source these are separate: catalog memory against timeseriesIdleBucketExpiryMemoryUsageThreshold, and a size limit derived from the WiredTiger cache size and bucket count.[^c1-2][^c1-1][^c1-8]
- Disagreement (Bucket catalog memory and closure reasons): Why one-document buckets happen. The Oct 2023 forum poster reasoned that the dynamic limit 'becomes comparable to the size of one record'. Source floors the limit at timeseriesBucketMinSize (5120 bytes), which SERVER-82798 made effective in 7.0.4, yet SERVER-89233 still reports one bucket per document on 7.0.4 and 7.0.5. The formula alone does not explain the reports, and no MongoDB staff root-cause text was found.[^c1-26][^c1-22][^c1-18][^c1-8]
- Disagreement (Bucket catalog memory and closure reasons): The manual says the catalog's default memory allocation is 2.5% of system memory; server source from 8.0.5 and Alibaba Cloud's 8.0 table say 5%.[^c1-1][^c1-43][^c1-28]
- Disagreement (Bucket catalog memory and closure reasons): The manual's bucketCatalog table lists numBucketsClosedDueToTimeBackward; server code emits only numBucketsArchivedDueToTimeBackward.[^c1-2][^c1-36]
- Disagreement (Bucket catalog memory and closure reasons): A user reports no server parameter exists to change catalog memory; the server defines timeseriesIdleBucketExpiryMemoryUsageThreshold, settable at runtime (checked in 7.0.0 and master).[^c1-26][^c1-51][^c1-44][^c1-31]
- Disagreement (Bucket catalog memory and closure reasons): The manual ties the cache-pressure limit to 'available storage engine cache size'; the code uses the configured cache size, not free or available cache.[^c1-2][^c1-39]
- Disagreement (Bucket catalog memory and closure reasons): The IDL and Alibaba Cloud say idle buckets expire when the side-catalog threshold is exceeded; SERVER-75176 says an over-limit update returns an error.[^c1-31][^c1-28][^c1-48]
- Disagreement (Bucket catalog memory and closure reasons): The manual calls the bucket catalog 'a specialized in-memory cache in WiredTiger'; the source shows a mongod-level object (ServiceContext decoration) with its own tracked memory budget.[^c1-1][^c1-41][^c1-40]
- Open (Bucket catalog memory and closure reasons): Whether SERVER-89233 was ever backported to 7.0.x: the ticket requested v8.0 and v7.0 backports but lists only 8.0.5 and 8.1.0-rc0 as fix versions.
- Open (Bucket catalog memory and closure reasons): The exact mechanism that turns inflated cardinality into one measurement per bucket, given the 5120-byte floor: no staff root-cause text exists in SERVER-89233, the commit, or the forum threads.
- Open (Bucket catalog memory and closure reasons): Why the 128 GB host in forum thread 265066 shows all-zero closure counters yet the smallest buckets (possible replica secondary or restart; not stated).
- Open (Bucket catalog memory and closure reasons): What the side bucket catalog (timeseriesSideBucketCatalogMemoryUsageThreshold, 100 MB) serves. It is a second BucketCatalog instance passed into timeseries_write_util.cpp write paths; its role was not traced.
- Open (Bucket catalog memory and closure reasons): Whether timeseriesBucketMinSize is a supported customer tuning knob: it is absent from the manual pages read and from Alibaba's 8.0 list, and only SERVER-105187 names it as a lever.
- Open (Bucket catalog memory and closure reasons): Whether Atlas overrides timeseriesIdleBucketExpiryMemoryUsageThreshold or the manual's 2.5% is simply stale for 8.0.5 and later.
- Open (Bucket catalog memory and closure reasons): Independent third-party coverage is thin. Besides end-user posts hosted on MongoDB's forum and Alibaba Cloud's parameter list, no Percona, Datadog, Dynatrace or exporter documentation covering bucketCatalog metrics was found, and the DBA StackExchange question linked from SERVER-89233 could not be fetched.
- Open (Bucket catalog memory and closure reasons): Do the 8.0.5 release notes document the default change from about 2.5% to 5%? The 8.0.5-rc1 announcement snippet seen in search did not list SERVER-95511.
- Open (Bucket catalog memory and closure reasons): Is there a docs ticket to correct the manual's 2.5% sentence and the numBucketsClosedDueToTimeBackward row?
