# WiredTiger cache eviction and dirty ratio

## Overview

WiredTiger evicts pages to keep MongoDB's internal cache below its configured size. Background eviction workers start at eviction_target (80% of cache) and application threads join at eviction_trigger (95%). A parallel dirty-only pair uses 5% (target) and 20% (trigger) of cache size, and reaching the dirty trigger throttles application threads. Dirty data is what each 60-second checkpoint must flush, so the dirty ratio (tracked dirty bytes divided by maximum bytes configured) bounds checkpoint work. Since MongoDB 4.4 a separate updates trigger, half the dirty trigger by default, can bind while the dirty ratio is low. MongoDB engineering tickets from 2025 to 2026 track that problem and have not settled a new default. MongoDB's manual says to avoid changing eviction settings without MongoDB engineers. Third-party alert levels of 10% to 15% dirty are uncited vendor heuristics.

## Core Concepts

### WiredTiger cache eviction and dirty ratio

- WiredTiger starts evicting pages as the cache approaches its configured size and approximates least-recently-used order. An eviction server finds candidate pages and eviction worker threads evict them in the background. If workers cannot keep up with incoming data, application threads must do eviction work before they can read or write more data, which can cause latency spikes.[^c1-1][^c1-2][^c1-3]
- eviction_target (default 80% of cache size) is the level WiredTiger tries to hold overall cache usage; eviction worker threads are active once the cache holds at least that much. eviction_trigger (default 95%) is where application threads start evicting, which throttles operations and raises latency. Operations stall when the cache reaches 100% of its size. Each target must be lower than its trigger.[^c1-2][^c1-3][^c1-4]
- eviction_dirty_target (default 5%) and eviction_dirty_trigger (default 20%) work like the overall pair but count only dirty data, meaning pages modified since they were read from disk. Application threads are throttled when dirty data reaches eviction_dirty_trigger. WiredTiger 12.0.0 documents that the dirty trigger only changes behavior when it is lower than eviction_trigger. MongoDB's manual states the dirty cache is limited to 20% of the total cache size.[^c1-2][^c1-3][^c1-4][^c1-6][^c1-13]
- Dirty ratio is dirty bytes divided by the configured maximum cache bytes, not by bytes currently in the cache. mongod's cache-pressure monitor computes cacheBytesDirty / cacheBytesMax and compares it with the dirty trigger, falling back to 0.20 when no explicit trigger is set. Netdata gives the same formula over serverStatus fields wiredTiger.cache['tracked dirty bytes in the cache'] and ['maximum bytes configured']. WiredTiger documents the thresholds as percentages of cache size. verified-as-of: 2026-10-20[^c1-10][^c1-14][^c1-4]
- The dirty settings bound how much work each checkpoint must do in the worst case, and they limit likely memory fragmentation from mixing small update allocations with large cache-miss allocations. MongoDB writes a checkpoint every 60 seconds, and a sharp checkpoint must flush all dirty pages, so the dirty volume at checkpoint time sets how long the flush takes.[^c1-2][^c1-3][^c1-5][^c1-13]
- Since MongoDB 4.4 (WiredTiger 3.2.2), WiredTiger also limits bytes of updates in cache (small insert and update structures) with eviction_updates_target and eviction_updates_trigger. The trigger defaults to half of eviction_dirty_trigger (10% of cache with default dirty settings). The target defaults to half of eviction_dirty_target (2.5%), except that it equals eviction_dirty_target when precise checkpoints are enabled. A workload with many small objects can be governed by these limits, so cache dirty percent tends toward 2.5% instead of 5%. (two sources) verified-as-of: 2026-10-20[^c1-23][^c1-4][^c1-10]
- The updates trigger can bind while the dirty ratio is low. WT-15538, MongoDB's open umbrella ticket (updated 2026-10-09), covers 7.x and 8.x incidents on caches of 72 GB or more with 2,000+ updates per second: the cache stays at or above eviction_updates_trigger, server threads are pulled into eviction, and the update ratio exceeds the dirty ratio, sometimes by a lot, because the update content sits on clean pages. In the WT-17697 FTDC sample, tracked dirty bytes averaged 372 MB (peak 1.74 GB), well under the 20% dirty trigger, while application threads did heavy read-back and eviction writes. MongoDB states it does not yet understand the root cause. (two sources) verified-as-of: 2026-10-09[^c1-20][^c1-19]
- MongoDB engineering has not settled a new updates-trigger default. WT-17698 (open, updated 2026-10-19) tested 95% on sys-perf and found one causal effect, a +13.0% p95 regression on insert-bound bulk_insert_w1 (z = 2.18), and concluded 95% should not ship as a global default on that evidence. WT-15843 proposed a 20% default instead of 10% and was closed as a duplicate of WT-17698 on 2026-10-01. The WiredTiger 12.0.0 reference still gives the default as half of eviction_dirty_trigger. (two sources) verified-as-of: 2026-10-19[^c1-21][^c1-22][^c1-4]
- Because the dirty trigger is a percentage, permitted dirty volume grows with cache size. WT-11173 (open, no fix version, last updated 2024-03-07) notes 20% of a 512 GB cache is about 102 GB, says that much dirty data has little benefit for most workloads and makes checkpoints costly, and proposes an absolute cap (for example, stop applying the 20% rule at 10 GB). In 2015 Mark Callaghan asked for eviction_dirty_trigger (SERVER-16737) because on a 144 GB RAM server he did not want about 140 GB of dirty pages in the WiredTiger cache. Percona notes 1% of a 256 GB cache is still about 2.56 GB flushed at each checkpoint. verified-as-of: 2026-10-20[^c1-18][^c1-17][^c1-13]
- MongoDB's default WiredTiger cache is the larger of 50% of (RAM minus 1 GB) or 0.256 GB. The cache belongs to the whole mongod instance, cannot pin documents, and is not split between reads and writes, so dirty pages compete with clean working-set pages for the same budget. Collection data in the cache is uncompressed and has a different representation from the on-disk format.[^c1-5][^c1-8]
- In MongoDB's master branch, WiredTigerCachePressureMonitor reports cache pressure only when both checks pass: application cache-wait time exceeds cachePressureEvictionStallThresholdProportion (default 0.95) of expected thread time while no transactions commit, held longer than cachePressureEvictionStallDetectionWindowSeconds (default 20); and either dirty bytes over cache maximum exceeds the dirty trigger (default 0.20) or updates bytes over cache maximum exceeds the updates trigger (default half the dirty trigger). The WT-17697 ticket describes the monitor as reading the bytes-of-updates statistic. (two sources) verified-as-of: 2026-10-20[^c1-10][^c1-12][^c1-19]
- The dirty and updates limits arrived in stages: MongoDB gained eviction_dirty_trigger support after Mark Callaghan's January 2015 request (SERVER-16737, fix version 3.1.5, resolved 2015-06-26); WiredTiger staff proposed auto-scaling the dirty trigger to bound checkpoint time in 2016 (WT-2735, closed as a duplicate of WT-2666); and MongoDB 4.4 added the separate updates target and trigger (WT-6175). (two sources)[^c1-17][^c1-24][^c1-23]
- WiredTiger's documented defaults are eviction_target 80%, eviction_trigger 95%, eviction_dirty_target 5% and eviction_dirty_trigger 20%, all measured against cache_size. Eviction worker threads start at each target. At each trigger, WiredTiger recruits application threads to evict.[^c1-2][^c1-4][^c1-13]
- Eviction values inside the percentage range (1 to 100 for the dirty settings, 10 to 100 for eviction_target and eviction_trigger) are percentages of cache_size. Larger values are absolute sizes. Each target must be lower than its trigger, and no value may exceed cache_size. The dirty and updates triggers change behavior only when they are lower than eviction_trigger.[^c1-4][^c1-50][^c1-1]
- When eviction workers fall behind, WiredTiger makes application threads do eviction work before they continue. WiredTiger's tuning guide says this can cause latency spikes, and that operations stall when the cache reaches 100% of cache_size. The mongod source README calls this recruitment.[^c1-2][^c1-1][^c1-13][^c1-42]
- The mongostat dirty column is wiredTiger.cache 'tracked dirty bytes in the cache' divided by 'maximum bytes configured'. The used column is 'bytes currently in the cache' divided by 'maximum bytes configured'. Ops Manager defines CACHE_FILL_RATIO the same way and DIRTY_FILL_RATIO as dirty bytes relative to the total WiredTiger cache.[^c1-28][^c1-29][^c1-36]
- WiredTiger judges eviction_dirty_trigger against dirty leaf-page bytes only, not all dirty bytes. The usual dirty ratio uses total tracked dirty bytes, which also count dirty internal pages, so it can read above the quantity WiredTiger compares with the trigger. WT-13642 calls the total ratio incorrect for deciding whether application threads are evicting. The WiredTiger vendored in MongoDB 7.0.45, 8.0.34 and 9.0.4 computes the dirty trigger from dirty leaf bytes. verified-as-of: 2026-10-20[^c1-37][^c1-49][^c1-48][^c1-47]
- WT-13642 added WiredTiger statistics 'tracked dirty leaf page bytes in the cache' and 'tracked dirty internal page bytes in the cache'. The ticket lists fix versions WiredTiger 11.3.0 and MongoDB 7.0.18, 8.0.5 and 8.1.0-rc0. It proposes dirty leaf bytes divided by maximum bytes configured as the diagnostic ratio. (two sources) verified-as-of: 2026-10-20[^c1-37][^c1-51]
- MongoDB writes a WiredTiger checkpoint every 60 seconds, and a checkpoint flushes all dirty pages. Dirty volume at checkpoint time therefore sets checkpoint duration and the burst of disk writes. In Percona's bulk load, checkpoint time grew from seconds to minutes and throughput collapsed during checkpoints.[^c1-5][^c1-13][^c1-18]
- eviction_checkpoint_target (default 1, a percentage of cache_size) makes WiredTiger evict at the start of a checkpoint until dirty content falls to that level. A value of zero disables it. (two sources)[^c1-4][^c1-50]
- The default WiredTiger cache is the larger of 50% of (RAM minus 1 GB) or 0.256 GB. WiredTiger reserves no separate part of the cache for reads and writes, so clean and dirty pages share one budget. Every threshold above is a fraction of this configured cache, not of RAM.[^c1-5][^c1-13][^c1-35]
- mongod starts with 4 minimum and 4 maximum eviction threads. Percona reported the same default in 2020. The 9.0.4 source still defaults both to 4, with a valid range of 1 to 64 and runtime changes allowed. WiredTiger's own defaults are 1 minimum and 8 maximum, and it scales the worker count between them. verified-as-of: 2026-10-20[^c1-44][^c1-13][^c1-4][^c1-1]
- MongoDB 8.2 and later define startup parameters wiredTigerEvictionDirtyTargetGB, wiredTigerEvictionDirtyMaxGB (the dirty trigger) and wiredTigerEvictionUpdatesMaxGB. They set absolute sizes in GB (minimum 0.01). The default 0 keeps WiredTiger's 5%, 20% and half-of-dirty-trigger limits. No such parameter appears in wiredtiger_global_options.idl at tag r8.0.34. Percona asked for an absolute dirty target in 2020, and WT-11173 proposes an absolute cap on the default. (two sources) verified-as-of: 2026-10-20[^c1-44][^c1-45][^c1-18][^c1-13]
- eviction_updates_target and eviction_updates_trigger default to 0, which WiredTiger resolves to half of eviction_dirty_target and half of eviction_dirty_trigger. With precise checkpoints enabled, the updates target equals the dirty target. These limits count bytes of updates in cache, not dirty bytes. The mongod parameter wiredTigerEvictionUpdatesMaxGB describes the same half-of-dirty-trigger default.[^c1-4][^c1-50][^c1-44]
- Tentative: WT-17697 (status Backlog, unresolved, last updated 2026-06-04) concludes that removing the updates target and trigger is net-negative, and that 'updates eviction is load-bearing for update-heavy workloads'. The ticket says the cache can fill with update-laden leaf pages that clean eviction skips and dirty eviction does not reclaim. It says bytes_updates accounting tracks that memory separately from dirty bytes. Its benchmark run showed 47 regressions against 17 improvements. verified-as-of: 2026-06-04[^c1-19]
- The WiredTiger 12.0.0 reference documents four eviction sub-options that change how application threads are recruited or how eviction runs, all off by default: app_eviction_min_cache_fill_ratio (0 to 50), cache_tolerance_for_app_eviction (0 to 100), incremental_app_eviction and prefer_scrub_eviction. Whether mongod accepts or sets them was not verified. (two sources) verified-as-of: 2026-10-20[^c1-4][^c1-50]
- MongoDB 8.2 and later include a cache-pressure monitor. It flags pressure only when three conditions hold: dirty bytes exceed the dirty trigger (default 20% of maximum bytes) or update bytes exceed the updates trigger (default half of that); application-thread cache wait time exceeds 95% of expected thread time; and no transaction commits for a sustained 20 seconds. A periodic thread then aborts the oldest transactions until the pressure clears. (two sources) verified-as-of: 2026-10-20[^c1-43][^c1-42][^c1-46][^c1-39]
- The cache-pressure monitor and its rollback thread are present in the r9.0.4 source. SERVER-100367 and SERVER-102446 list fix version 8.2.0-rc0, and raw file requests for the monitor at tags r7.0.45, r8.0.34 and r8.1.3 returned 404. The manual documents cachePressureQueryPeriodMilliseconds (default 1000 ms) as new in 8.3 and says MongoDB aborts the oldest transaction when the storage engine is under cache pressure. (two sources) verified-as-of: 2026-10-20[^c1-39][^c1-40][^c1-6][^c1-43]
- Tentative: In the monitor source, the dirty check divides WT_STAT_CONN_CACHE_BYTES_DIRTY, the total 'tracked dirty bytes in the cache' statistic, by maximum bytes configured. It does not use dirty leaf bytes, so it can trip at a slightly different level than WiredTiger's own dirty trigger. This is a reading of the code, not a documented statement.[^c1-43][^c1-51]
- MongoDB writes to a separate 'spill' WiredTiger instance for some disk-spilling operations, and that instance has its own cache. Its eviction defaults differ from the main cache: dirty target 5%, dirty trigger 80%, updates trigger 80%. (two sources) verified-as-of: 2026-10-20[^c1-7][^c1-44]
- Older WiredTiger references list different dirty defaults. The 2.8.0 reference gives eviction_dirty_target 80 and eviction_dirty_trigger 95 (range 5 to 99). The 12.0.0 reference gives 5 and 20 (range 1 to 10TB). Check the version of any reference before quoting dirty defaults. (two sources)[^c1-27][^c1-4]

## Tools & Frameworks

- WiredTiger 12.0.0 reads eviction target and trigger values up to 100 as percentages of cache size and values above 100 as absolute sizes, up to 10TB. MongoDB's master branch has startup-only parameters wiredTigerEvictionDirtyTargetGB, wiredTigerEvictionDirtyMaxGB (the dirty trigger) and wiredTigerEvictionUpdatesMaxGB, which take absolute GB values; mongod converts them to megabytes and passes them to WiredTiger as eviction_dirty_target, eviction_dirty_trigger and eviction_updates_trigger. Their defaults are 5% of cache, 20% of cache and half the dirty trigger. (two sources) verified-as-of: 2026-10-20[^c1-4][^c1-9][^c1-11] _(WiredTiger cache eviction and dirty ratio)_
- In MongoDB's master branch the parameters wiredTigerEvictionThreadsMin and wiredTigerEvictionThreadsMax both default to 4, accept 1 to 64, and can be set at startup or at runtime; mongod passes them to WiredTiger as eviction=(threads_min=...,threads_max=...). Percona (2020) likewise reports that MongoDB allocates four eviction threads by default, and said WiredTiger then capped them at 20. (two sources) verified-as-of: 2026-10-20[^c1-9][^c1-11][^c1-13] _(WiredTiger cache eviction and dirty ratio)_
- The serverStatus fields for a dirty-ratio check are wiredTiger.cache['tracked dirty bytes in the cache'] and ['maximum bytes configured'], with ['bytes currently in the cache'] for fill and ['pages evicted by application threads'] for application-thread eviction. MongoDB's manual describes tracked dirty bytes as the size of dirty data in the cache, which should be below bytes currently in the cache, and warns that WiredTiger statistics may change between releases. verified-as-of: 2026-10-14[^c1-7][^c1-14][^c1-15] _(WiredTiger cache eviction and dirty ratio)_
- Tentative: The WiredTiger 12.0.0 reference lists further eviction controls: eviction=(app_eviction_min_cache_fill_ratio) (0 to 50, default 0) delays application-thread eviction until a minimum cache fill; eviction=(cache_tolerance_for_app_eviction) (0 to 100, default 0, in steps of 10) loosens the dirty and updates triggers; eviction=(incremental_app_eviction) (default false) lets only some application threads evict; and eviction_checkpoint_target (default 1) evicts dirty content at the start of each checkpoint down to that level. verified-as-of: 2026-10-20[^c1-4] _(WiredTiger cache eviction and dirty ratio)_
- MongoDB's manual says recent versions run a separate 'spill' WiredTiger instance with its own cache for operations that write to disk, isolated from the main cache, with metrics under serverStatus spillWiredTiger. The master-branch IDL gives that instance its own settings: cache 2.5% of system memory bounded to 100 to 1000 MB, one eviction thread, dirty target 5%, dirty trigger 80% and updates trigger 80%. The main cache's dirty ratio therefore excludes spill data. (two sources) verified-as-of: 2026-10-14[^c1-7][^c1-9] _(WiredTiger cache eviction and dirty ratio)_
- Tentative: The manual's spillWiredTiger.cache listing, described as a subset of the wiredTiger fields, names these eviction counters: 'number of times dirty trigger was reached', 'number of times eviction trigger was reached', 'number of times updates trigger was reached', 'application threads eviction requested with cache fill ratio < 25%' and '>= 75%', 'eviction state', 'eviction empty score' and 'eviction currently operating in aggressive mode'. The manual's sample for the main wiredTiger.cache still shows older fields such as 'cache overflow score', so check a live serverStatus for the exact names. verified-as-of: 2026-10-14[^c1-7] _(WiredTiger cache eviction and dirty ratio)_
- In the serverStatus manual sample, wiredTiger.cache lists 'maximum bytes configured', 'tracked dirty bytes in the cache', 'tracked dirty pages in the cache', 'pages evicted by application threads', 'modified pages evicted by application threads' and 'operations timed out waiting for space in cache'. 'application thread time evicting (usecs)' and 'application thread time waiting for cache (usecs)' sit under wiredTiger.thread-yield. The manual warns that the available statistics can change between releases. (two sources) verified-as-of: 2026-10-14[^c1-7][^c1-15] _(WiredTiger cache eviction and dirty ratio)_
- WiredTiger defines counters for trigger crossings: 'number of times dirty trigger was reached', 'number of times eviction trigger was reached' and 'number of times updates trigger was reached'. The serverStatus manual shows them in the spillWiredTiger.cache sample but not in its wiredTiger.cache sample, so check a live server before relying on them. ## Methodology

- Watch checkpoint duration beside the dirty ratio. serverStatus wiredTiger.transaction['transaction checkpoint most recent time (msecs)'] is the time to create the latest checkpoint, and MongoDB's manual says a rise under steady write load may indicate I/O subsystem saturation. Netdata alerts on checkpoint time above 30 seconds sustained; Percona's bulk-load goal was checkpoints under about 10 seconds. (two sources) verified-as-of: 2026-10-14[^c1-7][^c1-14][^c1-13] _(WiredTiger cache eviction and dirty ratio)_
- Netdata's undated guides, which cite no source, give these alert levels: dirty ratio above 10% as early warning, above 15% as concerning, a sustained climb toward 20% as critical, and any sustained nonzero rate of pages evicted by application threads as abnormal. OneUptime's cache-eviction article gives no numeric health threshold. Treat the Netdata levels as vendor heuristics for lead time before the 20% trigger. (two sources) verified-as-of: 2026-10-20[^c1-14][^c1-15][^c1-16] _(WiredTiger cache eviction and dirty ratio)_
- WiredTiger statistics are cumulative counters, so rates need two samples. Netdata treats any sustained nonzero rate of 'pages evicted by application threads' as abnormal and suggests sampling twice about 10 seconds apart. The mongod monitor differences 'application thread time waiting for cache' between polls in the same way. (two sources)[^c1-15][^c1-43] _(WiredTiger cache eviction and dirty ratio)_
- To see whether dirty data is driving application-thread eviction, compare dirty leaf bytes with eviction_dirty_trigger and update bytes with the updates trigger, then confirm with the delta of 'pages evicted by application threads'. Total dirty bytes over maximum bytes configured is an upper bound for the dirty check. (two sources)[^c1-37][^c1-47][^c1-15] _(WiredTiger cache eviction and dirty ratio)_
- Read the dirty percentage next to checkpoint behavior. mongostat 'flushes' counts WiredTiger checkpoints triggered between polls, and serverStatus wiredTiger.transaction 'transaction checkpoint most recent time (msecs)' gives the last checkpoint duration. Netdata flags checkpoints near 30 seconds, and above 60 seconds when they cannot keep up with the interval. (two sources)[^c1-28][^c1-15][^c1-14] _(WiredTiger cache eviction and dirty ratio)_

## Practical Patterns

- Lowering eviction_dirty_target and eviction_dirty_trigger makes background eviction start earlier and caps the dirty data each checkpoint must flush, at the price of more eviction I/O and CPU (block compression) and earlier throttling of application threads. In 2016 WT-2735 stated that WiredTiger checkpoints work best when there is not too much dirty data in cache and proposed setting eviction_dirty_trigger automatically to bound checkpoint time; it was closed as a duplicate of WT-2666. (two sources)[^c1-2][^c1-13][^c1-24] _(WiredTiger cache eviction and dirty ratio)_
- Tentative: Percona's 2020 bulk-load recipe lowered eviction_dirty_trigger from 20 to 5 and eviction_dirty_target from 5 to 1, raised eviction threads from 4 to 20, and used a 1 GB cache to hold dirty pages to about 10 to 50 MB, aiming for checkpoints under about 10 seconds. The author estimated the default-settings load at about 21 days (it was not finished) versus about one week tuned. The runtime change blocks client threads for seconds to minutes, so the author advises a maintenance window. A commenter about five years later said the change only helps if eviction workers keep up and 'didn't help much' for their load.[^c1-13] _(WiredTiger cache eviction and dirty ratio)_
- Tentative: For a multi-billion-record bulk load, Percona raised eviction threads from 4 to 20, set eviction_dirty_trigger=5 and eviction_dirty_target=1, and cut the cache to 1 GB to cap dirty data at 10 to 50 MB. The load took about a week; Percona estimated 21 days with defaults but did not finish a default run. Percona says to raise the cache again after loading.[^c1-13] _(WiredTiger cache eviction and dirty ratio)_
- wiredTigerEngineRuntimeConfig changes eviction settings on a running mongod through setParameter, and the manual says it is available only at runtime. Percona warns that client threads block while the command runs, usually seconds but sometimes minutes on busy servers, and advises a maintenance window. To persist a setting, Percona and OneUptime both show passing it in the startup engine config string. (two sources)[^c1-6][^c1-13][^c1-35] _(WiredTiger cache eviction and dirty ratio)_
- Abandoned or long transactions hold memory that eviction cannot reclaim. MongoDB's guidance is to abort abandoned transactions and to keep transactionLifetimeLimitSeconds, which aborts expired transactions periodically to relieve cache pressure. The server README adds that if enough such transactions fill the cache, none are evicted and none make progress. (two sources)[^c1-30][^c1-42] _(WiredTiger cache eviction and dirty ratio)_

## Anti-Patterns

- Tentative: Removing the updates target and trigger (clean/dirty-only eviction) is not a safe simplification. A WT-17697 sys-perf experiment (backlog, updated 2026-06-04) found 64 significant movers, 47 regressions and 17 improvements, including tpce_locust latency up 40% to 75%. MongoDB engineers concluded updates eviction is load-bearing for update-heavy workloads. The experiment's patch also changed the cache-pressure monitor, so the result is not fully isolated. verified-as-of: 2026-06-04[^c1-19] _(WiredTiger cache eviction and dirty ratio)_
- MongoDB's manual says to avoid modifying wiredTigerEngineRuntimeConfig unless directed by MongoDB engineers, because it has major implications across WiredTiger and MongoDB; the parameter exists only at runtime and is set with setParameter. The manual also says to avoid raising the WiredTiger cache above its default, with cacheSizePct accepting at most 80% of memory. Netdata likewise says to tune eviction parameters only as a last resort, tested in staging, with a rollback plan. verified-as-of: 2026-10-14[^c1-6][^c1-5][^c1-8][^c1-15] _(WiredTiger cache eviction and dirty ratio)_
- Do not judge cache health from fill ratio alone. WiredTiger works to hold usage near eviction_target (80%) once data exceeds the cache, and application threads join only at eviction_trigger (95%) or at the dirty or updates triggers. A MongoDB forum reply and Netdata both treat about 75% to 80% fill as normal; Netdata says to graph dirty ratio, not just fill.[^c1-2][^c1-3][^c1-14][^c1-25] _(WiredTiger cache eviction and dirty ratio)_
- Every eviction target must stay lower than its trigger. The WiredTiger 3.0.0 tuning page example eviction_trigger=90,eviction_dirty_target=75 sets a dirty target far above the default dirty trigger of 20, which breaks that rule; the 12.0.0 page fixes the example by adding eviction_dirty_trigger=90.[^c1-3][^c1-2][^c1-4] _(WiredTiger cache eviction and dirty ratio)_
- Eviction tuning is a last resort. The MongoDB manual says to avoid modifying wiredTigerEngineRuntimeConfig unless MongoDB engineers direct it, because it has major implications across WiredTiger and MongoDB. Netdata lists eviction parameters after throttling writes, ending long operations, checking storage and resizing the cache.[^c1-6][^c1-15] _(WiredTiger cache eviction and dirty ratio)_
- Vendor dirty-ratio alert levels are heuristics, not MongoDB-defined limits. Netdata gives above 10% to alert, 15% as warning and 20% as critical. Vortex IQ alerts above 20% and says it chose that level to match the engine default. Neither cites MongoDB documentation, OneUptime gives no thresholds or sources, and Netdata's lead-time claim of 'minutes' for the dirty ratio comes without data. (two sources)[^c1-14][^c1-36][^c1-35] _(WiredTiger cache eviction and dirty ratio)_
- A larger cache is not a fix when writes outpace disk flush. Vortex IQ says a larger cache only treats the symptom because dirty bytes still have to reach disk. The manual advises against raising the cache above its default and allows cacheSizePct up to 80% of memory when needed. Percona instead shrank the cache to 1 GB to cap dirty bytes, at the price of more disk reads. (two sources)[^c1-36][^c1-5][^c1-13] _(WiredTiger cache eviction and dirty ratio)_
- The default 20% dirty trigger can be too large on big caches. WT-11173 (open when fetched, last updated 2024-03-07) estimates about 102 GB of dirty data allowed on a 512 GB cache and proposes an absolute cap such as 10 GB. Percona notes that even 1% of a 256 GB cache is about 2.56 GB flushed each minute. (two sources) verified-as-of: 2026-10-20[^c1-18][^c1-13] _(WiredTiger cache eviction and dirty ratio)_
- Tentative: Lowering dirty thresholds helps only if eviction workers can keep up. A commenter on Percona's post reported that dirty trigger 5 with dirty target 1 'didn't help much' for their load, and argued the change works only when worker threads keep up and the load stays mostly below the old 20% level.[^c1-13] _(WiredTiger cache eviction and dirty ratio)_

## Troubleshooting

- MongoDB's recorded workaround for the updates-trigger problem is to raise eviction_updates_trigger in small steps until the problem stops; success was seen with values as high as 95%. WT-15538 names two costs: more memory fragmentation, which raises out-of-memory risk on memory-limited hosts, and a higher cache-miss rate. It says legacy_page_visit_strategy=true is not recommended, and the WiredTiger 12.0.0 reference calls that option highly discouraged because it re-introduces a bug where eviction can fail to find older cache content. (two sources) verified-as-of: 2026-10-09[^c1-20][^c1-4] _(WiredTiger cache eviction and dirty ratio)_
- Application-thread eviction can occur well below the documented 95% fill and 20% dirty triggers. A MongoDB 5.0.10 forum post (2023-07-11) reported spikes in pages evicted by application threads, with latency spikes, at 80% cache fill and 1.4% dirty; the reply named no cause beyond other cache consumers. The separate updates trigger (half the dirty trigger by default) is a candidate cause, since WT-15538 shows the update ratio can exceed the dirty ratio, but the thread does not confirm it. (two sources) verified-as-of: 2026-10-09[^c1-25][^c1-20][^c1-23] _(WiredTiger cache eviction and dirty ratio)_
- Tentative: A May 2025 MongoDB forum post described an 850 GB WiredTiger cache holding about 400 GB of active data, dirty pages well below 64 GB, fill peaking near 80%, and queries spending most of their time waiting for cache. A community reply attributed this to eviction threads that cannot keep up and suggested eviction=(threads_min=8,threads_max=16) in configString. The thread auto-closed with no reported result, and the reply's arithmetic assumed a one-thread default that conflicts with MongoDB's default of four.[^c1-26][^c1-9] _(WiredTiger cache eviction and dirty ratio)_
- MongoDB parameter transactionTooLargeForCacheThreshold (default 0.75, new in 6.2) sets the share of the dirty cache a transaction may use and still be retried after a cache-pressure rollback. With the 20% dirty limit that is 15% of total cache (0.75 * 20%). A larger transaction rolled back for cache pressure fails with TransactionTooLargeForCache instead of retrying. Setting the parameter to 1.0 disables the limit. (two sources) verified-as-of: 2026-10-14[^c1-6][^c1-9] _(WiredTiger cache eviction and dirty ratio)_
- If mongod runs in a container with less RAM than the host, WiredTiger may size its cache from host memory. MongoDB's manual says to set cacheSizeGB or cacheSizePct below the container's RAM, and Netdata lists an ignored cgroup limit as a cause of high dirty ratio. (two sources)[^c1-5][^c1-14] _(WiredTiger cache eviction and dirty ratio)_
- When cache pressure forces WiredTiger to roll back a transaction, the error MongoDB returns depends on version. Early servers surfaced a WriteConflict. SERVER-60839 (fixed in 5.0.15 and 6.0.0-rc0) added TemporarilyUnavailable: the server retries internal operations indefinitely with growing backoff, and retries user operations a fixed number of times before returning the error. Since 6.2, a transaction too large for the cache returns TransactionTooLargeForCache and is not retried.[^c1-38][^c1-31] _(WiredTiger cache eviction and dirty ratio)_
- transactionTooLargeForCacheThreshold (new in 6.2, default 0.75) decides when a cache-pressure rollback is final instead of retried. The parameters page says setting it to 1.0 disables the behavior. The two manual pages describe its base differently, so verify behavior on your version. (two sources)[^c1-6][^c1-31] _(WiredTiger cache eviction and dirty ratio)_
- A lagging majority commit point raises cache pressure. In a PSA replica set with a down or lagging data-bearing member, majority writes stall and the storage engine keeps every change after the commit point on disk as durable history. The manual says this can greatly impact write performance and increase cache pressure. It says setting votes: 0 and priority: 0 on the lagging member lets majority writes succeed and reduces the pressure. SERVER-31767 likewise describes cache pressure from storing history. (two sources)[^c1-32][^c1-41] _(WiredTiger cache eviction and dirty ratio)_
- Time-series collections close buckets early under cache pressure. One documented closure reason is that the set of active buckets does not fit within the allowed storage engine cache size, and serverStatus counts these closures in numBucketsClosedDueToCachePressure. (two sources)[^c1-33][^c1-7] _(WiredTiger cache eviction and dirty ratio)_

## Disagreements & Open Questions

- Disagreement (WiredTiger cache eviction and dirty ratio): Eviction thread default: WiredTiger's tuning page says eviction is handled by a single separate thread by default, and its 12.0.0 reference lists threads_min 1 and threads_max 8, but MongoDB's server parameters default both to 4 and Percona reports four threads. A 2025 forum reply sized its advice on a one-thread default.[^c1-2][^c1-4][^c1-9][^c1-13][^c1-26]
- Disagreement (WiredTiger cache eviction and dirty ratio): Whether any sustained application-thread eviction is abnormal: Netdata says the target is zero and any sustained nonzero rate is a problem, while WiredTiger's design has application threads help whenever workers lag, and a MongoDB 5.0.10 forum case saw them active at 80% fill and 1.4% dirty without a documented cause.[^c1-15][^c1-1][^c1-25]
- Disagreement (WiredTiger cache eviction and dirty ratio): Cache fill alert level: Netdata's signals table alerts above 95% sustained fill but its cause table says above 80% and climbing, while WiredTiger holds usage near 80% by design through eviction_target.[^c1-15][^c1-2]
- Disagreement (WiredTiger cache eviction and dirty ratio): Raising the cache as a fix: Netdata lists increasing cacheSizeGB as remediation for high dirty ratio and application-thread eviction, while MongoDB's manual says to avoid raising the WiredTiger cache above its default.[^c1-14][^c1-15][^c1-5]
- Disagreement (WiredTiger cache eviction and dirty ratio): Updates-trigger default: WT-15538 reports success raising eviction_updates_trigger as high as 95%, WT-15843 proposed a 20% default instead of 10%, and WT-17698 found a 95% default caused a +13.0% p95 regression on insert-bound bulk_insert_w1 and should not ship globally on sys-perf evidence. WT-15843 closed as a duplicate of WT-17698, which remains open.[^c1-20][^c1-22][^c1-21]
- Disagreement (WiredTiger cache eviction and dirty ratio): Dirty-setting granularity: Percona (2020) says eviction threads are hard-coded to a maximum of 20 and dirty settings cannot go below 1% or take fractions, while WiredTiger 12.0.0 allows 1 to 64 threads and absolute sizes above 100, and MongoDB master takes GB values at startup.[^c1-13][^c1-4][^c1-9]
- Disagreement (WiredTiger cache eviction and dirty ratio): Dirty-ratio denominator: mongostat divides by maximum bytes configured, and Netdata's dirty-ratio guide does the same. Netdata's undersized-working-set guide divides dirty bytes by bytes currently in the cache. The two give different values whenever the cache is not full.[^c1-28][^c1-14][^c1-34]
- Disagreement (WiredTiger cache eviction and dirty ratio): Dirty-ratio numerator: mongostat, Ops Manager and the vendor guides use total tracked dirty bytes. WT-13642 and the vendored WiredTiger source evaluate the dirty trigger on dirty leaf bytes only.[^c1-28][^c1-37][^c1-47]
- Disagreement (WiredTiger cache eviction and dirty ratio): Alert level: Netdata alerts above 10% dirty, warns at 15% and calls 20% critical. Vortex IQ alerts above 20%. WiredTiger's trigger is 20% of dirty leaf bytes. MongoDB publishes no alert level.[^c1-14][^c1-36][^c1-2]
- Disagreement (WiredTiger cache eviction and dirty ratio): transactionTooLargeForCacheThreshold base: the parameters page defines 0.75 as a share of the dirty cache, which it says is limited to 20% of the cache (15% of total). The transactions page says the error is returned when a transaction uses more than 75% of the cache.[^c1-6][^c1-31]
- Disagreement (WiredTiger cache eviction and dirty ratio): Dirty defaults by version: the WiredTiger 2.8.0 reference lists eviction_dirty_target 80 and eviction_dirty_trigger 95. The 12.0.0 reference lists 5 and 20.[^c1-27][^c1-4]
- Disagreement (WiredTiger cache eviction and dirty ratio): Eviction thread cap: Percona (2020) says the maximum is hardcoded to 20. The 9.0.4 mongod source and the WiredTiger 12.0.0 reference allow up to 64.[^c1-13][^c1-44][^c1-4]
- Disagreement (WiredTiger cache eviction and dirty ratio): Release of the cache-pressure thread: Jira lists fix version 8.2.0-rc0, but the manual labels cachePressureQueryPeriodMilliseconds as new in 8.3. The ticket mentions a feature flag that gated the thread.[^c1-40][^c1-6]
- Disagreement (WiredTiger cache eviction and dirty ratio): Runtime tuning stance: the manual says to avoid wiredTigerEngineRuntimeConfig unless MongoDB engineers direct it. Percona and OneUptime show runtime changes to dirty and eviction limits for write-heavy loads.[^c1-6][^c1-13][^c1-35]
- Open (WiredTiger cache eviction and dirty ratio): Which MongoDB release first shipped the startup parameters wiredTigerEvictionDirtyTargetGB, wiredTigerEvictionDirtyMaxGB and wiredTigerEvictionUpdatesMaxGB? They are in the master-branch IDL but not on the manual's parameters page (cached 2026-10-14).

- Open (WiredTiger cache eviction and dirty ratio): What caused the 2023 forum case (application-thread eviction at 80% fill and 1.4% dirty on MongoDB 5.0.10)? The updates trigger is a candidate but unconfirmed.
