# Hidden indexes and safe index removal

## Overview

A hidden index is a normal MongoDB index that the query planner ignores. Hiding it (collMod index.hidden, mongosh hideIndex) lets you test a drop and reverse it at once with unhideIndex, because the index stays fully maintained. That upkeep also means hiding saves no write cost or storage; only dropIndexes does. Safe removal pairs $indexStats evidence (per node; reset by restart and by hide or unhide) with a hide, observe, drop sequence. Hiding cannot reveal what a drop would remove from a unique or TTL index, and hinted queries fail against a hidden index. Atlas Performance Advisor flags unused (7+ days), redundant (prefix) and hidden indexes, and always recommends dropping hidden ones.

## Core Concepts

### Hidden indexes and safe index removal

- A hidden index is not visible to the query planner and cannot support a query. The planner does not evaluate it during plan selection, and it does not appear even in rejectedPlans. Hiding therefore shows what would happen if the index were dropped, and unhiding undoes it without a rebuild.[^c1-1][^c1-2][^c1-15]
- A hidden index is fully maintained. Every write still updates it, and it keeps consuming disk space and memory. A hidden unique index still enforces its unique constraint, and a hidden TTL index still expires documents. The index still appears in listIndexes, db.collection.getIndexes(), db.collection.stats() and $indexStats.[^c1-1][^c1-15]
- Hiding an index does not reduce write cost or storage. Only dropping the index reclaims disk space and improves write performance. An index left hidden keeps its full maintenance cost.[^c1-19][^c1-3][^c1-1]
- Unhiding is immediate and cheaper than rebuilding. Because the index is maintained while hidden, it is available for use the moment it is unhidden. Atlas states that unhiding takes less time than rebuilding a dropped index. Percona notes that building an index is expensive on large collections or when memory is short.[^c1-1][^c1-2][^c1-3][^c1-15]
- The current MongoDB 9.0 manual says hiding an index, or creating one with the hidden: true option, requires featureCompatibilityVersion 7.0 or greater. Percona's 2020 test on MongoDB 4.4 reports FCV 4.4 as the requirement. Read the manual that matches your server version. verified-as-of: 2026-10-18[^c1-1][^c1-2][^c1-15]
- The default _id index can be neither hidden nor dropped. To remove the _id index you must drop the whole collection.[^c1-1][^c1-2][^c1-4][^c1-8]
- dropIndexes takes an exclusive lock on the collection for the duration of the operation, and all later operations on the collection wait until it finishes. Netdata advises dropping during a low-traffic window and watching globalLock.currentQueue and lock waits, because a drop under heavy write load can stall writes.[^c1-4][^c1-18]
- Tentative: dropIndexes kills only the queries that use the index being dropped. That can include queries that are still considering the index during query planning. The pages read document this kill behavior for dropIndexes only, not for hiding.[^c1-4]
- You can drop a hidden index directly. You do not need to unhide it first. If the evaluation shows a negative impact, unhide it instead of dropping it. (two sources)[^c1-4][^c1-3][^c1-12]
- Tentative: The Query Plans page lists hiding an index as a DDL event that clears the plan cache for that collection. Queries on the collection therefore plan again after a hide.[^c1-9]
- Unnecessary indexes cost write throughput, cache and disk. Each insert and delete updates every index, and an update that changes an indexed field updates each index containing that field. In WiredTiger, index pages compete with documents for cache space. Unused indexes also add disk and memory use.[^c1-18][^c1-16][^c1-17][^c1-7]
- Tentative: Since MongoDB 6.0, dropIndexes raises an error if you try to remove the last remaining shard-key-compatible index. Passing index: "*" drops every index except _id and that last shard-key-compatible index. verified-as-of: 2026-10-14[^c1-4]
- A hidden index is invisible to the query planner: the planner does not consider it for plan selection, and it does not even appear in rejectedPlans. Apart from that, it behaves like a normal index. Writes still update it, it still uses disk and memory, listIndexes and getIndexes() still list it with hidden: true, a hidden unique index still enforces uniqueness, and a hidden TTL index still expires documents.[^c1-1][^c1-15][^c1-34]
- Two hard restrictions apply. The _id index cannot be hidden. A query that passes hint() naming a hidden index returns an error instead of falling back to another plan; the server test pins this to error code 2 (BadValue).[^c1-1][^c1-20][^c1-25][^c1-34][^c1-35]
- Hiding an unhidden index, or unhiding a hidden index, resets that index's $indexStats counters. Hiding an already-hidden index or unhiding an already-visible index does not reset them. More generally, $indexStats counters also reset on mongod restart and on index drop and recreate, and the manual states that any collMod modification of an existing index resets them.[^c1-1][^c1-2][^c1-6][^c1-5]
- Hiding validates only the read side of a drop. A hidden index is still fully maintained, so write amplification, WiredTiger cache use and disk use do not fall until the index is dropped. For this reason the Atlas Performance Advisor always recommends dropping hidden indexes. Treat hiding as a time-boxed trial, not a resting state.[^c1-1][^c1-3]
- Hiding is cheap to undo; dropping is not. A hidden index is fully maintained, so unhiding makes it usable immediately. A dropped index must be rebuilt, which Percona calls quite expensive for large collections or when memory is short, and Atlas notes that unhiding takes less time than rebuilding. A hidden index can be dropped directly; unhiding it first is not required.[^c1-2][^c1-21][^c1-15][^c1-3]
- Hiding an index clears the plan cache of its collection. The query-plans manual lists 'creating, deleting, or hiding an index' as DDL events that clear that collection's plan cache. SERVER-102775 says hiding any index clears the entire collection plan cache, forces every later query to replan, and can cause a 'multiplan storm'. SERVER-103054 says dropping an already-hidden index also clears the entire plan cache. As of 2026-10-20 both tickets are in Backlog with no fix version. Inference: hide large, query-heavy collections off-peak. verified-as-of: 2026-10-20[^c1-9][^c1-31][^c1-32]
- Hidden indexes shipped in MongoDB 4.4, and hiding required featureCompatibilityVersion 4.4 or greater at that time. The collMod reference still says 4.4 in its option description. Hidden-index pages for other manual versions print a different number (see disagreements), so check the cluster's actual FCV instead of trusting one page. (two sources) verified-as-of: 2026-10-20[^c1-15][^c1-6]
- Unneeded indexes cost every write. Each insert and delete updates every index, and an update to an indexed field removes and re-adds entries in each index that contains the field. Indexes also compete with documents for WiredTiger cache. MongoDB says an index on every field bloats a collection and hurts write performance; Percona says extra indexes hurt write performance, disk and memory. A collection can hold at most 64 indexes. verified-as-of: 2026-10-14[^c1-7][^c1-16][^c1-18][^c1-25]

## Methodology

- The MongoDB manual's workflow for removing an index has three steps. First, evaluate usage with $indexStats. Second, hide the candidate indexes with hideIndex(). Third, once no harm shows, drop them with dropIndexes([...]). The Drop an Index page says to consider hiding before dropping, and the Atlas page repeats that advice.[^c1-7][^c1-8][^c1-3][^c1-1] _(Hidden indexes and safe index removal)_
- $indexStats returns usage per index. accesses.ops counts user operations that used the index, and accesses.since is when MongoDB began gathering statistics. Internal operations such as TTL deletion and chunk split or migration are not counted. The counters reset on mongod restart, on index drop and recreation, and when collMod modifies the index.[^c1-5][^c1-16][^c1-17] _(Hidden indexes and safe index removal)_
- Hiding an unhidden index, or unhiding a hidden index, resets that index's $indexStats. Hiding an already hidden index, or unhiding an already unhidden one, does not reset them. Read and record accesses.ops and accesses.since before you hide.[^c1-1][^c1-2][^c1-5] _(Hidden indexes and safe index removal)_
- Judge the effect of a hide with application latency, slow-query log entries and explain() on the critical query shapes, not with the hidden index's own counter. The planner cannot choose a hidden index, so its counter is no evidence of safety. After a removal, watch for COLLSCAN entries and a rising docsExamined to docsReturned ratio. (two sources)[^c1-18][^c1-1][^c1-7] _(Hidden indexes and safe index removal)_
- $indexStats reports usage only for the node where the query runs. Run it on every data-bearing node, secondaries included, before you call an index unused. The Atlas Data Explorer Usage metrics show the primary only, so they miss indexes that serve secondary reads.[^c1-5][^c1-10][^c1-11][^c1-7] _(Hidden indexes and safe index removal)_
- On a sharded cluster, an index can be idle on one shard and busy on another. Netdata advises collecting $indexStats from each shard primary and summing accesses.ops across shards before calling an index globally unused. The manual documents a shard field in $indexStats output for sharded clusters. (two sources)[^c1-18][^c1-5] _(Hidden indexes and safe index removal)_
- The sources give different minimum observation windows. Netdata asks for at least 24 hours of uptime under representative load that includes peak and off-peak traffic. Atlas Performance Advisor flags an index after 7 days without a supported query. Percona and Pythian say to observe long enough to cover every query pattern, such as monthly reports, and to check uptime with db.serverStatus().uptime. Choose a window longer than your longest business cycle. (two sources)[^c1-18][^c1-3][^c1-16][^c1-17] _(Hidden indexes and safe index removal)_
- Redundancy is a prefix test. Atlas Performance Advisor flags an index as redundant when it matches the prefix of another index in the same collection. With indexes { a: 1 }, { b: -1 } and { a: 1, b: -1 }, only { a: 1 } is redundant. The advisor lists the covering indexes under each redundant index so you can verify the drop, and it does not recommend removing the covering indexes.[^c1-3][^c1-12][^c1-18] _(Hidden indexes and safe index removal)_
- MongoDB's documented removal workflow has three steps. (1) Evaluate usage with the $indexStats stage, on each node. (2) Hide the candidates with hideIndex(). (3) If the impact is acceptable, drop with dropIndex() or dropIndexes([...]); if the impact is negative, unhide. The manual warns that dropping an index that is actively used in production can degrade performance, and it recommends hiding first.[^c1-7][^c1-8][^c1-22][^c1-3] _(Hidden indexes and safe index removal)_
- $indexStats reports accesses.ops (the number of user operations that used the index) and accesses.since (when MongoDB began gathering that index's statistics). The count excludes internal operations: TTL deletions and chunk split and migration are not counted. Counters reset on mongod restart, on index drop and recreate, and on collMod changes. So ops: 0 means only that no user operation used the index since the since timestamp.[^c1-5][^c1-16][^c1-17] _(Hidden indexes and safe index removal)_
- $indexStats is node-local. Each node reports only the operations that ran on that node, so an index used only by secondary reads can show ops: 0 on the primary. MongoDB says to run $indexStats on every node in the cluster. The Atlas Data Explorer usage column reflects only the primary.[^c1-5][^c1-10][^c1-7][^c1-11][^c1-17] _(Hidden indexes and safe index removal)_
- Use more than $indexStats to judge impact. MongoDB's Measure Index Use page points to explain() in executionStats and allPlansExecution modes, serverStatus metrics.queryExecutor.scanned and metrics.operation.scanAndOrder, collStats totalIndexSize and indexSizes, and dbStats indexes and indexSize. Netdata adds post-removal checks: new COLLSCAN entries in the slow query log, a rising docsExamined-to-docsReturned ratio, opLatencies.writes, and the WiredTiger cache dirty ratio. (two sources)[^c1-10][^c1-18] _(Hidden indexes and safe index removal)_
- dropIndex takes an exclusive lock on the collection for the duration of the operation, and all later operations on that collection wait for it. Netdata warns that concurrent writes can stall, advises a low-traffic window, and suggests watching globalLock.currentQueue during the drop. If the target index is still building, dropIndex attempts to stop the build.[^c1-21][^c1-18] _(Hidden indexes and safe index removal)_

## Practical Patterns

- Practitioner guides add safeguards around the drop. Record index definitions with db.collection.getIndexes() as a rollback plan. Take a backup of the affected collections. Run the drop in a low-traffic window. Afterward, check the slow-query log for COLLSCAN, run explain('executionStats') on critical query shapes, and compare opLatencies.writes before and after. (two sources)[^c1-18][^c1-17] _(Hidden indexes and safe index removal)_
- Hiding shows the fallback plan. In Percona's test, hiding { cuisine: 1, borough: 1 } made the winning plan an IXSCAN on { borough: 1 } with a FETCH filter on cuisine, and rejectedPlans was empty. Netdata makes the same point: after a drop the planner may pick another index instead of a COLLSCAN, so verify critical shapes with explain(). (two sources)[^c1-15][^c1-18] _(Hidden indexes and safe index removal)_
- Tentative: Persisting $indexStats in monitoring lets the observation window outlast mongod restarts. Percona's 2018 post used the PMM mongodb exporter option -collect.indexusage, which is off by default because it runs an aggregate on the source instance. Retention must match or exceed your full application cycle. verified-as-of: 2018-11-21[^c1-16] _(Hidden indexes and safe index removal)_
- Prefix redundancy is the safest drop candidate. A single-field index that is the leading prefix of a compound index (for example { a: 1 } next to { a: 1, b: -1 }) is redundant. Atlas flags only prefix matches and lists the covering indexes so you can verify the drop; the covering indexes are not recommended for removal. The Ops Manager example drops { last_name: 1 } because { last_name: 1, first_name: 1 } covers it.[^c1-3][^c1-27][^c1-18] _(Hidden indexes and safe index removal)_
- Judge a hide trial by workload signals, not by the hidden index's own counters. Inference: a hidden index cannot accumulate ops (the planner cannot choose it, hint() on it fails, and its counters reset when it is hidden), so its $indexStats says nothing about demand. Watch the slow query log or profiler for COLLSCAN, the docsExamined-to-docsReturned ratio, tail latency, and explain('executionStats') on critical query shapes. (two sources)[^c1-1][^c1-18][^c1-10] _(Hidden indexes and safe index removal)_
- Before hiding, save the evidence that hiding will erase. Inference: record $indexStats output (ops, since, host) from every node and save db.collection.getIndexes() output. Hiding resets the counters, and a dropped index must be rebuilt from its saved definition. Netdata lists getIndexes() as the rollback plan; Pythian lists a backup of the affected collections. (two sources)[^c1-1][^c1-6][^c1-18][^c1-17] _(Hidden indexes and safe index removal)_
- Audit application code before hiding. Any query that passes hint() with the name or key pattern of a hidden or dropped index fails with an error instead of choosing another index. Search drivers, ODM models and saved queries for hint usage. An error during the hide window exposes such a dependency, and unhiding restores the index immediately. (two sources)[^c1-20][^c1-34][^c1-1] _(Hidden indexes and safe index removal)_

## Anti-Patterns

- A hidden index cannot be targeted with cursor.hint(), and active index filters cannot use it. Any operation that hints a hidden index returns an exception. Hiding an index that application code hints therefore makes those queries fail instead of only slowing them. Search the code base for hint() calls on the index before you hide it.[^c1-1][^c1-19] _(Hidden indexes and safe index removal)_
- Dropping on short evidence is the main removal mistake. Counters restart at zero after a restart, so an index that serves a monthly or quarterly job looks unused until that job runs. Percona warns that dropping an index used once a month for heavy reporting can be problematic. Netdata says not to drop within 24 hours of a restart.[^c1-16][^c1-18][^c1-17] _(Hidden indexes and safe index removal)_
- Zero accesses.ops does not prove an index is useless when it enforces a constraint. A uniqueness check on insert does not increment the counter. Dropping a unique index removes the constraint and can let duplicate keys in. A hidden unique index keeps enforcing uniqueness, and a hidden TTL index keeps expiring documents, so a hide-and-observe test cannot show what a drop would remove. (two sources)[^c1-16][^c1-18][^c1-1] _(Hidden indexes and safe index removal)_
- Do not drop a single-field index only because a compound index contains the same field in a non-leading position. Atlas Performance Advisor treats { b: -1 } as not redundant next to { a: 1, b: -1 }. Only a leading prefix makes the smaller index redundant. (two sources)[^c1-3][^c1-12] _(Hidden indexes and safe index removal)_
- ops: 0 is not proof that an index is unnecessary unless the observation window spans the longest workload cycle. Percona warns that an index used once a month for heavy reporting looks idle in between. Netdata notes that a nightly batch job may use an index that daytime OLTP never touches. The Ops Manager docs keep an infrequently used { stars: -1 } index so that a leaderboard query does not scan every document.[^c1-16][^c1-18][^c1-27] _(Hidden indexes and safe index removal)_
- The hide trial cannot test the removal of a unique or TTL index. A hidden unique index still rejects duplicates and a hidden TTL index still deletes expired documents, so hiding shows nothing about what dropping the constraint or the expiry would do.[^c1-1][^c1-15] _(Hidden indexes and safe index removal)_
- A unique index can show accesses.ops of 0 while still protecting data, because the uniqueness check on insert does not increment the counter. Dropping such an index silently allows duplicate keys. Exclude unique indexes from ops-based candidate lists. (two sources)[^c1-16][^c1-18] _(Hidden indexes and safe index removal)_
- A TTL index can show accesses.ops of 0 while it actively expires documents, because $indexStats does not count TTL deletions. Do not treat a zero count on a TTL index as evidence that it is unused.[^c1-5][^c1-16] _(Hidden indexes and safe index removal)_
- On a sharded collection, MongoDB refuses to drop or hide an index that is the only non-hidden index supporting the shard key. The exception is a hashed shard key: since 7.0.3 (also 6.0.12 and 5.0.22) its index can be dropped. The manual advises dropping it only if a supporting non-hashed index on the shard key exists, and says dropping it disables balancing for the collection until the hashed index is recreated. The _id index cannot be dropped at all.[^c1-23][^c1-24][^c1-8] _(Hidden indexes and safe index removal)_
- Hiding a text index breaks $text queries instead of slowing them. The server test hides a text index and then expects a find with $text to fail with error code 291 (NoQueryExecutionPlans). Hide-before-drop on a text index is therefore an outage risk, not a performance experiment. A text index must be hidden by name, not by key pattern. (two sources)[^c1-34][^c1-35][^c1-6] _(Hidden indexes and safe index removal)_
- Tentative: SERVER-92843: in 7.0.9 and 7.0.12 a hidden 2d index still affected planning. With two 2d indexes on the same field and one of them hidden, a $geoNear aggregation failed with IndexNotFound: 'There is more than one 2d index on admin.data; unsure which to use for $geoNear'. The ticket is Closed/Fixed in 8.1.0-rc0, with backports requested to 8.0, 7.0, 6.0 and 5.0; whether those backports shipped is unverified. verified-as-of: 2026-10-20[^c1-33] _(Hidden indexes and safe index removal)_
- Idempotent index-ensure scripts can collide with a hidden index. The server test asserts that createIndex on the same key with hidden: false, against an existing hidden index, fails with IndexOptionsConflict (code 85). Inference: pause schema-sync jobs, or give them the same hidden option, during a hide trial. (two sources)[^c1-34][^c1-35] _(Hidden indexes and safe index removal)_

## Troubleshooting

- Tentative: Before MongoDB 8.3, dropIndexes returns an IndexNotFound error when a named index does not exist, so a re-run of a drop script fails on indexes it already removed. From 8.3, dropIndexes is idempotent: it ignores missing names and drops the rest of an array. verified-as-of: 2026-10-14[^c1-4] _(Hidden indexes and safe index removal)_
- Tentative: dropIndexes can drop one index while another index build runs on the same collection. The manual says earlier versions instead failed with a BackgroundOperationInProgressForNamespace error. The manual does not give the version where that changed. verified-as-of: 2026-10-14[^c1-4] _(Hidden indexes and safe index removal)_
- Tentative: In Percona's 2020 test on MongoDB 4.4, hideIndex first failed with errmsg 'not authorized on restaurants to execute command { collMod: "restaurants", index: { keyPattern: { cuisine: 1.0, borough: 1.0 }, hidden: true }, ... }', code 13, codeName 'Unauthorized'. After db.adminCommand({ setFeatureCompatibilityVersion: "4.4" }), the same hideIndex returned { hidden_old: false, hidden_new: true, ok: 1 }. If hideIndex returns code 13 for a user who holds dbAdmin, check featureCompatibilityVersion.[^c1-15] _(Hidden indexes and safe index removal)_
- Tentative: Before MongoDB 8.1, some $geoNear queries failed with an IndexNotFound error when a hidden 2d or 2dsphere index existed, because the server was unsure which index to use. MongoDB 8.1 made some of those queries succeed. Test $geoNear paths before you hide a geospatial index on an older server.[^c1-13] _(Hidden indexes and safe index removal)_
- Tentative: Version-specific dropIndex behavior from the manual: starting in MongoDB 8.3, dropIndex is idempotent and ignores a missing index. In earlier versions it returns an IndexNotFound error. Earlier versions also return BackgroundOperationInProgressForNamespace when you drop a different index during an in-progress build; current versions allow it. verified-as-of: 2026-10-14[^c1-21] _(Hidden indexes and safe index removal)_
- If hideIndex or collMod fails, check four things. (1) The index must exist: collMod errors with 'cannot find index <name|keyPattern> for ns <db.collection>'. (2) Privilege: collMod needs the collMod action (built-in role dbAdmin); on Atlas, creating, dropping or hiding indexes needs Project Owner, Organization Owner or Project Data Access Admin. (3) featureCompatibilityVersion must be high enough: Percona's 4.4 walkthrough hit code 13 Unauthorized ('not authorized on restaurants to execute command { collMod: ... hidden: true }') until it ran setFeatureCompatibilityVersion '4.4'. (4) The _id index cannot be hidden, and a text index must be named. (two sources)[^c1-6][^c1-11][^c1-15] _(Hidden indexes and safe index removal)_

## Disagreements & Open Questions

- Disagreement (Hidden indexes and safe index removal): Required featureCompatibilityVersion for hiding differs by source date. Percona's 2020 article on MongoDB 4.4 says FCV 4.4. The current 9.0 manual says FCV 7.0 or greater. The two describe different manual versions, so check the manual for your server.[^c1-15][^c1-1]
- Disagreement (Hidden indexes and safe index removal): Percona's 2020 post got a code 13 'Unauthorized' error from hideIndex and cleared it by setting FCV 4.4. The manual names the collMod privilege (dbAdmin) as the access requirement and does not describe an Unauthorized error for a low FCV. The post does not show whether the error came from FCV or privilege.[^c1-15][^c1-2]
