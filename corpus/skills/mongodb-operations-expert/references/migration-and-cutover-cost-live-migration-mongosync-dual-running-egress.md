# Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)

## Overview

Migrating a MongoDB deployment has almost no tool cost and several indirect ones. Atlas Live Migration (pull or push) is a free MongoDB-hosted wrapper around mongosync, and nothing bills for data arriving in Atlas. The money goes to a destination sized at least two tiers above the source, extra destination disk and oplog, a migration host for push or standalone mongosync, the sender's egress, and the overlap while both clusters run; Atlas's cutover timer is 120 hours after the initial copy. Downtime is the write block between stopping source writes and the destination accepting writes, driven by replication lag. mongosync cannot move time-series collections, users and roles, or Atlas Search indexes, and cannot collapse shards into a replica set. Atlas egress lists at $0.09-$0.16/GB on AWS. Google, AWS and Azure waive egress only for full exits, and the EU Data Act ends switching charges on 12 January 2027. No Atlas exit waiver was found.

## Core Concepts

### Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)

- Moving data into Atlas incurs no ingress fee: Atlas does not charge for incoming data transfer to an Atlas cluster, and AWS states there is no charge for inbound data transfer across all services in all Regions. The metered leg is the sender's egress, billed by the source's provider, or by Atlas when the source is an Atlas cluster. verified-as-of: 2026-10-20[^c1-2][^c1-17]
- Atlas Live Migration carries no tool fee: the Atlas data-transfer docs call it 'the free Atlas Live Migration Service'. MongoDB's migration guidance frames the cost the user controls as destination-cluster sizing: temporary scaling during the sync, then resizing to the right tier after cutover. (two sources) verified-as-of: 2026-10-20[^c1-2][^c1-1]
- For the migration window, MongoDB recommends a destination Atlas tier at least two tiers above the source, at least an M40, and an M80 with 6000 IOPS disks or higher for large data sets. It tells users to disable auto-scaling on the destination during the migration and to set a large fixed oplog size or minimum oplog window there. Users may raise the destination tier temporarily and resize after cutover. verified-as-of: 2026-10-20[^c1-8][^c1-9][^c1-1]
- Atlas starts an extendable 120-hour (5-day) timer when it detects that source and destination are nearly in sync. When the timer expires, Atlas stops synchronizing and the user must retry the migration. The timer starts after the initial copy, so dual-running lasts the initial-copy time plus up to 120 hours, or more if the user extends the sync. verified-as-of: 2026-10-20[^c1-8][^c1-9]
- While a live migration runs, Atlas pauses both scheduled and on-demand cloud backup snapshots of the target cluster. Atlas resumes them automatically after the cutover step. The destination takes no new Atlas snapshots during the overlap.[^c1-8][^c1-9]
- The mongosync destination needs disk for the logical data plus the destination oplog entries the initial sync writes. The mongosync FAQ example: migrating 10 GB of data needs 10 GB for the data and another 10 GB for insert oplog entries. From mongosync 1.22, /start estimates on-disk size, applies a 1.25x safety factor, and returns InsufficientDestinationDiskSpace if the destination lacks room. skipDiskSpaceCheck: true turns the check off. The check is best effort only. verified-as-of: 2026-10-20[^c1-5][^c1-4]
- In a mongosync cutover, application downtime runs from stopping writes on the source until the application can write to the destination after /progress reports canWrite: true. Start only when canCommit is true and lag.overallLagSeconds is near 0. If the embedded verifier is on, also require both verification documents to show lagTimeSeconds near 0 in the 'stream hashing' phase. If lag is not near 0 when cutover starts, the cutover can take a long time. With default settings mongosync blocks source writes once the user requests commit, and the user must first wait for open source transactions to commit or abort.[^c1-6][^c1-3]
- mongosync copies unique indexes as non-unique indexes and restores uniqueness at commit. /progress returns canWrite: true once the indexes are set to prepareUnique, but the state reaches COMMITTED only after mongosync converts them to unique indexes. On large collections the conversion is resource intensive, so the gap between canWrite: true and COMMITTED can be long. Applications can write in the gap, but index builds wait and write latency can rise. (two sources)[^c1-6][^c1-7]
- mongosync supports one-time migrations only. The destination cannot serve application reads or writes until commit succeeds and canWrite is true. MongoDB states that disaster recovery, analytics, and similar use cases are not supported workflows, so mongosync cannot keep a standing standby copy during a long dual-run.[^c1-3][^c1-5]
- MongoDB suggests running the live-migration procedure twice. A first partial run stops before the cutover step and creates an up-to-date Atlas staging cluster for application tests. A second run performs the production cutover. The staging cluster is an extra Atlas cluster, so budget its run-rate for as long as it exists. (two sources)[^c1-8][^c1-9]
- Atlas docs list data transfer prices by provider (checked 2026-10-20). AWS clusters: same region $0.00-$0.01/GB, different region $0.02-$0.15/GB, out to internet $0.09-$0.16/GB. Azure clusters: internet data transfer $0.087-$0.181/GB. Google Cloud clusters: internet $0.12-$0.23/GB, between regions $0.02-$0.15/GB. The Atlas-on-AWS pricing page shows the base figures $0.01 same region, $0.02 cross-region, $0.09 internet. Ranges depend on region. Atlas charges no incoming transfer and charges no outgoing transfer on Free and Flex tiers. verified-as-of: 2026-10-20[^c1-2][^c1-14]
- MongoDB says the vast majority of Atlas customers spend less than 10% of their budget on data transfer (Atlas docs), and that data transfer fees are under 10% of the bill for most customers (AWS pricing page). These are vendor statements about steady-state spend, not about migrations. (two sources) verified-as-of: 2026-10-20[^c1-2][^c1-14]

Steps: submit an Exit Notice; Google assigns a billing-support agent within 14 days; the customer starts migrating within a 30-day Initiation Period; the Migration Period lasts at least 30 days; the customer sends a Completion Notice within 180 days after the Migration Period; the credit appears on the final invoice; the agreement for that service ends after at least 30 more days. verified-as-of: 2026-10-20[^c1-19][^c1-18]

## Tools & Frameworks

- Atlas Live Migration (pull) is the managed wrapper around mongosync: it needs little setup, the destination must be in Atlas, and the source may be on-premises or in Atlas. MongoDB recommends it for source clusters of 5 TB or less or up to 3 shards. It recommends standalone mongosync above those thresholds, and whenever the user must use VNet peering or Private Link, cannot allow a third party to reach the source, or will not import the source into Cloud Manager or Ops Manager. Standalone mongosync adds tunable parameters, pause and resume, detailed progress, direct logs, filtered sync, and a destination that may be on-premises, but the user hosts it. verified-as-of: 2026-10-20[^c1-10][^c1-1] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Pull live migration needs a publicly reachable source and cannot use VPC peering or private endpoints as the migration data path; both stay usable for application connectivity. The destination cannot be a Free or Flex cluster. Clusters on 'Latest Version With Auto Upgrades' are unsupported. MongoDB Search (Atlas Search) indexes are not migrated. Push live migration supports VPC peering or private endpoints between the migration host and Atlas, with private endpoints only within a single cloud provider and region. verified-as-of: 2026-10-20[^c1-1][^c1-8][^c1-9] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- mongosync does not sync users or roles, system.* collections, Atlas Search indexes, or Persistent Query Settings. It does not support time-series collections, clustered collections with expireAfterSeconds, Queryable Encryption, client-side field-level encryption, global clusters, or sync from a sharded cluster to a replica set. Each gap needs separate work after or instead of the sync, such as recreating users and roles and rebuilding search indexes on the destination. verified-as-of: 2026-10-20[^c1-4][^c1-7][^c1-8] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_

- In a push live migration the user provisions, secures, and runs the migration host, and Cloud Manager must monitor the source cluster. ## Methodology

- Budget a migration overlap from these documented terms: source run-rate, plus destination run-rate at least two tiers above the source, for the initial copy plus up to 120 hours of sync and the cutover window; destination disk for data plus sync oplog; a migration host for push or standalone mongosync; source-side egress; and a staging cluster if the user rehearses. MongoDB publishes no copy throughput and no downtime figure, so the duration term must come from a test run. (two sources)[^c1-8][^c1-5][^c1-2] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Tentative: Estimate egress as gigabytes moved times the sending provider's per-GB rate. Arithmetic example, not a quoted figure: 10 TB (10,240 GB) out of Atlas on AWS at the $0.09-$0.16/GB internet list range is about $920-$1,640 before any waiver. mongosync's default network compression lowers wire bytes, and change-stream traffic during the overlap adds to them. verified-as-of: 2026-10-20[^c1-2][^c1-5] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Size the source oplog window to cover the whole migration: raise the minimum oplog window when storage auto-scaling is on, or the fixed oplog size when it is off. If operations that mongosync has not applied roll off the source oplog, the sync fails. If a source outage or pause outlasts the oplog window, mongosync cannot resume, and the user must restart from the beginning, which removes all migrated data from the destination.[^c1-8][^c1-7][^c1-5] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- The embedded verifier is on by default in mongosync (since 1.9) and keeps its state in memory. The limitations page sizes it at about 10 GB plus 500 MB per 1 million documents; the start-up disclaimer says about 0.5 GB per 1 million documents and that verification fails if memory is insufficient. Verification cannot resume after a pause or restart. Atlas Live Migration verifies by default and then needs a large destination oplog; the 'Verify data post-migration' switch turns it off. (two sources) verified-as-of: 2026-10-20[^c1-4][^c1-7][^c1-8] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Tentative: MongoDB's worked example of a forced serverless-to-dedicated migration (50 GB, AWS us-east-1, help-center article dated 1 July 2025) bills a migration M50 cluster at $2.00/h for 24 h ($48.00), interim M40 and M30 clusters ($27.12 and $15.12), and data transfer at $0.01/GB (up to $5.00), total $95.24. It shows that Atlas bills a temporary oversized cluster by the hour and that auto-scaling through interim tiers adds line items. verified-as-of: 2025-07-01[^c1-13] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- AWS and Google size the credit on the data stored when the request is made, so the credit covers moving each byte once. A migration that moves data more than once can exceed it, for example re-seeding, or a forward sync plus a reverse sync kept for rollback. That example is an inference from the CMA's reasoning. The CMA judged AWS and Google credits insufficient for temporary multi-cloud use during a switch. Microsoft told the CMA its program covers multi-cloud egress inside the 60-day window for a total switch. (two sources) verified-as-of: 2025-07-31[^c1-39][^c1-19][^c1-16] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Cutover in a managed pull migration is manual. You stop writes to the source, stop the application instances, point them at the Atlas cluster, and restart them. Atlas reports the application downtime after success. MongoDB tells you to run the three-step cutover quickly to keep downtime minimal.[^c1-8][^c1-36] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Cutover downtime runs from stopping source writes until canWrite is true on the destination. The steps: confirm lag is near zero, stop writes, wait for open transactions to end, call commit, poll /progress for canWrite, verify, then repoint applications. Since mongosync 1.21, canCommit is false and /commit returns an error when mongosync or the embedded verifier lags more than 30 seconds. If lag is not near zero when cutover starts, the cutover can take a long time. verified-as-of: 2026-10-20[^c1-28][^c1-6] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Track mongosync lag against the source oplog window for the whole sync. Compare db.getReplicationInfo().timeDiff with lag.overallLagSeconds from /progress. If lag nears the window, widen the oplog window or add CPU or memory to the mongosync host. If unapplied operations roll off the source oplog, the sync fails and mongosync exits. Large data sets and long pauses are the main risk.[^c1-27][^c1-5][^c1-8] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- A migration bill has these parts. This list is derived from the sources; it is not a published formula. Destination hours at the elevated tier through initial sync, lag drain, cutover and any hold. Source environment hours until the rollback window closes. Any staging cluster from a rehearsal. The mongosync host for standalone runs. Egress billed by the source provider. Application downtime. Exit-program credits offset only the egress part. The CMA's customer research found switches usually run two sets of services at once and keep the old one for a while in case of problems. (two sources)[^c1-8][^c1-39][^c1-1] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_

## Practical Patterns

- mongosync protects small destinations: for migrations of 64 GB or less into destinations with 4 or fewer vCPUs, the collection copy issues fewer concurrent writes. Setting an explicit load level turns this off, and the user can change the load level during a sync. On Atlas destinations mongosync runs 12 createIndexes commands at once, capped by maxNumActiveUserIndexBuilds. Raising that value speeds index builds but raises destination CPU and can trigger unintended Atlas auto-scaling events. verified-as-of: 2026-10-20[^c1-3][^c1-7][^c1-5] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- A migration started with reversible: true can be reversed after commit, which keeps the old cluster usable as a rollback target. Reversal needs the same number of shards and the same major version on both clusters and no filtered sync, and the user must not drop the mongosync metadata databases. The rollback window is therefore an extra dual-running period. (two sources)[^c1-3][^c1-4][^c1-6] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Tentative: Changing the region or cloud provider of an existing Atlas cluster runs as an in-place rolling migration: Atlas replaces one node at a time, secondaries first, then the primary, using initial sync, and an election takes about five seconds on average. Each new node's initial sync adds load to the primary. The cluster cost estimate excludes data transfer, and the docs do not say whether the sync is billed as transfer.[^c1-12] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Tentative: MongoDB's architecture page limits mongodump with mongorestore to data sets under about 300 GB that can tolerate extended downtime, and limits mongoexport with mongoimport to small data sets with no index concerns. These are the fallback paths when live migration cannot be used.[^c1-1] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Reverse sync is the rollback path for standalone mongosync. Plan it at /start with reversible=true, which cannot change later. Reverse also needs the COMMITTED state, the same shard count and major version on both clusters, no legacy-format unique indexes on the source, and no destination oplog rollover between canWrite=true and /reverse. You must commit the reverse sync, or the original source stays unusable. Filtered sync and pre-6.0 sources cannot reverse, and dropping mongosync's metadata databases ends the option. verified-as-of: 2026-10-20[^c1-29][^c1-4][^c1-6] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- MongoDB's settings to contain cost and risk during a live migration: disable auto-scaling on the destination to avoid unexpected resizes, set a large fixed destination oplog for the duration, and expect Atlas to pause cloud backups on the target until cutover completes. After cutover, ask MongoDB Support to help right-size the destination to minimize cost. (two sources) verified-as-of: 2026-10-14[^c1-8][^c1-1] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Tentative: Rehearse on a staging cluster. Run the live migration up to the cutover step to get a current Atlas-backed staging cluster for testing with the target driver version, then run the full migration into a separate Atlas cluster for production. This adds one more destination cluster to the bill.[^c1-8] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Application-level dual writing is the alternative to database-level sync, and it has its own cost. Stripe's four phases are dual write, read from the new store, write only to the new store, then remove old data. Stripe's backfill was costly because finding records through production queries was slow, so it moved discovery to offline jobs on database snapshots, and it used GitHub's Scientist to compare old and new reads. Haptik warns that running two change streams at once for zero downtime risks duplicate operations, race conditions and complex conflict resolution. (two sources)[^c1-41][^c1-42] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Tentative: Haptik moved a multi-terabyte MongoDB replica set across clouds without mongosync. It seeded from a hidden secondary (priority 0, votes 0) cloned as a VM, captured changes with change streams into a delta store, and replayed the delta in a short maintenance window. Reverse streaming kept the old cluster usable for rollback. It named oplog rollover during the VM transfer and heavy CDC bandwidth as the main risks. The article gives no egress cost figures. verified-as-of: 2025-10-09[^c1-42] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_

## Anti-Patterns

- Exit waivers do not fund a partial move or a dual-run. Google's program bars migrating only part of a service; AWS scopes its waiver to all data off AWS or off one AWS service; Azure scopes its waiver to customers leaving Azure. A team that keeps part of its estate on the old cloud should assume list egress rates apply to the data it moves. (two sources) verified-as-of: 2026-10-20[^c1-19][^c1-16][^c1-20] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Vendor statements that egress is a minor part of switching cost are unmeasured for database migrations. Bloomberg reported Google's position that switching fees are about 2% of the total cost of migrating to a new provider. AWS said about 90% of its customers already pay nothing for data transfer out because of the 100 GB/month free allowance. Gartner's Lydia Leong said the cost of the move is trivial compared with the ongoing cost of storing data. None of these sources measured a database-cluster migration. (two sources)[^c1-22][^c1-23][^c1-24] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Relocating only the application tier to another cloud while the Atlas cluster stays put turns in-region traffic into billed internet transfer. One user reported an Atlas bill rising from about $250 to $850 a month, all of it on the line 'Data Transfer: Atlas AWS Internet Transfer', after moving an app from Heroku to Railway, which runs on Google Cloud (thread dated 2 May 2024). Atlas docs say queries from on-premises, across cloud providers, or between continents incur the greatest data transfer costs. (two sources)[^c1-26][^c1-2] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- mongosync does not check that a deployment meets its limitations; running it in the presence of a limitation 'could lead to undefined behavior on the destination cluster', and the limits apply for the whole migration, including pauses. Operations that break or slow a sync include DDL on the source, movePrimary, moveChunk, moveRange, reshardCollection, shard-key refinement, rolling index builds, writes by other clients to the destination, and a balancer that is enabled after start. verified-as-of: 2026-10-20[^c1-4][^c1-7] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Do not budget the exit programs as zero-rated transfer. Google and Azure pay after the move: Google puts the credit on the final invoice, and Azure issues it only after the data is out and every subscription is cancelled. The customer carries the egress bill until then and has no certainty over the credit value. verified-as-of: 2026-07-25[^c1-37][^c1-19][^c1-39] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- File the exit notice before moving data. Google requires the Exit Notice before any migration the customer expects a credit for. Azure requires advance notice through a support request. The CMA found AWS requests ineligible where the migration was already underway or notice came late. verified-as-of: 2025-09-11[^c1-19][^c1-37][^c1-39] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Do not run mongosync as a standing replica for disaster recovery, analytics or other continuous use. It is built for one-time migrations. The destination cannot take application traffic until commit has run and canWrite is true. Any dual-running window with mongosync is temporary.[^c1-3][^c1-5] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Respect the write rules or lose data. Atlas blocks writes on the destination when a live migration starts. Other clients must not write to the destination while mongosync runs. A write to the source during commit can cause data loss.[^c1-8][^c1-4][^c1-28] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- A reversible rollback window lengthens the dual-running bill. Both clusters stay in service, and reverse sync replicates every post-cutover write on the destination back to the old source. When the destination is Atlas, that flow is outbound transfer, which Atlas bills (Atlas charges outbound but not inbound). This cost is derived from the reverse-sync and Atlas pricing docs; neither states it. (two sources) verified-as-of: 2026-10-14[^c1-29][^c1-2] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Tentative: The Atlas Live Migrate (Pull) procedure does not describe a reverse sync. A 2021 customer request asks for a fallback sync because there is no way to sync data in reverse after a Live Migrate cutover. MongoDB's comparison page lists reverse sync as a row that differs between Atlas Live Migration and standalone mongosync. Treat rollback from a managed pull migration as unavailable until MongoDB confirms otherwise. verified-as-of: 2026-10-20[^c1-35][^c1-10] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- A live migration does not carry everything across. Atlas migrates no users or roles, and neither migration path syncs MongoDB Search (Atlas Search) indexes. mongosync does not replicate system.* collections, and it rejects time-series collections, serverless clusters, Queryable Encryption and client-side field-level encryption. Persistent Query Settings need a manual move. Budget time to recreate these after cutover. verified-as-of: 2026-10-20[^c1-8][^c1-4] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Destination indexes can end up larger than source indexes. mongosync builds indexes before the copy by default and copies in _id order. The fixes cost time or load: buildIndexes=never means you build indexes by hand afterward, buildIndexes=beforeDataCopy can lengthen the migration, and a rolling initial sync or compact after migration adds load. (two sources) verified-as-of: 2026-10-20[^c1-5][^c1-4] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_

## Troubleshooting

- For sharded migrations without namespace filtering, mongosync needs the balancers stopped. Since version 1.17 it disables them during initialization and waits 15 minutes for in-flight chunk migrations, and it fails if a balancer is enabled later. Atlas Live Migration stops the balancers on both clusters for the whole procedure and restarts them at the end; if it cannot restart one, a banner tells the user to restart it manually. mongosync does not preserve chunk distribution, so the user rebalances the destination after cutover. verified-as-of: 2026-10-20[^c1-7][^c1-8][^c1-4] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- mongosync returns 'Invalid URI option, read concern must be majority' or 'Invalid URI option, write concern must be majority' when a connection string sets a non-majority concern. After a fatal error the user deletes all migrated data on the destination, including the __mdb_internal_mongosync database, and starts a new migration. Log lines that contain 'error' or 'failure', and duplicate key errors, are normal and do not mean the sync is failing. (two sources)[^c1-5][^c1-7] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- If mongosync crashes during commit with default write blocking, source writes can stay blocked. Run db.adminCommand({ setUserWriteBlockMode: 1, global: false }) on the source to unblock them. If mongosync disabled a balancer and then failed before commit, run balancerStart manually unless the user will run mongosync again.[^c1-6][^c1-7] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Tentative: Before MongoDB 8.0.20, a replace operation that adds a field named $v makes mongosync exit with an unrecoverable fatal error during change event application, and resuming fails with the same error. The fix is to restart the sync from scratch after deleting mongosync's metadata database on the destination, or to upgrade the source to 8.0.20 or later. verified-as-of: 2026-10-20[^c1-4] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- If an Atlas cutover has run for at least 12 hours, Atlas emails the user to check the migration or contact support. If live migration cannot recover automatically from network interruptions or elections on either cluster, the user restarts it from the beginning, which repeats the initial copy and extends the dual-running period.[^c1-8][^c1-9] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Tentative: On large collections, converting prepareUnique indexes to unique indexes during commit can be resource intensive. That can leave a long gap between canWrite=true and COMMITTED. Writes may see extra latency in the gap, and operations that need exclusive locks, such as index builds, wait until the conversion finishes. verified-as-of: 2026-10-20[^c1-6] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- A managed pull migration tries to survive elections and network interruptions but can fail. If it cannot recover on its own, you restart from the beginning. Standalone mongosync keeps its restart state on the destination, so restarting it with the same parameters resumes the sync, and since 1.18 it retries network or availability errors for up to 30 minutes. A restart from zero extends the time you pay for both environments. verified-as-of: 2026-10-20[^c1-8][^c1-5][^c1-30] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Documents updated very frequently (hot documents) cause replication lag that delays a low-lag commit. mongosync 1.18 added --hotDocIDs to copy named hot documents at the commit stage. The option is not retained on a reverse sync, so restart mongosync with hot document IDs for the reverse direction. verified-as-of: 2026-10-20[^c1-30][^c1-29] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Sources older than 6.0 add constraints. No DDL may run on the source during the migration (collMod, create, createIndexes, drop, rename and similar, including collections created implicitly by inserts). Reverse is unavailable. Sharded 5.0 sources need cleanupOrphaned on every shard's primary first. (two sources) verified-as-of: 2026-10-20[^c1-4][^c1-8] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_
- Pull live migration validates before moving data. It supports specific source and destination version pairs (sources from 5.0 to 8.0), rejects clusters on Latest Version With Auto Upgrades, cannot target Free or Flex clusters, needs an empty destination or the clear-data option, and fails if the source holds the mongosync_reserved_for_internal_use database. (two sources) verified-as-of: 2026-10-14[^c1-8][^c1-32] _(Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress))_

## Disagreements & Open Questions

- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): The mongosync limitations page sizes the embedded verifier at about 10 GB plus 500 MB per 1 million documents; the mongosync start-up disclaimer says about 0.5 GB per 1 million documents.[^c1-4][^c1-7]
- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): The Atlas architecture page says source and destination topologies must match (both replica sets, or sharded with the same shard count). The Atlas pull-migration page supports replica set to sharded migrations with sharding parameters and says shard counts may differ.[^c1-1][^c1-8]
- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): The mongosync FAQ says mongosync builds indexes before copying data by default; the mongosync behavior page says that for sources on MongoDB 6.0 or later it builds indexes after the data copy.[^c1-5][^c1-7]
- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): The mongomirror page says the tool is end of life since 31 July 2025; the Atlas architecture page still lists it as a manual migration tool.[^c1-11][^c1-1]
- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): AWS Prescriptive Guidance gives 6.0.8 as the minimum version for guided pull or push live migration; the Atlas push page requires 6.0.17 on both clusters.[^c1-15][^c1-9]
- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): March 2024 coverage reports a 60-day completion window for AWS's egress waiver, and Gartner's Sid Nag called that window a challenge. AWS's page now gives non-EU customers 180 days.[^c1-23][^c1-16]
- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): MongoDB says most Atlas customers spend under 10% of budget on data transfer; one Atlas user's bill rose from about $250 to $850 a month after a cross-cloud app move. The statements differ in scope: typical spend versus one outlier.[^c1-2][^c1-26]
- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): AWS move window: AWS's own post, updated 2026-10-08, gives eligible non-EU customers 180 days. The CMA's July 2025 appendix, citing the AWS FAQ of that time, recorded 60 days. The post is newer and primary; the CMA figure is stale.[^c1-16][^c1-39]
- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): Atlas cutover timer: a 2021 MongoDB forum answer, quoting the docs of that date, says 72 hours. Current Atlas docs say 120 hours (5 days), extendable. Use the current docs.[^c1-34][^c1-8]
- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): mongomirror status: the Atlas Architecture Center (version v20260520) still lists mongomirror among manual migration tools, and the AWS Prescriptive Guidance pattern names it as the fallback when VPC peering or PrivateLink is required. MongoDB's forum announcement and its own mongomirror reference page say it reached end of life on 2025-07-31. - Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): Minimum source version for pull live migration: the AWS Prescriptive Guidance pattern lists MongoDB 6.0.13 or later. - Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): Google partial moves: the CMA appendix says Google confirmed its program applies to partial switching. Google's page, updated 2025-09-11, says customers may not migrate only a portion of a given Google Cloud service under the program, though they may exit a service completely while keeping others.[^c1-39][^c1-19]
- Disagreement (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): Azure scope: the CMA appendix says Microsoft's program is for full switching only. Microsoft's current Learn page lets UK-billed customers moving data out of UK datacenters leave single Azure services, with 180 days instead of 60.[^c1-39][^c1-37]
- Open (Migration and Cutover Cost (Live Migration, mongosync, Dual-Running, Egress)): No MongoDB statement was found on waiving or crediting Atlas data-transfer-out charges for customers leaving Atlas, or on how MongoDB applies EU Data Act Art. 29 to Atlas. Hyperscaler waivers cover the hyperscaler's own bills; whether they reach transfer billed through Atlas is unverified.
