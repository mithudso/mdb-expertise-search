# Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB)

## Overview

Consolidating search or vector retrieval into MongoDB Atlas removes the sync pipeline, second datastore and dual-write logic, and allows document-plus-embedding transactions. It is not free at production scale: MongoDB documents co-located search as testing and prototyping only, and production needs dedicated Search Nodes billed per node-hour (minimum two, plus transfer) with RAM large enough to hold the whole vector index. At small scale that floor (about $161-175 a month on AWS before the cluster) exceeds pay-as-you-go separate stores such as Pinecone's $50 minimum, so the case rests on removed operations work. Published savings figures (MongoDB's 77%, a 60-90% Qdrant claim) are unsubstantiated vendor assertions, and no independent TCO study was found. Academic and analyst sources expect vector search to become a database feature; Forrester and Pinecone limit separate stores to extreme scale or diverging growth rates.

## Core Concepts

### Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB)

- Atlas Search and Vector Search run a Lucene-based search process (mongot) beside the database that stays current by following the cluster's change stream/oplog, so the application owns no sync pipeline, second datastore or dual-write path. Removing that layer is the entire basis of the consolidation argument; the sync work moves into the platform instead of disappearing (see the lag and read-load claim).[^c1-1][^c1-8][^c1-6]
- Co-located search (the default: mongot shares the mongod node) carries no additional search fee, and MongoDB concedes it 'might be more cost-efficient' than a dedicated node, but the docs scope it to testing and prototyping (roughly under 2M documents, 10 GB of indexed data and 10,000 queries per 7 days for Atlas Search) and recommend dedicated Search Nodes for production. The Vector Search page repeats the testing/prototyping-only advice without numeric limits, and MongoDB's 2023 launch post calls the co-located model 'simple and cheap'. The no-extra-cost form of consolidation is therefore a prototype tier, not the production TCO. verified-as-of: 2026-10-18[^c1-1][^c1-2][^c1-7]
- Dedicated Search Nodes are billed per node-hour on top of the cluster: minimum 2 nodes, maximum 32 per region per shard, a full hour charged for any partial hour, plus network-transfer charges between Search Nodes and database nodes. The node count applies per shard (2 nodes on a 3-shard cluster = 6 nodes), and the rate is paid whether or not queries arrive. verified-as-of: 2026-10-18[^c1-3][^c1-1][^c1-8]
- On MongoDB's price list dated 2026-09-29 (AWS us-east-1) the cheapest listed high-CPU Search Node is S20 (2 vCPU, 4 GB RAM, 106 GB) at $0.12/hr and the cheapest listed low-CPU node is S30 (1 vCPU, 8 GB RAM, 53 GB) at $0.11/hr. At the 2-node minimum and about 730 hours a month that is roughly $175 and $161 per month before the M10+ cluster cost (inference from list prices; excludes the newer S10 tier, whose price is not on that page). (two sources) verified-as-of: 2026-09-29[^c1-4][^c1-3]
- Inference for small workloads: Pinecone Standard has a $50/month minimum (Enterprise $500/month), storage at $0.33/GB-month and read units at $16-$18 per million, so for a small corpus a production-grade Atlas search tier (about $161-$175/month for two nodes, S10 aside) costs more in raw infrastructure than a pay-as-you-go separate vector store. At that scale consolidation has to win on removed sync and operations work and atomic document-plus-embedding writes, not on the infrastructure invoice. (two sources) verified-as-of: 2026-09-29[^c1-9][^c1-4][^c1-3]
- MongoDB announced the S10 Dedicated Search Node on 2026-07-23 as a lower-cost entry tier below the S20 floor for developers and architects running M10, M20 and M30 clusters, saying the lowest dedicated tier had 'priced smaller workloads out of those benefits'. The Search price tables on the pricing page dated 2026-09-29 list no S10 row, so its hourly price could not be confirmed. (two sources) verified-as-of: 2026-09-29[^c1-5][^c1-4]
- Vector Search holds the entire index in memory. About 90% of a Search Node's RAM can hold vectors and indexes (the rest goes to the JVM) and MongoDB recommends RAM at least 10% larger than the total index size. In co-located mode on M10/M20/M30 only 1/2/4 GB (50% of 2/4/8 GB) is available to the vector index. Search-tier cost therefore tracks vector count times dimensions; automatic quantization is documented at roughly 3.75x (scalar) and 24x (binary) RAM reduction (the quantization concept covers the detail). verified-as-of: 2026-10-20[^c1-2][^c1-8]
- In the coupled model, search and database sizing must be planned together and search growth forces scaling the entire database cluster, paying for compute that may be unneeded; MongoDB's launch post also lists contention risk and no granular limits on each side's share. Dedicated Search Nodes decouple the two, which is the cost lever behind the consolidated-but-isolated architecture. (two sources)[^c1-7][^c1-6]
- Inference from list prices: node class changes the hourly price by up to about 2.3x at the same RAM. On the 2026-09-29 AWS us-east-1 list at 16 GB RAM, high-CPU S40 is $0.48/hr (8 vCPU, 426 GB), low-CPU S40 is $0.21/hr (2 vCPU, 106 GB) and storage-optimized S40-S is $0.25/hr (2 vCPU, 421 GB). MongoDB's sizing guide (2025-08-12) maps the classes to workloads: high-CPU 2:1 RAM:vCPU for full-text and heavy query load, low-CPU 8:1 for vector search at low data volume, storage-optimized 8:1 with 2x+ storage for large indexes. Matching the class to the bottleneck is the main in-platform cost lever. (two sources) verified-as-of: 2026-09-29[^c1-4][^c1-6]
- The search index is eventually consistent with the database. MongoDB's sizing guide sets a goal of under one second from collection to index and lists lag causes: cluster load, change-stream read pressure, Search Node indexing capacity, very heavy ingestion (over 10k inserts/updates per second may need sharding) and many indexes. Initial indexing and ongoing sync 'can impose considerable read pressure on the cluster'. Pinecone's page notes that neither it nor MongoDB publishes a guaranteed time for a write to become searchable. Consolidation moves sync load onto the cluster's read path; it does not remove it. (two sources)[^c1-6][^c1-8]
- Compliance can force the dedicated-node cost: with customer-managed encryption keys, co-located search indexes are not covered (only database data), while dedicated Search Nodes support Search Node Data Encryption with the same keys. Enabling customer-managed encryption on Search Nodes also forfeits the optimized resize path that reuses a recent index copy from S3 or Azure Blob. (two sources) verified-as-of: 2026-10-18[^c1-1][^c1-2]
- Independent academic and analyst sources expect vector search to become a feature of general-purpose databases. Stonebraker and Pavlo (SIGMOD Record, June 2024) call vector DBMSs 'essentially document-oriented DBMSs with specialized ANN indexes', where 'such indexes are a feature, not the foundation of a new system architecture'; several RDBMSs (Oracle, SingleStore, Rockset, ClickHouse) added vector indexes in 2023, mostly by integrating open-source libraries (pgvector, DiskANN, FAISS), and they expect vector DBMSs to become more relational-like. Forrester (July 2024, via BigDATAwire) projected about 75% of traditional databases would incorporate vector capabilities by 2026, some at no extra cost within existing licenses. These are 2024 forecasts and say nothing about Atlas pricing. (two sources)[^c1-12][^c1-11]
- Forrester and Pinecone both scope the consolidation case. Forrester (via BigDATAwire, 2024-08-22) recommends native vector databases for exceptional performance and low-latency access to very large vector volumes and says most vector databases 'haven't yet demonstrated high-end scalability and performance, particularly when handling billions of vectors'; it recommends multimodel databases when vector and non-vector data, hybrid search or existing infrastructure matter. Pinecone's compare page says a separate store wins when retrieval grows at a different rate than the database beside it, and to 'stay on Atlas' if a document and its embedding must be written in one transaction or single-query hybrid search matters. (two sources)[^c1-11][^c1-8]
- Tentative: SoftwareSeni (2026-09-28), citing third parties, lists other separate-store minimums: Weaviate Flex from $45/month, Turbopuffer $64/month, and a quiet-month model (10M vectors, 1,000 queries) of about $3 on Amazon S3 Vectors versus Pinecone's $50. These are secondhand and indicative; they show that pay-per-use object-storage designs have near-zero idle cost while Atlas Search Nodes do not (inference). verified-as-of: 2026-09-28[^c1-10]
- Atlas runs MongoDB Search and Vector Search in the mongot process in one of two layouts: co-located with mongod on the same node (Atlas enables this by default when the first search index is created), or on dedicated Search Nodes that sit apart from the database nodes and need an M10-or-higher dedicated cluster.[^c1-1][^c1-2]
- Co-located search carries no separate fee: MongoDB docs say there are no additional fees or charges when you enable Search on a cluster, only higher resource use on the existing nodes, and that running both processes on one node might be more cost-efficient than a dedicated node. The same docs warn of mongod/mongot resource contention and recommend dedicated Search Nodes for production.[^c1-1][^c1-2]
- Dedicated Search Nodes are billed hourly per node (a partial hour bills as a full hour). Atlas requires at least 2 nodes per region and allows up to 32 per region per shard, so topology multiplies the floor: 2 Search Nodes on a 3-shard cluster deploy 6 nodes. Atlas also bills traffic between Search Nodes and database nodes, but shows it at cluster level rather than as a Search Node line item.[^c1-3][^c1-1][^c1-17]
- MongoDB list prices for dedicated Search Nodes (High-CPU family), AWS us-east-1: S20 (2 vCPU, 4 GB RAM) $0.12/hr, S30 (4 vCPU, 8 GB) $0.24/hr, S40 (8 vCPU, 16 GB) $0.48/hr, S50 (16 vCPU, 32 GB) $0.99/hr. S20 is $0.14/hr on Google Cloud (us-central1) and $0.15/hr on Azure (eastus2). The pricing page shows identical tier prices under Search and under Vector Search. (two sources) verified-as-of: 2026-10-20[^c1-4][^c1-30]
- Search Node list prices have barely moved: a third-party December 2023 snapshot (region not stated) lists High-CPU S20 $0.12, S30 $0.23, S40 $0.48, S50 $0.98, S80 $3.22 per hour and Low-CPU S30 $0.11, S40 $0.21, S110 $5.79; the October 2026 AWS table shows $0.12, $0.24, $0.48, $0.99, $3.26 and $0.11, $0.21, $5.87. No compared tier moved by more than about 4%. (two sources) verified-as-of: 2026-10-20[^c1-30][^c1-4]
- S10 is the lowest dedicated Search Node tier (announced 2026-07-23 on AWS, GCP and Azure), meant for M10-M30 clusters with index footprints under 10 GB. On AWS it has 4 GiB RAM, 54 GiB storage and 1 vCPU, against 4 GiB, 98 GiB and 2 vCPU for S20. MongoDB's tier docs say Atlas deploys Search Nodes on S20 by default and that S10 is not suited to large indexes or query-intensive workloads. verified-as-of: 2026-10-20[^c1-5][^c1-17][^c1-18]
- MongoDB's own pages disagree on the minimum production search tier. The Vector Search deployment page says 'M10 or higher cluster tier and S30 or higher search tier', the Search deployment page says S20 or higher, and the tier docs make S10 the lowest tier. The public pricing tables fetched 2026-10-20 list no S10 row, so the S10 hourly price was not found; a floor-cost model that uses S10 needs the price from the Atlas UI or the pricing calculator. verified-as-of: 2026-10-20[^c1-2][^c1-1][^c1-17][^c1-4]
- Minimum isolated production footprint, derived from list prices: a dedicated cluster (M10, estimated at about $57/month on the MongoDB pricing page) plus two Search Nodes. At AWS us-east-1 High-CPU prices, two S20 nodes cost about $175/month (2 x $0.12 x 730 h) and two S30 nodes about $350/month, so the floor is roughly $230 (S20) to $410 (S30) per month before storage, backup and data transfer. (two sources) verified-as-of: 2026-10-20[^c1-4][^c1-1][^c1-2]
- Memory is the main cost driver for vector search. Atlas Vector Search holds the entire index in RAM: about 90% of a Search Node's RAM can hold vector data and indexes (the rest goes to the JVM), and MongoDB recommends RAM at least 10% larger than total index size. A 1536-dimension float32 vector takes about 6 KB, so 1M vectors is about 6 GB before index overhead. The Next Platform says consolidation 'does not remove the physics': memory, compression and tiering set the bill on any platform.[^c1-2][^c1-23][^c1-24]
- Automatic quantization cuts mongot RAM for vectors by about 3.75x (scalar) or 24x (binary), but Atlas still stores full-precision vectors on disk for rescoring. MongoDB advises roughly a 4:1 (scalar) or 24:1 (binary) storage-to-RAM ratio on Search Nodes and free disk of about 125% of the estimated index size, so quantization lowers the RAM requirement but adds a disk requirement. (two sources)[^c1-2][^c1-8]
- Atlas dedicated Search Nodes are provisioned capacity: Pinecone's comparison page describes two hourly rates (database cluster and Search Node tier) 'paid whether or not queries arrive', and MongoDB's billing docs confirm hourly per-node billing with a 2-node minimum. Pinecone instead prices storage plus read and write units. The cost shapes differ (capacity-based versus consumption-based), so the break-even depends on query rate; Pinecone says idle capacity usually decides it. (two sources)[^c1-8][^c1-3]
- Pinecone (separate vector database) prices by consumption with plan minimums: Standard has a $50/month minimum applied to usage (anything above is pay-as-you-go) and Enterprise $500/month; storage $0.33/GB-month; read units $16-$18 per million (Standard) and $24-$27 (Enterprise); write units $4-$4.50 per million (Standard) and $6-$6.75 (Enterprise). Dedicated Read Nodes have no listed price. SoftwareSeni reports Pinecone raised the low-traffic floor from roughly $8 to $50 in late 2025. (two sources) verified-as-of: 2026-10-20[^c1-9][^c1-10]
- Amazon OpenSearch Serverless bills $0.24 per OCU-hour. Classic collections need at least 2 OCUs with redundancy (about $350/month at 730 hours, derived) or 1 OCU for dev/test (about $175/month). Vector search collections cannot share OCUs with search or time-series collections (vector collections with the same KMS key share a separate set), so a vector workload next to full-text search adds a second OCU minimum. AWS's newer NextGen collections list no minimum OCU requirement and scale to zero after 10 minutes of inactivity. verified-as-of: 2026-10-20[^c1-25][^c1-27][^c1-26]
- Tentative: Elasticsearch Serverless lists search from $0.09 per VCU-hour, ingest from $0.14, storage from $0.047 per GB retained per month and egress from $0.05 per GB. No minimum charge is listed, but the page says a baseline of search resources is always provisioned and idle periods bill at a reduced rate (rate not stated). The core prices took effect 2024-12-01. verified-as-of: 2026-10-20[^c1-29]
- A separate vector store adds synchronization work that in-database search avoids. Qdrant, a dedicated-vector-database vendor, concedes sync 'is extra work' and that a model change leaves 'two copies during a migration'. The Next Platform says a separate vector database 'forces dual writes, a second consistency model, and a second thing to page someone about'. Pinecone says separate writes need retry logic and reconciliation between the record write and the vector upsert.[^c1-24][^c1-23][^c1-8]
- Atlas removes the user-built sync pipeline but not the sync: mongot replicates from mongod's oplog (Pinecone says via change streams), Atlas alerts on Index Replication Lag, and Pinecone notes neither product publishes a guaranteed time for a write to become searchable. Writing a document and its embedding in one transaction prevents record-versus-vector drift, but search results can still lag the primary write. (two sources)[^c1-19][^c1-8][^c1-1]
- Tentative: Pinecone's own comparison page says a document and its embedding can be written to MongoDB in one transaction (calling it MongoDB's clearest advantage) and that MongoDB's $rankFusion (from MongoDB 8.0) merges full-text and vector scores in one query, which Pinecone says it has no equivalent for today. A separate vector database plus a separate full-text engine therefore needs application-level fusion (inference).[^c1-8]
- Tentative: MongoDB Search and Vector Search also run on Community Edition and other self-managed deployments: Atlas does not manage mongot, there are no S-tiers, and you provision and operate the mongot hosts yourself in the same co-located or dedicated patterns, so the Atlas Search Node bill is replaced by hardware and labour (inference).[^c1-1]
- Tentative: Consolidation can also happen on a search engine rather than a database: The Next Platform lists Elasticsearch and OpenSearch alongside Postgres, ClickHouse, MongoDB and Redis as engines where vector search is now a native column type, so the realistic 'separate' comparison for a hybrid text-plus-vector workload may be Atlas against a single Elasticsearch or OpenSearch cluster rather than against two separate products (inference).[^c1-23]

## Methodology

- A separate search or vector system adds costs that list prices omit: application-side dual writes with a retry or reconciliation job (Pinecone: write the document, then upsert the vector; 'Count it when you compare the two'), a second consistency model, and another system to operate and page on. SoftwareSeni frames TCO as six line items: storage, writes, searches, idle minimums, egress and engineering operations. Atlas can write a document and its embedding in one transaction.[^c1-8][^c1-10] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Cost depends on workload shape more than list price. Pinecone's page says 'It depends on the shape of the workload more than on list prices' and offers no head-to-head comparison. SoftwareSeni concludes that idle spend and workload shape decide more than sticker price: pay-per-use or near-zero-idle options win quiet traffic, while steady heavy traffic can favour provisioned capacity or a dedicated store. Search Nodes bill whether or not queries arrive, so capacity sized to hold the index but idle between peaks is the main Atlas-side waste (inference). (two sources)[^c1-8][^c1-10] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Size from the measured index, not the collection. Index size varies with mapping (a 100-field document indexed on 5 fields gives a far smaller index; mapping all fields or autocomplete inflates it), so MongoDB suggests building a sample index to get an index-to-collection ratio. If the node's RAM is smaller than the index the remainder is paged from disk: MongoDB's example is a 10 GB index on a 4 GB node with 3 GB free for index data, leaving 7 GB paged and causing page faults, disk I/O and CPU IOWait. Local SSDs need 20% overhead for index operations. (two sources)[^c1-6][^c1-1] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Tentative: MongoDB's sizing guide gives a starting estimate of about 10 queries per second per vCPU, so the 2 x S20 minimum (4 vCPUs) supports roughly 40 QPS, with a general aim of sub-100 ms latency; real throughput depends on query complexity and index mapping. This is the only published throughput heuristic found and is vendor guidance, not a benchmark.[^c1-6] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Tentative: Embedding and reranking token spend and egress are often missing from vector-store cost calculators; SoftwareSeni says that at modest query volumes model spend can exceed the vector store invoice. Inference: these costs are the same whether retrieval is consolidated or separate, so they drop out of the consolidation delta but must stay in the absolute budget.[^c1-10] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- A TCO model for either path needs these line items: storage, writes, searches, idle minimums, egress and engineering operations (SoftwareSeni), plus embedding and reranking token spend, which calculators often omit. Atlas-specific items are the database cluster rate, at least 2 Search Nodes per region per shard, Search-to-database transfer, and a 20% local-SSD overhead on Search Nodes. SoftwareSeni and Pinecone both say idle capacity and workload shape (corpus size, query rate) decide the result more than list price. (two sources)[^c1-10][^c1-8][^c1-3][^c1-1] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_

## Practical Patterns

- Customer evidence for removing a bolt-on Elasticsearch and sync layer is qualitative and published by MongoDB. THL: about two years of sync, stability and outage problems, then Atlas Search replaced Elasticsearch iteratively, 'a couple of months' to migrate everything, Elasticsearch cluster and dedicated sync resources turned off, no cost figures given. Orbweaver: search move took about two weeks including testing, no separate ETL tool, latency down over 70%, previously 'kept scaling Elasticsearch ... extremely expensive', cost reduction stated without a number. (two sources)[^c1-13][^c1-14] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Tentative: Consolidation does not require Atlas: Community Edition supports self-managed MongoDB Search where you install and operate mongod and mongot yourself, on a single host or separate hosts, which shifts cost from Atlas Search Node rates to your own hardware and operations time (inference).[^c1-1] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- MongoDB's progression is to prototype co-located (suited to under 2M documents, under 10 GB of indexed data and under 10,000 queries per 7 days) and move to dedicated Search Nodes when usage exceeds that. S10 (July 2026) is the cheaper first step for M10-M30 clusters with index footprints under 10 GB; MongoDB says that until S10 the lowest dedicated tier priced smaller workloads out of workload isolation. verified-as-of: 2026-10-20[^c1-1][^c1-5][^c1-17] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Search Node families partly unbundle RAM from CPU. At equal RAM on AWS us-east-1 the Low-CPU family costs about 43-52% of High-CPU (8 GB $0.11 vs $0.24 per hour; 16 GB $0.21 vs $0.48; 32 GB $0.43 vs $0.99; 64 GB $0.89 vs $1.77; 128 GB $1.68 vs $3.26; ratios derived). MongoDB's own example still prefers High-CPU S20 over Low-CPU S30 for a 3 GB, 1M-vector index when concurrent queries matter, and Pinecone argues memory, query CPU and isolation are bought together in each Search Node. (two sources) verified-as-of: 2026-10-20[^c1-4][^c1-2][^c1-8] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Atlas Automated Embedding (an autoEmbed Vector Search index) generates embeddings with Voyage AI models at index time and query time, so no external embedding service or embedding pipeline is needed; docs list $0.02 (voyage-4-lite), $0.06 (voyage-4) and $0.12 (voyage-4-large, voyage-code-4) per 1M tokens. Generated embeddings are stored on the cluster in a reserved database, and on M10+ clusters storage auto-scaling must be on or the index goes Stale when disk fills. Omdia analyst Stephen Catanzano says it 'eliminates the need for external embedding pipelines'; Constellation Research frames it as removing a 'synchronization tax'. verified-as-of: 2026-10-14[^c1-20][^c1-22][^c1-28] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Cases where a separate store can win: Pinecone argues storage, reads and writes scale independently while Atlas bundles memory, query CPU and tenant isolation in each Search Node; Qdrant cites independent upgrades, regional placement and no noisy-neighbour load on the primary database; SoftwareSeni says a managed store earns its minimum under steady high query traffic and that on-premises, edge or regulated settings can force the choice. For small data and simple similarity search, Qdrant itself calls an extension inside an existing database 'the fastest way to prototype'.[^c1-8][^c1-24][^c1-10] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- For quiet or cold-but-large corpora, object-storage-backed vector stores undercut always-on RAM-resident indexes. The Next Platform reports S3 Vectors targeting up to 90% lower cost with a latency trade-off (OpenSearch disk-based mode p90 96 ms vs 24 ms in-memory); a practitioner model cited by SoftwareSeni puts S3 Vectors at about $3 versus Pinecone's $50 for 10M vectors and 1,000 queries a month. Atlas Search Nodes are always-on, RAM-resident and sold in pairs, so the same idle-cost gap likely applies to Atlas (inference). (two sources)[^c1-23][^c1-10][^c1-1] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Use stored source fields (returnStoredSource) to cut database load from search: by default mongot returns document IDs and mongod then performs a full document lookup for each match; with stored fields defined in the search index, mongot returns the fields directly, trading extra index storage for fewer lookups on the shared database nodes. (two sources)[^c1-1][^c1-2] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_

## Anti-Patterns

- Antipattern: running production search co-located on the database node, especially on M10-M30. MongoDB documents contention between mongod and mongot that can hurt index performance and query latency, and mongot is unavailable (search queries fail) during cluster tier scaling, node replacement or initial sync, mongot version updates, reboots and restarts. Fix: add dedicated Search Nodes on an M10+ cluster.[^c1-1][^c1-2][^c1-7] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Antipattern: deciding on a published savings percentage. MongoDB's price page claims search that is '4x faster and for 77% lower cost than alternative search solutions' with no basis shown in the retrieved page; a Towards AI guide (EY consultant author, 2025-10-24) claims 60-90% savings moving from Atlas Vector Search to self-hosted Qdrant, but its scenario figures are infrastructure estimates with no labour accounting and its three-year TCO is asserted without a calculation; Pinecone says it has no head-to-head comparison to point to; SoftwareSeni notes most online cost comparisons come from vendors with a stake. Model your own vector count, dimensions, QPS and sync effort. verified-as-of: 2026-09-29[^c1-4][^c1-16][^c1-8][^c1-10] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Tentative: MongoDB's Atlas Search vs Elasticsearch compare page asserts, without citation, that about 10% of engineering cycles can be lost to sync failures and recovered by Atlas Search, and that customers report 30% to 50% improvements in time to market. These are marketing figures with no stated method and should not be used as TCO inputs.[^c1-15] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Antipattern: buying a larger compute tier only to get disk. MongoDB's own example is a customer needing S50 compute but S70 storage and paying a 'major price premium'; storage-optimized nodes (375-6,000 GB, 8:1 RAM:vCPU) were added for large indexes and binary-quantized vector search, with vendor claims of up to 50% lower DSN storage cost and about 40% cheaper than high-CPU nodes anchored on RAM (2025-08-12, not independently measured). ## Troubleshooting

- Tentative: If $search fails with 'Failed to Execute search Command' on a cluster that has no dedicated Search Nodes, mongot probably terminated during a cluster scale-up, node failover or mongot upgrade; search queries fail until mongot is running again or an initial sync completes. With dedicated Search Nodes, mongod uses a proxy that routes search queries only to healthy nodes where mongot is active.[^c1-1] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Dedicated Search Nodes cannot be enabled everywhere: they need an M10 or larger dedicated cluster (not Free or Flex), a cloud region that supports node isolation (all Google Cloud regions but only a subset of AWS and Azure regions), and are not supported on Atlas Infinite clusters during public preview. A cluster in an unsupported region must be migrated before consolidation onto isolated search is possible. verified-as-of: 2026-10-18[^c1-1][^c1-3][^c1-2] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Tentative: Adding Search Nodes or changing the search tier triggers a rebuild of the full search index; on AWS or Azure with dedicated nodes and without customer-managed encryption, Atlas instead reuses a recent index copy from S3 or Azure Blob. Expect extra indexing and read load on the cluster during a rebuild (inference), and schedule resizes accordingly. verified-as-of: 2026-10-20[^c1-2] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Tentative: Selective filters can multiply vector query cost: Pinecone, summarising MongoDB's own benchmark, reports that for a filter matching about 3% of a 15.3M-vector corpus, reaching 90-95% recall cost about four times the unfiltered query under binary quantization; the engine falls back to exact nearest-neighbour search when a query asks for more candidates than match the filter inside a Lucene segment. Test with your real filters before sizing Search Nodes.[^c1-8] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- If mongot falls behind the oplog window it cannot sync incrementally and performs a full index rebuild; during the rebuild search queries keep working but return stale results. On dedicated Search Nodes, replication pauses at 90% disk utilization (warning alert at 85%) and resumes below 85%. MongoDB's remedies are upscaling Search Nodes (more CPU and memory for replication), adding nodes, deleting unused indexes, throttling bulk writes, or growing the oplog. (two sources)[^c1-19][^c1-31] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Tentative: Scaling Search Nodes (count or tier) triggers a rebuild of the full search index. On AWS and Azure without customer-managed-key encryption, Atlas can use a recent index copy from S3 or Azure Blob Storage instead; the optimization is not yet available on Google Cloud. Deleting all Search Nodes interrupts search query processing.[^c1-2] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
- Under-sized Search Node RAM degrades before it fails: when the index exceeds the memory available to mongot, pages are read from disk, causing page faults, disk I/O, CPU IOWait and slower queries (MongoDB's example: a 10 GB index on a 4 GB node). At the limit the 'Search Process: Ran out of memory' alert fires and 'indexing and queries fail'; sustained query pressure raises 'Search Process is Overloaded', where the remedy is a tier with more vCPUs. (two sources)[^c1-1][^c1-19] _(Platform Consolidation TCO (Atlas Search/Vector Search vs Separate Search or Vector DB))_
