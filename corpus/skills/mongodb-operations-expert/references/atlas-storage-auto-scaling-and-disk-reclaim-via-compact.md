# Atlas storage auto-scaling and disk reclaim via compact

## Overview

Atlas Core clusters raise disk automatically when any node passes 90% used, but never lower it. Auto-scaling is up-only, and a manual reduction forces new volumes, a data sync and per-node downtime, because AWS, Azure and Google Cloud cannot shrink volumes in place. Deleting or expiring data (TTL included) frees nothing on disk, because WiredTiger keeps freed blocks for reuse. compact (run per node; dryRun and autoCompact since 8.0) returns blocks to the OS but does not change provisioned size, so reclaim and shrink are separate steps. Atlas blocks writes, deletes included, once free disk gets critically low. Traps: compaction needs headroom and can slow checkpoints and backups, Terraform can revert an auto-scaled disk, and oplog or tier limits can stall scale-ups. Volatile as of 2026-10: Atlas Core vs Infinite editions.

## Core Concepts

### Atlas storage auto-scaling and disk reclaim via compact

- On an Atlas Core dedicated cluster, storage auto-scaling is on by default. Atlas raises cluster storage when disk space used reaches 90% on any node. To opt out, clear the Storage Scaling checkbox in the Auto-scale section. verified-as-of: 2026-10-18[^c1-1][^c1-2]
- Tentative: On AWS, Azure and Google Cloud, a storage scale-up sizes the new disk to bring used space to about 70%. verified-as-of: 2026-10-18[^c1-1]
- Atlas auto-scales storage up only. Lowering storage is a manual change on the Edit Cluster page. A user whose cluster auto-scaled from 8 GB to 32 GB after a one-time load had to try to scale it back by hand (forum thread, January 2024). verified-as-of: 2026-10-18[^c1-1][^c1-3][^c1-15]
- A storage scale-up can also change the cluster tier. If the new capacity exceeds what the current tier supports, Atlas raises the tier even when tier auto-scaling is off. Documented example: an M30 tops out at 480 GB, so a 600 GB need moves the cluster to M40. If the configured maximum tier cannot hold the new capacity, Atlas raises that maximum and turns off downward tier auto-scaling. (two sources) verified-as-of: 2026-10-18[^c1-1][^c1-8]
- After a disk auto-scale, further auto-scaling and manual disk scaling may be unavailable for a few hours. On AWS the cause is the EBS limit: at most four modifications per volume in a rolling 24 hours, and each must finish before the next starts. Atlas delays later storage or IOPS changes until AWS allows another. verified-as-of: 2026-10-18[^c1-1][^c1-3][^c1-19]
- Tentative: On AWS the first storage increase is done in place with no downtime. For later increases Atlas provisions new volumes and syncs data from the old ones if the last change was under 6 hours ago (volumes under 1 TB) or under 6 hours per TB ago (volumes over 1 TB). During that sync the cluster stays reachable, but a node being modified is unreachable until its new volume attaches. Otherwise Atlas waits out the cooldown and modifies in place. On M40+ non-NVMe AWS clusters, Atlas also uses one EBS modification for fast disk pre-warming during a cloud-based initial sync. Single vendor page. verified-as-of: 2026-10-18[^c1-3]
- No cloud provider shrinks a block volume in place. AWS states 'You can't decrease the volume size'. Google Cloud states a disk's size cannot be reduced; the workaround is a new smaller disk plus a copy. Atlas documents the same limit for Azure. So Atlas always lowers storage by provisioning new smaller volumes and syncing data from the old ones. Each node has downtime during its sync, and the Azure and GCP pages warn of a rolling restart. verified-as-of: 2026-10-18[^c1-3][^c1-19][^c1-20]
- Oplog size can block a storage scale-up. Atlas delays an auto-scaling event until the oplog window covers the estimated scaling time. For storage auto-scaling to complete, Atlas requires oplogMinRetentionHours to be up to 60 seconds multiplied by the GB of configured disk space. When the oplog is too small Atlas raises 'Auto-scaling: Disk auto-scaling didn't initiate due to insufficient oplog size'. At the tier's disk ceiling it raises 'Auto-scaling: Disk auto-scaling didn't initiate due to the cluster reaching maximum available disk size'. verified-as-of: 2026-10-18[^c1-3][^c1-2][^c1-5]
- On an Atlas Infinite cluster (public preview) storage grows with the data and there is no storage auto-scaling to configure. You set a maximum storage size, and Atlas blocks writes when logical data size approaches it. The 'Disk Space % Used' alert does not apply; Atlas raises 'Atlas Infinite: Storage Space Used %' instead. During preview Atlas may throttle writes before the limit. (two sources) verified-as-of: 2026-10-20[^c1-1][^c1-4][^c1-6]
- Tentative: WiredTiger does not overwrite in place, so expect about 20% more disk than the compressed data occupies. MongoDB also uses part of the configured capacity for buffer, journal and log files.[^c1-3]
- After deletes, WiredTiger keeps the freed blocks in its data files for reuse and does not return them to the OS, so disk usage stays flat. compact releases obsolete blocks to the OS for a collection and its indexes. How much it frees depends on how many free blocks exist and where they sit in the file. It can free nothing. freeStorageSize in collStats shows the reusable space; Percona points to wiredTiger.block-manager 'file bytes available for reuse' in collection stats.[^c1-10][^c1-18][^c1-16]
- Deleting documents does not lower disk usage on its own, and a TTL index never triggers compaction. On Atlas, after deleting about 100 million of 110 million documents, one user's collection reported about 25 GB but cluster storage and backup size did not drop. In another thread, primary disk use fell from about 40 GB to about 6 GB only after a manual compact, and each secondary needed its own compact. (two sources)[^c1-17][^c1-16][^c1-18]
- On an Atlas Core (dedicated) cluster, storage auto-scaling is on by default. Atlas raises disk capacity when disk used reaches 90% on any node. On AWS, Azure and GCP it sizes the new disk so that usage lands at 70%. verified-as-of: 2026-10-18[^c1-1][^c1-21]
- Storage auto-scaling only grows disks. As of the 2026-10-18 Atlas docs, Atlas does not shrink a disk automatically. Lowering capacity is a manual change from the Edit Cluster page. (two sources) verified-as-of: 2026-10-18[^c1-1][^c1-3]
- On AWS and Azure the cloud provider cannot shrink a volume in place. Atlas lowers capacity by provisioning new volumes and syncing data from the old ones. Each node is unavailable while its data syncs. Atlas always uses this path for decreases, even though it can resize in place for increases. verified-as-of: 2026-10-18[^c1-3][^c1-19]
- AWS allows at most four Elastic Volumes modifications per EBS volume in any rolling 24 hours, and a new modification waits for the previous one to complete. Atlas inherits this limit, so repeated storage or IOPS changes, including auto-scaling, can be delayed. The Clusters page then shows: 'Some EBS volume changes are delayed because AWS has reached the maximum number of allowed EBS volume modifications for this volume within a 24-hour period.'. verified-as-of: 2026-10-18[^c1-19][^c1-27][^c1-3]
- After a disk auto-scaling event, further disk auto-scaling and manual disk scaling may be unavailable for a few hours. On AWS the first change is made in place without downtime. A later increase made inside the cooldown (6 hours, or 6 hours per TB above 1 TB) provisions new volumes and syncs data. After the cooldown Atlas modifies the volume in place. (two sources) verified-as-of: 2026-10-18[^c1-1][^c1-3]
- Storage auto-scaling can raise the cluster tier. If the new capacity exceeds what the current tier supports, Atlas also raises the tier, even when tier scaling is disabled. Docs example: an M30 at its 480 GB maximum and 90% full needs 600 GB, so Atlas moves it to M40. If a smaller tier cannot hold the configured disk, Atlas does not scale the cluster down to it and raises an event. (two sources) verified-as-of: 2026-10-20[^c1-1][^c1-5]
- On Atlas Core, Atlas delays a storage auto-scaling event until the oplog window covers the estimated scaling time. The docs state that Atlas requires oplogMinRetentionHours 'to be up to (60 seconds) * (GB of disk space configured)'. If the oplog is too small, Atlas raises the event 'Auto-scaling: Disk auto-scaling didn't initiate due to insufficient oplog size' and does not scale. (two sources) verified-as-of: 2026-10-20[^c1-3][^c1-5]
- With storage auto-scaling on, Atlas manages the oplog by the minimum oplog retention window (default 24 hours). With it off, Atlas manages the oplog by size: 5% of disk for General and Low-CPU clusters, 10% for NVMe. When storage decreases, Atlas scales the oplog down in the same ratio, but never below those minimums. (two sources) verified-as-of: 2026-10-18[^c1-3][^c1-1]
- Write blocking is Atlas's last guard against a full disk. If the primary runs critically low on free disk, Atlas blocks writes on the replica set (on a sharded cluster, only writes routed to the affected shard) and keeps serving reads. Thresholds by total disk size: 8-20 GiB blocks below 600 MiB free and unblocks above 900 MiB; 20 GiB-1.25 TiB blocks below 4% free and unblocks above 6%; 1.25 TiB or more blocks below 50 GiB and unblocks above 75 GiB. It is active on M10+ clusters running MongoDB 8.0 or later. verified-as-of: 2026-10-14[^c1-22][^c1-6]
- NVMe clusters have a fixed disk size per tier and cannot resize storage independently. Auto-scaling moves them to the next higher tier when 90% of storage is consumed. Each NVMe tier change requires an initial sync, which is file-copy based on Atlas Core. (two sources) verified-as-of: 2026-10-20[^c1-26][^c1-3]
- Atlas bills dedicated-cluster storage by configured capacity, not by bytes used. The tier price includes the default capacity. If you set a custom capacity, Atlas charges for the full custom amount. Inference from this rule: blocks freed inside a disk lower the bill only after you also lower the configured disk size. (two sources) verified-as-of: 2026-10-18[^c1-23][^c1-1]
- On Gen2 dedicated clusters (AWS and Google Cloud, M30+), storage capacity and extended standard IOPS are configured independently, and Atlas bills them separately. The storage charge includes the baseline IOPS for that disk size. (two sources) verified-as-of: 2026-10-18[^c1-21][^c1-23]
- Atlas Infinite, in public preview as of October 2026, has no disk size and no storage auto-scaling to configure. Storage grows with data up to a max storage limit of 1 GB to 128 TB of logical data (field shardSizeLimitGB). Atlas blocks writes at the limit and keeps serving reads. Atlas meters storage hourly by uncompressed logical data size, including the oplog. (two sources) verified-as-of: 2026-10-14[^c1-24][^c1-25]
- WiredTiger keeps the space freed by deletes inside its data files and reuses it for later writes. It does not return that space to the operating system. Deleting documents therefore does not shrink disk usage. Dropping a collection or database removes its files and frees the space at once.[^c1-28][^c1-18][^c1-29][^c1-30]
- compact rewrites one collection and its indexes and tries to release obsolete blocks to the operating system. The manual says effectiveness depends on how many blocks are available to release and where they sit in the data file. It can free little or nothing, and it may need extra disk space to run. A first run can leave the physical size unchanged and need repeating.[^c1-10][^c1-31][^c1-18]
- The primary does not replicate compact to secondaries, so reclaiming disk on a replica set means running compact on each member. On a sharded cluster, run it on each shard's mongod. compact cannot run against mongos. Two concurrent compact commands on the same collection return an error.[^c1-10][^c1-30][^c1-18]
- The current manual says compact does not block CRUD operations on the database. Since MongoDB 6.1.0 (and 6.0.2) a secondary keeps replicating and serves reads while compact runs. Percona lists backports to 5.0.12 and 4.4.17 and says drop, createIndex(es), dropIndex(es) and collMod are still blocked. Percona's 2022 blog says that before 4.4 compact took a write lock on the database. (two sources) verified-as-of: 2026-10-20[^c1-10][^c1-28][^c1-18]
- Tentative: Index storage size can differ across replica set members that hold identical data, because secondaries apply writes in different batches and order. To bring an oversized index back in line, compact that node, initial sync it, or drop and recreate the index. Account for this variation when planning capacity.[^c1-10]

## Tools & Frameworks

- compact options by version: freeSpaceTargetMB (default 20 MB, the minimum recoverable space for compaction to proceed) since 7.3; dryRun and the autoCompact command since 8.0. With dryRun: true, compact only returns estimatedBytesFreed. A real run returns bytesFreed. On a replica set primary, compact needs force: true. verified-as-of: 2026-10-20[^c1-10][^c1-13][^c1-11] _(Atlas storage auto-scaling and disk reclaim via compact)_
- compact is not replicated, so you run it on each node. On Atlas, rs.stepDown() and member-priority changes are unsupported, so the compact reference says to run compact on every node and use force: true on the primary. MongoDB staff and an official App Services page describe another route: compact each secondary one at a time, run Test Primary Failover in Atlas, then compact the former primary. verified-as-of: 2026-10-20[^c1-10][^c1-14][^c1-9] _(Atlas storage auto-scaling and disk reclaim via compact)_
- autoCompact (new in 8.0) turns on background compaction: the server walks all files and compacts whenever enough space is recoverable. For Atlas, the compact reference suggests autoCompact to avoid running compact on every node. It is not supported on M0 and Flex clusters. With authentication on, Atlas users need the Atlas-only built-in role 'autoCompact', which grants the cluster 'compact' action. verified-as-of: 2026-10-20[^c1-11][^c1-10][^c1-12] _(Atlas storage auto-scaling and disk reclaim via compact)_
- With autoCompact on, the server tries to keep free space in each collection and index below freeSpaceTargetMB (default 20). Before enabling it, run $collStats with storageStats: {} and compare freeStorageSize to freeSpaceTargetMB. If freeStorageSize is smaller, background compaction has no effect. (two sources) verified-as-of: 2026-10-20[^c1-11][^c1-13][^c1-10] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: autoCompact details: runOnce: true makes one pass over every collection on the node. runOnce: false runs continuously and retries a collection that failed to compact after about one hour. It skips the oplog. It applies the same blocking behavior as compact, so a second call while it runs returns an error; send { autoCompact: false } first. After a mongod restart it stays off unless the enableAutoCompaction parameter is true (default disabled). It is not replicated, so enable it per node and per shard, never through mongos. verified-as-of: 2026-10-20[^c1-11] _(Atlas storage auto-scaling and disk reclaim via compact)_
- autoCompact (new in MongoDB 8.0) runs background compaction. It iterates over the available files and compacts when enough free space is recoverable. freeSpaceTargetMB sets that minimum (default 20 MB). runOnce: true makes one pass over every collection. A collection that fails to compact is retried after about an hour. The oplog is excluded. autoCompact applies the same blocking behavior as compact, and a second autoCompact call while one is active returns an error. verified-as-of: 2026-10-20[^c1-11][^c1-10] _(Atlas storage auto-scaling and disk reclaim via compact)_
- On Atlas, autoCompact is supported only on dedicated clusters running MongoDB 8.0 or later, and not on M0 or Flex clusters. The database user needs the autoCompact privilege (built-in role). Connect to each node and run the command against the admin database. For a sharded cluster, fetch each node's connection string from the Atlas Administration API. verified-as-of: 2026-10-20[^c1-21][^c1-11] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: If Terraform manages an auto-scaled Atlas cluster, enable effective fields (API header Use-Effective-Instance-Fields: true). Spec attributes then keep your configured diskSizeGB and instanceSize, and the auto-scaled values appear in effective specs such as effectiveElectableSpecs, so no drift occurs. Without effective fields you must add lifecycle.ignore_changes, which the docs do not recommend. verified-as-of: 2026-10-14[^c1-7] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Atlas logs every auto-scaling event in the project Activity Feed. The disk events are 'Disk auto-scaling initiated', 'Disk auto-scaling didn't initiate due to the cluster reaching maximum available disk size' and 'Disk auto-scaling didn't initiate due to insufficient oplog size'. Since early August 2024 these are configurable alerts that default to project owners. The default 'Disk space % used on Data Partition' alert fires at 90% of configured storage. verified-as-of: 2026-10-20[^c1-5][^c1-7][^c1-6] _(Atlas storage auto-scaling and disk reclaim via compact)_

## Methodology

- Synthesis: lowering an Atlas bill after a large purge takes three separate steps. First, free space inside the files: delete or archive, then compact every node. Second, confirm used disk on every node fits the smaller size. Third, reduce storage by hand, which Atlas does through the new-volume sync with per-node downtime. Compaction alone leaves the provisioned size and cost unchanged, and auto-scaling never lowers it. One 2022 user could shrink the disk only after compacting the primary as well. (two sources) verified-as-of: 2026-10-18[^c1-3][^c1-1][^c1-14][^c1-15] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Atlas community threads give these connection details for per-node compact: connect straight to each node, not through the mongodb+srv:// string (node hostnames are in the metrics view), set tls=true and usually authSource=admin. One user fixed a failed secondary connection by adding directConnection=true. (two sources)[^c1-16][^c1-17] _(Atlas storage auto-scaling and disk reclaim via compact)_
- On Atlas, rs.stepDown() and member-priority changes are unavailable, so the self-managed sequence 'compact secondaries, step down, compact the old primary' does not apply as written. The manual says to run compact on every node and to use force: true on the current primary. A MongoDB forum answer (February 2025) instead says to compact secondaries one at a time, run Atlas Test Failover, then compact the former primary. (two sources) verified-as-of: 2026-10-14[^c1-10][^c1-30] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Percona's checklist before compacting: take a full backup, confirm the replication oplog window is large enough, run compact on secondary and hidden nodes first, and compact the primary last after stepping it down. The MongoDB manual gives the same secondary-first order for self-managed replica sets. (two sources)[^c1-18][^c1-10] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Measure reclaimable space before acting. Run collStats (or $collStats with storageStats) and read freeStorageSize. If freeStorageSize is below freeSpaceTargetMB, background compaction has no effect. On 8.0+, compact with dryRun: true returns estimatedBytesFreed without compacting. Percona reads db.<collection>.stats().wiredTiger['block-manager']['file bytes available for reuse'] per collection.[^c1-11][^c1-10][^c1-18] _(Atlas storage auto-scaling and disk reclaim via compact)_

## Practical Patterns

- With storage auto-scaling on, the disk size Atlas holds drifts from the Terraform value. The Atlas scalability guidance warns that applying a plan then sets the disk back to the original disk_size_gb. Per the storage-change docs, any reduction takes the new-volume sync path. Set use_effective_fields = true (API header 'Use-Effective-Instance-Fields: true') so the spec keeps your configured values and the effective specs show the auto-scaled ones. verified-as-of: 2026-10-20[^c1-7][^c1-8][^c1-3] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Atlas logs every auto-scaling event in the project Activity Feed, with the triggering metric and threshold. Auto-scaling alerts are set per project and cannot be scoped to one cluster. The default 'Disk space % used on Data Partition' alert fires at 90% of configured storage. It can fire even with Auto-Expand Storage on, when the disk fills too fast or the tier's maximum storage is reached. verified-as-of: 2026-10-20[^c1-7][^c1-6][^c1-5] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Archive or expire history first, then compact. The Atlas scalability guidance recommends data tiering, archival and TTL indexes to cut storage cost. Percona's field report: a cloud customer on eight shards (4 TB per node, 96 TB across all nodes) archived data and ran compact, cutting each node to 2.5 TB (60 TB total) and the cloud bill with it. The report dates from August 2022 and names no Atlas cluster. (two sources)[^c1-8][^c1-18] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Before a bulk insert, migration or other high-speed write job, raise disk capacity (or the tier) by hand instead of waiting for the 90% trigger. The Atlas docs advise scaling up in advance of bulk inserts. (two sources)[^c1-1][^c1-6] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Compact outcomes vary widely. Percona reports a customer whose per-node footprint fell from 4 TB to 2.5 TB (96 TB to 60 TB across eight shards) after archiving data and compacting. On an Atlas 6.0.24 three-node replica set with about 2 TiB of free blocks, compact on each collection freed about 1 TiB per node, and a second run freed no more. (two sources)[^c1-18][^c1-31] _(Atlas storage auto-scaling and disk reclaim via compact)_
- A rolling resync (initial sync, one member at a time) rebuilds a member's data files compactly. Percona's advisor calls it the safest way to reclaim disk, with no downtime or application impact, but slow for large data. Netdata adds that the sync source's oplog window must cover the sync and that only one member of a three-node set should resync at a time. The MongoDB manual also lists initial sync as an alternative to compact.[^c1-28][^c1-29][^c1-10] _(Atlas storage auto-scaling and disk reclaim via compact)_
- A MongoDB forum answer (February 2025) says that more often than not there is no need to compact, because WiredTiger is a no-overwrite engine that reuses free blocks for new writes before it extends files. Inference: compaction pays off when you intend to shrink the disk or when the freed space will not be reused soon. (two sources)[^c1-30][^c1-28] _(Atlas storage auto-scaling and disk reclaim via compact)_

## Anti-Patterns

- Bulk writes can outrun a storage scale-up. Atlas needs time to prepare and copy data to new disks, so a bulk insert or data migration can fill the disk first, and the 'Disk Space % Used' alert fires even with Auto-Expand Storage on. Scale up before bulk loads.[^c1-1][^c1-6] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Compaction, manual or automatic, checkpoints the database regularly. On busy systems that can delay or prevent backups, so the docs say to disable compaction before a backup. The autoCompact page also recommends running it in low-traffic periods. (two sources)[^c1-10][^c1-11] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: If a deployment uses secondary reads and multi-shard transactions, MongoDB advises an initial sync instead of compact. Compact makes WiredTiger adjust its block-manager strategy, which slows checkpoints and delays transaction commits. The docs name read latency, replication lag and operational queuing as the result. verified-as-of: 2026-10-20[^c1-10] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: Inference, not a documented rule: compact may need extra disk space to run, and a write-blocked Atlas node also rejects deletes. So start compaction well before the write-block threshold. The docs give no safe free-space margin.[^c1-10][^c1-4] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Compaction checkpoints the database regularly. On a busy database this can delay or prevent backups, so disable compaction (compact or autoCompact) before taking a backup.[^c1-10][^c1-11] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: If a deployment uses secondary reads and multi-shard transactions, compact makes WiredTiger adjust its block-manager strategy, which can slow checkpoints and delay transaction commits. The manual warns this can cause significant read latency, replication lag and operational queuing, and suggests an initial sync instead of compact.[^c1-10] _(Atlas storage auto-scaling and disk reclaim via compact)_

## Troubleshooting

- When the primary runs critically low on free disk, Atlas blocks writes on the replica set and keeps serving reads. On sharded clusters only writes routed to the affected shard are blocked. Writes resume automatically once free space passes the unblock threshold. Fix: raise storage or enable storage auto-scaling. Write blocking is active on M10+ clusters running MongoDB 8.0 or later. (two sources) verified-as-of: 2026-10-20[^c1-4][^c1-6] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: Atlas write-block thresholds by node disk size: 8 to 20 GiB blocks below 600 MiB free and unblocks above 900 MiB; 20 GiB to 1.25 TiB blocks below 4% free and unblocks above 6%; 1.25 TiB and up blocks below 50 GiB free and unblocks above 75 GiB. Blocked writes include deletes, because deleting can temporarily raise used disk. Logs show 'Replica set writes blocked, reason: InsufficientDiskSpace' on FCV 9.0 or later, and 'User writes blocked, reason: DiskUseThresholdExceeded' on earlier FCV. verified-as-of: 2026-10-20[^c1-4] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: Atlas disables disk auto-scaling when the base nodes and analytics nodes use different cluster tier classes, for example a General base tier with a Low-CPU analytics tier. The message is 'Disk auto-scaling is not yet available for clusters with mixed instance classes.'. verified-as-of: 2026-10-18[^c1-1] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: Reported failure: after an auto-scale from 8 to 32 GB, deleting data and compacting one collection, a user saw 6.15 GB used but Atlas rejected a resize to 8 GB with 'The selected disk size (8.0 GB) is smaller than the amount of data currently used (16.04489517211914 GB)'. The January 2024 thread has no answer. A 2022 thread suggests Atlas judges disk by the primary's usage, and that user could shrink only after compacting the primary. The cause in the 2024 case is unconfirmed.[^c1-15][^c1-14] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: autoCompact skips the oplog. In a 2022 Atlas thread (M10, MongoDB 4.4), shrinking the oplog from the console did not free disk until compact ran on oplog.rs on each secondary, then on the former primary after Test Failover.[^c1-11][^c1-14] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: Index storage size can differ across replica set members holding identical data, because each node applies writes to its indexes independently. Remedies: compact the affected node, run an initial sync of it, or drop and recreate the index. Plan capacity for that variation.[^c1-10] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: For dedicated Atlas Core clusters, restoring a snapshot larger than the destination cluster's storage does not trigger auto-scaling. verified-as-of: 2026-10-18[^c1-3] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Tentative: Write-blocking log errors depend on the cluster feature compatibility version. FCV 9.0 or later returns a MongoServerError like 'Replica set writes blocked, reason: InsufficientDiskSpace'. Earlier FCV returns 'User writes blocked, reason: DiskUseThresholdExceeded'. verified-as-of: 2026-10-14[^c1-22] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Blocked writes include deletes, because deleting documents can temporarily increase used disk. Deleting data therefore cannot free space while writes are blocked. Recovery is to increase cluster storage or enable storage auto-scaling. Atlas unblocks writes by itself once free space on the primary rises above the unblock threshold. (two sources) verified-as-of: 2026-10-14[^c1-22][^c1-6] _(Atlas storage auto-scaling and disk reclaim via compact)_
- Storage auto-scaling can lose a race with the workload. Atlas needs time to prepare and copy data to new disks. A burst of high-speed writes, such as a bulk insert or a data migration, can fill the disk before the scale-up finishes. Other causes of a Disk Space % Used alert: auto-expand is off, or the cluster is already at the maximum storage for its tier. verified-as-of: 2026-10-18[^c1-1][^c1-6] _(Atlas storage auto-scaling and disk reclaim via compact)_
- When a cluster reaches the maximum storage for its tier, disk auto-scaling cannot add more. Atlas raises the event 'Disk auto-scaling didn't initiate due to the cluster reaching maximum available disk size'. Options are a larger tier, extended storage, or sharding. ## Disagreements & Open Questions

- Disagreement (Atlas storage auto-scaling and disk reclaim via compact): The Atlas scalability guidance says that with disk_gb_enabled Atlas 'will automatically scale disk size up and down'. The dedicated storage page says Atlas 'auto-scales cluster storage up only' and that reductions are manual. The storage page is the specific one, and no source found describes automatic storage scale-down. The scalability wording is probably loose.[^c1-8][^c1-1]
- Disagreement (Atlas storage auto-scaling and disk reclaim via compact): Which node's disk counts: the storage page says scaling triggers when disk space used reaches 90% for any node. A 2022 forum user observed that the size Atlas counts for the storage autoscaler is the primary's, and could shrink the disk only after compacting the primary. The two accounts are not reconciled.[^c1-1][^c1-14]
- Disagreement (Atlas storage auto-scaling and disk reclaim via compact): Handling the primary during compact: the current compact reference says to run compact on every Atlas node and use force: true on the primary. A 2022 MongoDB staff reply, a 2024 community reply and the App Services page say to run Test Primary Failover and compact the former primary. Both routes are documented. No source says which is safer for a busy primary.[^c1-10][^c1-14][^c1-16][^c1-9]
- Disagreement (Atlas storage auto-scaling and disk reclaim via compact): How to compact the Atlas primary. The compact manual says to run compact on every node and use force: true on the primary, because Atlas lacks rs.stepDown(). A MongoDB forum answer (February 2025) says to compact secondaries one at a time, run Atlas Test Failover, then compact the former primary. The thread's original poster also reported that compaction only worked on the primary.[^c1-10][^c1-30]
- Disagreement (Atlas storage auto-scaling and disk reclaim via compact): EBS cooldown. The Atlas storage page still describes a 6-hours-per-TB volume modification cooldown that decides between an in-place change and new volumes. - Disagreement (Atlas storage auto-scaling and disk reclaim via compact): What compact blocks. The manual says compact does not block CRUD operations.
