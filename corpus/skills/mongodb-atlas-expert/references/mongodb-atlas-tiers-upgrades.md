## M30 (AWS) specifications

- **2 vCPUs, 8 GB RAM per node** (3-node replica set = 8 GB on each data-bearing node). **QUALIFIED** [^1][^4]
- **Max 3,000 concurrent incoming connections per node.** Atlas connection limits are per node, set via `net.maxIncomingConnections` by tier and class. **QUALIFIED** [^1][^2]
- On M30 and smaller tiers, WiredTiger cache is ~**25% of physical RAM** (vs the self-managed default of 50% of (RAM−1 GB)) — ≈2 GB WT cache on an M30. **QUALIFIED** [^1]
- M30 is the smallest tier MongoDB recommends for production; AWS-backed instances at M30 get up to 10 Gb/s network. **QUALIFIED** [^1][^4]
- Cross-check heuristic: any claimed concurrent-connection count **above 3,000 on an M30 is impossible** — treat it as a misread metric (e.g. cumulative `connections.totalCreated` rather than `connections.current`).

## Connection limits by tier

- M10: 1,500 connections/node; M10 + M20 additionally have a **connection-rate limit of 15 new connections/second/node**; M40+ has no rate limit (M30 sits between — no rate limit documented in that table). **QUALIFIED** [^2]
- Limits apply per node, not per cluster. **FACT** [^2]

## Major-version upgrade mechanics

- Upgrade is a **rolling process**: secondaries first, then the primary is directed to step down and a new primary is elected, then the former primary is upgraded. **At least one replica-set election is required** — writes hold during the election (typically seconds). **FACT** [^3][^5]
- Cluster must be healthy before upgrading; take/wait for snapshots first. **QUALIFIED** [^3]
- Full auto-upgrade cadence (maintenance windows/EOL-forced upgrades), the 2-major-version FCV ceiling, the 8.0 write-blocking mechanism, and the FCV pin/no-downgrade rule are covered in depth, with primary-source citations, in `references/mongodb-atlas-managed-upgrades.md` — this file does not restate them.
- The docs do **not** state whether nodes are binary-swapped in place or re-provisioned onto new instances, and do **not** mention cold-cache or plan-cache effects post-upgrade (verified absence — the restart-implies-empty-WT-cache effect is real but undocumented on this page). **TENTATIVE (absence verified 2026-07-14)** [^3]

## FCV pinning & the no-downgrade rule

See `references/mongodb-atlas-managed-upgrades.md` §3 and §5 for the 2-major-version FCV ceiling, the 4-week pin window, and the no-downgrade-without-pin rule with full citations. Practical consequence for support cases: a customer who upgraded without pinning FCV **cannot A/B the old version in place** — the only clean re-baseline is a new cluster on the old major version.

## Hardware generations: Atlas Gen2 on AWS (2026)

- **Atlas Gen2** infrastructure for M30+ dedicated AWS clusters: GA **June 30, 2026** (announced July 7, 2026), initially in select AWS regions. Newer **ARM-based processors**; internal pilot claims 15–20% CPU-utilization reduction and ~45% lower read/write latency; IOPS scaling decoupled from storage capacity. **QUALIFIED (vendor-only claims)** [^6]
- New clusters in supported regions default to Gen2; existing clusters are not force-migrated (no app changes required when they do move). Exact migration triggers for existing clusters (maintenance windows? tier changes?) are not documented in the announcement. **TENTATIVE** [^6]
- Case-analysis implication: from mid-2026 the AWS M30+ fleet is **heterogeneous across hardware generations (x86 Gen1 vs ARM Gen2)** — two clusters of the same tier, or the same cluster before/after a re-provision, can sit on materially different hardware. When comparing benchmark runs across an upgrade or across clusters in this era, confirm the instance generation with Atlas support rather than assuming tier ⇒ identical hardware.

## Post-upgrade performance expectations

What is and isn't expected right after a major-version upgrade:

1. **Expected**: empty WiredTiger cache on each restarted node (rolling restart = every node restarts), reset plan cache, re-established connections. First workload pass pays cache-warming costs.
2. **Expected**: one election's worth of write pause.
3. **Not documented, verify per case**: instance re-provisioning / hardware-generation change during the upgrade — ask Atlas support for the node instance metadata before/after if a hardware hypothesis matters (see Gen2 above).
4. **Not expected**: persistent (post-warm-up) latency regression — if one persists, treat it as a real regression to diagnose (see `mongodb-expert/references/mongodb-80-performance-changes.md` for the 8.0 regression catalog and the 7→8 diagnostic checklist).
